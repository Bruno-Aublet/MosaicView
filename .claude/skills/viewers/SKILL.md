# Visionneuses plein-écran — MosaicView

Deux fenêtres plein-écran distinctes affichent une image en grand avec zoom/pan (une troisième, `StraightenViewerDialog`, a été supprimée en v1.7.3 ; une quatrième, `CloneZoneViewerDialog`, a été supprimée en v1.7.3+ ; une cinquième, `TextViewerDialog`, a été supprimée en v1.7.3+ — voir section dédiée ci-dessous). Toutes héritent de `QDialog`, sont non-modales (règle UI n°4), et partagent un vocabulaire commun (`zoom_level`/`_zoom`, `adjust_zoom`, `reset_zoom`, `fit_to_window`) — mais **ce sont des implémentations séparées**, pas une classe commune : une correction ou un ajout dans l'une ne se propage jamais automatiquement aux autres (voir historique récent : le pan écrasé au zoom, le lag à fort zoom, Ctrl+0/Ctrl+1/Ctrl+Plus/Ctrl+Minus ont dû être portés fichier par fichier).

## Les 2 visionneuses restantes

| Fichier | Classe | Rôle | Ouverte depuis |
|---|---|---|---|
| `modules/qt/image_viewer_qt.py` | `ImageViewer` | Visionneuse principale de lecture (pages simple/double/continue, GIF animés — lecture seule, voir skill `animated-gif` pour la création/édition, crop/redressement/clonage/texte — voir section barre d'outils ci-dessous, marque-page) | Double-clic sur une vignette de la mosaïque → `panel_widget.py::_open_image_viewer` → `open_image_viewer()` ; aussi ouverte avec un outil présélectionné (`initial_tool="crop"`/`"straighten"`/`"clone"`/`"text"`) depuis les commandes Recadrer/Redresser/Cloner/Texte (voir section barre d'outils) |
| `modules/qt/adjustments_viewers_qt.py` | `AdjustmentViewerDialog` | Aperçu/édition plein écran pour 8 modes de retouche (voir tableau ci-dessous) | Bouton "aperçu plein écran" de chaque onglet dans `adjustments_dialog_qt.py::_open_viewer(mode)` |

## Fusion progressive en une seule visionneuse — barre d'outils flottante (v1.7.3, en cours — 4 outils migrés)

**Chantier en cours, pas terminé** : idée retenue dans `idees.txt` (section "VISIONNEUSES — FUSIONNER PROGRESSIVEMENT EN UNE SEULE VISIONNEUSE") visant à fondre à terme la visionneuse annexe restante (ajustements — recadrage, redressement, clonage et texte sont déjà faits) DANS la visionneuse principale de lecture (`ImageViewer`), en la remplaçant par une sélection d'outil dans une barre flottante plutôt que par l'ouverture d'une fenêtre dédiée par outil. Méthode strictement progressive (jamais de big-bang) : chaque outil est ajouté à la barre SANS supprimer sa fenêtre dédiée existante, testé, puis seulement l'ancienne fenêtre est retirée avant de passer à l'outil suivant. Se référer à `idees.txt` pour le détail complet des décisions de design (composition de la barre, comportement d'auto-masquage, undo/redo unifié, persistance du travail non validé...) — ce skill documente uniquement ce qui est réellement implémenté à date.

**État actuel (v1.7.3)** : quatre outils ont une icône dans la barre — le recadrage, le redressement manuel, le clonage de zone, et l'insertion de texte riche. Les trois anciennes fenêtres dédiées correspondantes (`StraightenViewerDialog`/`straighten_viewer_qt.py`, `CloneZoneViewerDialog`/`clone_zone_viewer_qt.py`, `TextViewerDialog`/`text_viewer_qt.py`) ont été **entièrement supprimées**, pas seulement mises de côté. La visionneuse annexe ajustements n'a pas encore été touchée.

### Architecture en modules séparés — RÈGLE ABSOLUE (CLAUDE.md)

**Le code de chaque outil migré ne vit JAMAIS dans `image_viewer_qt.py`.** Consigne expresse de l'utilisateur donnée dès le début de ce chantier, inscrite dans `CLAUDE.md` (section "Règles générales de collaboration") après un refactor correctif le 2026-08-12 : les 3 premiers outils avaient été implémentés directement dans `image_viewer_qt.py` au fil des sessions, rendant le fichier de plus en plus difficile à gérer. Chaque outil a désormais son propre module :

| Module | Contenu |
|---|---|
| `modules/qt/crop_tool_qt.py` | `CropCanvasMixin`, `CropViewerMixin` |
| `modules/qt/straighten_tool_qt.py` | `_StraightenAnglePanel`, `StraightenCanvasMixin`, `StraightenViewerMixin` |
| `modules/qt/clone_tool_qt.py` | `_CloneOptionsPanel`, `CloneCanvasMixin`, `CloneViewerMixin` |
| `modules/qt/text_tool_qt.py` | `_ColorPickerDialog`, `_TextOptionsPanel`, `TextCanvasMixin`, `TextViewerMixin` — détail complet dans le skill `add-text-to-image` |
| `modules/qt/viewer_toolbar_qt.py` | `_ToolButton`, `_ActionButton`, `_ViewerToolbar` (composant transversal, pas un outil au sens strict, mais même principe de séparation appliqué par cohérence) |

**Pattern retenu — deux mixins par outil**, hérités par les deux classes centrales de `image_viewer_qt.py` :
- `*CanvasMixin` : état + interactions souris (mousePress/Move/Release, curseur, rendu de l'overlay) — hérité par `_ViewerCanvas` (`class _ViewerCanvas(CropCanvasMixin, StraightenCanvasMixin, CloneCanvasMixin, TextCanvasMixin, QLabel)`).
- `*ViewerMixin` : commit de l'opération dans l'historique du panneau (perform_*, validate_*, persistance par page) — hérité par `ImageViewer` (`class ImageViewer(CropViewerMixin, StraightenViewerMixin, CloneViewerMixin, TextViewerMixin, QDialog)`).

Chaque mixin `*CanvasMixin` expose une méthode `_init_xxx_state()` appelée explicitement dans `_ViewerCanvas.__init__` (pas de `__init__` propre au mixin, pour éviter tout conflit de MRO/super() avec les autres mixins et `QLabel`). Le canvas délègue depuis ses handlers réels (`mousePressEvent`/`mouseMoveEvent`/`mouseReleaseEvent`/`paintEvent`) vers les méthodes du mixin correspondant à l'outil actif (`self.crop_mouse_press(event)`, `self.paint_straighten_line(painter)`, etc.) — jamais de logique d'outil inline dans ces handlers.

**Ce qui reste dans `image_viewer_qt.py`** (points de couplage transversaux, pas spécifiques à un seul outil) :
- Le bouton "Valider" flottant du canvas (`_ensure_validate_btn`/`_show_validate_btn`/`_hide_validate_btn`/`_VALIDATE_KEYS`), **partagé** entre crop, straighten et text (un seul widget, texte/action selon l'outil actif — `_VALIDATE_KEYS = {"crop": ..., "straighten": ..., "text": ...}`, pas d'entrée `"clone"`) — ne peut pas appartenir à un seul module d'outil.
- `_ignore_crop_events` et `mouseDoubleClickEvent`, qui gèrent aussi le double-clic plein écran général (pas seulement la validation du crop).
- La logique générique de la visionneuse (zoom, pan, navigation, GIF, undo/redo unifié, fermeture, `_crop_by_page`/`_straighten_by_page` — les dicts de persistance par page restent définis dans `ImageViewer.__init__`, seules les méthodes `_save_*_for_current_page`/`_restore_*_for_page` sont dans les mixins).

**Import circulaire évité par import différé en local** : `clone_tool_qt.py::_clone_refresh_display` et `viewer_toolbar_qt.py::_ActionButton._load_icon` importent `_pil_to_qpixmap` depuis `image_viewer_qt.py` **à l'intérieur de la fonction**, pas au niveau module — `image_viewer_qt.py` important lui-même ces modules au niveau module, un import croisé au niveau module créerait un cycle.

**Fichiers `.spec` (PyInstaller)** : PAS à mettre à jour pour ces nouveaux modules — vérifié le 2026-08-12. Ils sont importés statiquement (pas dynamiquement) par `image_viewer_qt.py`, déjà présent dans `hiddenimports` des deux `.spec` (`MosaicView_ONE_DIR.spec`/`MosaicView_ONE_FILE.spec`) ; PyInstaller détecte les imports statiques transitifs automatiquement. Confirmé par `straighten_geometry.py` (module équivalent d'une extraction antérieure), qui n'y figure pas non plus et fonctionne dans les builds existants.

### Comportement de la barre (`_ViewerToolbar`, `viewer_toolbar_qt.py`)

- Widget flottant en surimpression de `_ViewerCanvas`, ancré en haut et centré horizontalement, **jamais inséré dans le layout** de `ImageViewer` (son apparition/disparition ne redimensionne donc jamais l'image affichée dessous). Instancié dans `ImageViewer.__init__` (`self._toolbar`), juste après la création de `self._canvas`.
- **Aucun outil présélectionné par défaut** (`set_active_tool(None)` en fin de `_ViewerToolbar.__init__`) — corrige un bug où le crop restait présélectionné à *chaque* ouverture de la visionneuse, y compris un simple double-clic sur une vignette. Un outil n'est présélectionné que si `ImageViewer(..., initial_tool="crop"|"straighten"|"clone"|"text")` le demande explicitement (voir plus bas).
- **Auto-masquage / survol** : masquée par défaut (`self.hide()` à la construction), réapparaît quand la souris entre dans les 10% supérieurs du canvas (`HOVER_ZONE_RATIO = 0.10`, détecté dans `_ViewerCanvas.mouseMoveEvent` via `self._viewer._toolbar.on_canvas_mouse_move(...)`, appelé en tout premier avant les branches pan/crop/straighten/clone existantes), se remasque après 3 secondes d'inactivité (`AUTO_HIDE_MS = 3000`) que ce soit à l'état "aucun outil" ou pendant qu'un outil est actif — même règle dans les deux cas. Repositionnée à chaque `resizeEvent` du canvas (`_ViewerCanvas.resizeEvent` appelle `self._viewer._toolbar.reposition()` si visible), même pattern que le bouton "Valider" flottant.
- **Sélection d'outil** : `self.active_tool` (`str | None`, `None` = "aucun outil", sinon `"crop"`/`"straighten"`/`"clone"`/`"text"`). Un seul outil actif à la fois. Cliquer sur l'icône d'un outil l'active ; re-cliquer sur l'icône déjà active la désélectionne (`_on_tool_clicked` → `set_active_tool(None)`). **Aucune icône dédiée "désélectionner tout"** (option écartée dans `idees.txt`) — uniquement le re-clic sur l'icône active, plus la touche Échap qui annule un rectangle de crop ou un trait de redressement en cours (ou efface la source de clonage) via `_on_escape` (ordre de priorité : crop d'abord, puis straighten, puis clone, puis plein écran, puis fermeture — mais ne désélectionne PAS l'icône de la barre, écart connu, jugé non gênant par l'utilisateur, volontairement pas corrigé ; le texte n'est pas dans cette chaîne, un bloc vide abandonné se nettoie via son propre mécanisme — voir skill `add-text-to-image`).
- **`_ToolButton`** (`QLabel`, icône d'outil sélectionnable) : survol = légère surbrillance temporaire (`theme['icon_hover']`) ; état actif = surbrillance **permanente** avec bordure (`border: 2px solid {theme['text']}`), visuellement distincte du simple survol — obligatoire (règle actée dans `idees.txt`, à respecter pour tout futur outil ajouté à la barre). Icônes actuelles : `BTN_Crop.png` (crop), `BTN_Straighten.png` (straighten), `BTN_Clone_Zone.png` (clone), `BTN_Text.png` (texte). **L'icône straighten est en plus bi-mode** (clic droit bascule `state.straighten_mode` manuel/auto, comme son homologue de la colonne d'icônes) — détail complet dans le skill `page-straighten`, hors périmètre de ce skill-ci au-delà de ce pointeur. Tout `mousePressEvent`/`mouseReleaseEvent` custom sur un widget de cette barre doit `event.accept()` les deux boutons (gauche et droit) : sans ça, un clic droit fuit vers `_ViewerCanvas` en dessous et ouvre son menu contextuel par accident (piège corrigé sur `_ToolButton`/`_ActionButton`/`_ViewerToolbar` elle-même en v1.7.3).
- **`_ActionButton`** (`QLabel`, action instantanée type undo/redo) : classe **distincte** de `_ToolButton` — pas de notion d'outil actif/sélectionné, seulement activé/désactivé (grisé). Réutilise l'algorithme de grisage PIL de `icon_toolbar_qt._to_grayscale` (conversion niveaux de gris + éclaircissement, pas une simple opacité Qt) et les icônes déjà existantes de la colonne d'icônes verticale (`BTN_Batch_Undo.png`/`BTN_Batch_Redo.png`) — ne jamais dupliquer/réinventer ces icônes ou cet algorithme.
- **Bouton "Valider" flottant partagé crop+straighten+text** (`_ViewerCanvas._show_validate_btn`/`_hide_validate_btn`, `image_viewer_qt.py`) : **un seul** `QPushButton`, réutilisé par ces trois outils plutôt qu'un par outil — texte et action câblés dynamiquement selon `self._viewer._toolbar.active_tool` (`_VALIDATE_KEYS = {"crop": "buttons.validate_crop", "straighten": "buttons.validate_straighten", "text": "buttons.validate_text"}`, **pas d'entrée `"clone"`**, voir plus bas). L'état de connexion du signal `clicked` est mémorisé dans `_validate_btn_connected_tool` pour ne le reconnecter que lors d'un vrai changement d'outil — **piège corrigé** : un `disconnect()` inconditionnel à chaque appel de `_show_validate_btn()` déclenchait un `RuntimeWarning: Failed to disconnect (None) from signal "clicked()"` de PySide6 au tout premier affichage (aucun slot encore connecté).
- **Panneau flottant de la spinbox d'angle** (`_StraightenAnglePanel`, `straighten_tool_qt.py`) : positionné sous `_ViewerToolbar` (`y = 8 + toolbar.height() + 6`), visible uniquement quand `active_tool == "straighten"` **et** qu'un trait existe sur la page courante (`set_visible_for_tool`). Contient un `QLabel` (libellé `dialogs.straighten_viewer.angle_label`, réutilisé tel quel de l'ancienne fenêtre) + un `QDoubleSpinBox` (plage `[-90, 90]`, pas `0.1°`). **Indépendant du timer d'auto-masquage de la barre d'outils** — reste affiché même si `_ViewerToolbar` se masque après 3s d'inactivité, pour ne pas interrompre un réglage d'angle en cours.
- **Panneau flottant des réglages du tampon** (`_CloneOptionsPanel`, `clone_tool_qt.py`) : même principe que `_StraightenAnglePanel`, visible uniquement quand `active_tool == "clone"`. Mode source (fixe/relatif) et taille du tampon (slider + spinbox, 1-400px). **Style non trivial** : plusieurs itérations nécessaires avant de trouver un rendu lisible — `QRadioButton`/`QCheckBox` avec `::indicator` stylé restent invisibles sur ce panneau à fond `WA_StyledBackground` (testé, abandonné), un `QSlider` sans `::sub-page`/`::add-page` explicitement stylés donne un rendu sombre uniforme dès que `::groove`/`::handle` le sont. Solution retenue : `QPushButton` checkable plein (texte + fond coloré à l'état actif), même mécanisme que `_ToolButton` de la barre principale — pas d'indicateur séparé à styler.
- **Panneau flottant de formatage rich text** (`_TextOptionsPanel`, `text_tool_qt.py`) : même principe de positionnement, mais condition de visibilité différente — visible uniquement quand `active_tool == "text"` **ET** qu'un bloc de texte est actif (pas juste l'outil sélectionné, un outil sans bloc actif n'a rien à formater). Contient le sélecteur de couleur maison `_ColorPickerDialog` en remplacement de `QColorDialog`. Détail complet dans le skill `add-text-to-image`.
- **Undo/Redo dans la barre** : `refresh_undo_redo_state()` pilote l'état activé/désactivé via `can_undo(state)`/`can_redo(state)` (`modules.qt.undo_redo`, mêmes fonctions que la colonne d'icônes verticale). Appelée après chaque undo/redo (`ImageViewer._refresh_after_undo_redo`), après `perform_crop()`, après `perform_straighten()`, après `perform_text()`, et après `_on_clone_paint_end()` (chacune crée une nouvelle entrée d'historique). **Piège pour les futurs outils** : toute nouvelle opération d'un outil de la barre qui appelle `save_state()` doit aussi rafraîchir `self._toolbar.refresh_undo_redo_state()`, sinon les icônes undo/redo de la barre restent dans un état obsolète après usage de cet outil.
- **Undo/redo unifié** (décision actée dans `idees.txt`, appliquée aux 4 outils migrés) : la barre pilote le **même historique unique que le panneau** (`undo_action`/`redo_action` dans `self.callbacks`, déjà utilisés par `Ctrl+Z`/`Ctrl+Y`) — `perform_straighten()`/`perform_text()` font `save_state()` avant modification puis `save_state()` (sans `force=True`) après, exactement comme `perform_crop()`. Pour le texte, un seul point d'historique est créé à la validation ("Appliquer", pas à chaque frappe) — l'undo de frappe Qt natif (`document().undo()/redo()`) reste local à chaque overlay tant qu'il a le focus, comportement standard de `QTextEdit`, pas un second système ajouté (voir skill `add-text-to-image`). Pour le clonage, chaque coup de tampon relâché appelle `save_state()` avant + `save_state(force=True)` après dans `_on_clone_paint_end()` (`clone_tool_qt.py`) — voir "Le clonage : différent des autres outils" ci-dessous, chaque stroke devient sa propre entrée d'historique, accepté explicitement par l'utilisateur ("l'historique correspond à la réalité de ce que fait l'utilisateur"). Aucun outil migré n'a d'historique local séparé, contrairement aux anciennes fenêtres dédiées.
- **Rafraîchissement après un undo/redo déclenché HORS de la visionneuse** (icône colonne verticale, menu Édition, `Ctrl+Z`/`Ctrl+Y` du panneau) : `refresh_image_viewers_after_external_undo_redo(state)` (`image_viewer_qt.py`) parcourt `image_viewer_refs`, et pour toute visionneuse ouverte sur ce même `state`, appelle `viewer._refresh_after_undo_redo()` (invalide le cache image + `display_image()` + `refresh_undo_redo_state()`). Appelée depuis `panel_widget.py::_undo_action`/`_redo_action`. **Bug corrigé 2026-08-12** : sans cet appel, une visionneuse déjà ouverte continuait d'afficher l'ancienne image après un undo/redo externe, alors que l'unique historique partagé avait bien été modifié — un seul historique existe, ce n'était qu'un défaut de rafraîchissement d'écran, pas une duplication d'historique.
- **`initial_tool`** (`ImageViewer.__init__(..., initial_tool: str | None = None)`, aussi sur `open_image_viewer(..., initial_tool=None)`) : présélectionne un outil de la barre dès l'ouverture, appliqué via `self._toolbar.set_active_tool(initial_tool)` juste après la création de `_toolbar` (le test couvre `"crop"`/`"straighten"`/`"clone"`/`"text"`). Utilisé par les commandes "Recadrer" (`PanelWidget._crop_selected_image` → `initial_tool="crop"`), "Redresser manuellement" (`PanelWidget._straighten_selected_image` → `initial_tool="straighten"`), "Cloner" (`PanelWidget._clone_selected_image` → `initial_tool="clone"`) et "Texte" (`PanelWidget._text_selected_image` → `initial_tool="text"`) — les quatre méthodes de secours sont identiques (première image sélectionnée valide, sinon première image de la mosaïque), reproduisant chacune la logique de l'ancienne fenêtre dédiée disparue. Le double-clic simple sur une vignette et le popup de reprise de marque-page n'utilisent pas ce paramètre (`None` implicite = aucune présélection).
- **Traduction/thème** : `_apply_theme()`/`retranslate()` appelées depuis `ImageViewer._retranslate()` (donc à la construction et à chaque changement de thème/langue, comme toute l'appli) — `_apply_theme()` rappelle aussi `self._overlay_tip.apply_theme()` (**piège corrigé, v1.7.3** : cet appel manquait initialement, donc le tooltip de la barre restait figé au thème clair/sombre actif à l'ouverture de la visionneuse même après un changement de thème pendant qu'elle restait ouverte — même dette trouvée et corrigée dans `adjustments_dialog_qt.py`, `pdf_loading_qt.py`, `resize_dialog_qt.py` ; voir "Piège transversal — `OverlayTooltip` et le thème dynamique" plus bas). Tooltips via `OverlayTooltip.track(widget, html)` (skill `qt-tooltips`), jamais `setToolTip()`. Clés de traduction : `viewer.toolbar_crop_tooltip`/`toolbar_crop_instruction`/`toolbar_straighten_tooltip`/`toolbar_clone_tooltip`/`toolbar_text_tooltip`/`toolbar_undo_tooltip`/`toolbar_redo_tooltip`, toutes propagées aux 45 langues (39 naturelles + tlh/sjn/qya latin + 3 CSUR). Les tooltips crop, straighten, clone et texte sont **enrichis** (titre en gras + instruction d'usage sur une seconde ligne via `<br>`) : `crop_tip = f"<b>{_('viewer.toolbar_crop_tooltip')}</b><br>{_('viewer.toolbar_crop_instruction')}"`, `straighten_tip` combine `toolbar_straighten_tooltip` + `dialogs.straighten_viewer.instruction` (clé récupérée de l'ancienne fenêtre supprimée plutôt que laissée orpheline), `clone_tip` combine `toolbar_clone_tooltip` + `dialogs.clone_zone_viewer.instruction` (même principe, clé de l'ancienne fenêtre clone récupérée), `text_tip` combine `toolbar_text_tooltip` + `dialogs.text_viewer.instruction` (même principe, clé de l'ancienne fenêtre texte récupérée).
- **Gating réel du crop/straighten/clone/text par l'état de la barre** (pas seulement visuel) : `_ViewerCanvas.mousePressEvent`/`mouseMoveEvent` (branche "bouton enfoncé") délèguent au mixin de l'outil actif (`crop_mouse_press`/`straighten_mouse_press`/`clone_mouse_press`/`text_mouse_press`, etc.) — les quatre outils se gatent mutuellement, jamais actifs simultanément sur le même geste de clic-gauche. Un rectangle/trait crop ou straighten existant désélectionné (icône non active) reste affiché mais passe du rouge (`QColor("red")`) au gris (`QColor("#888888")`, voir `CropCanvasMixin.paint_crop_rect`/`StraightenCanvasMixin.paint_straighten_line`) et devient totalement non interactif (curseur de redimensionnement désactivé, double-clic de validation désactivé, bouton "Valider" flottant automatiquement masqué). Les blocs de texte suivent le même principe de gris/figé mais via `_text_set_frozen` plutôt qu'une couleur d'overlay (bordure grise vs bleue, voir skill `add-text-to-image`). Le clonage n'a pas cette variante grise (voir ci-dessous).
- **Persistance entre pages — crop, straighten et texte** (`ImageViewer._crop_by_page`, `_straighten_by_page`, `_text_blocks_by_page`, trois dicts séparés indexés par page, définis dans `ImageViewer.__init__` — `_crop_by_page: dict[int, tuple[float,float,float,float]]` en coordonnées relatives 0-1, `_straighten_by_page: dict[int, tuple[tuple,tuple]]` en coordonnées **image** absolues, `_text_blocks_by_page: dict[int, list[tuple]]` liste de N blocs par page) : un rectangle, un trait ou des blocs de texte tracés sur une page **ne sont plus perdus** en changeant de page. `navigate()` (`image_viewer_qt.py`) appelle `_save_crop_for_current_page()`/`_save_straighten_for_current_page()`/`_save_text_for_current_page()` avant de changer `current_idx` puis les méthodes `_restore_*_for_page(idx)` correspondantes juste après (avec `display_image(keep_crop_rect=True)` pour ne pas effacer la restauration qui vient d'être posée). L'entrée est retirée du dict correspondant quand l'opération est validée ou annulée. **Volatile** : jamais persisté sur disque, perdu au ferme-et-rouvre de la visionneuse ou au crash de l'appli (voir point suivant). **Limitation connue, partagée par les trois outils, pas corrigée** : rien de tout ça n'est redessiné si la page s'affiche en mode double page (`_display_double_page` ne redessine aucun overlay, seul `_display_single_page` le fait). **Le clonage n'a pas cette persistance** — voir ci-dessous.
- **Confirmation de fermeture avec travail non validé** : `ImageViewer._has_unvalidated_work()` (rectangle/trait/blocs de texte de la page courante OU `_crop_by_page`/`_straighten_by_page`/`_text_blocks_by_page` non vides — le clonage n'y contribue jamais, voir ci-dessous) intercepte `closeEvent` (`event.ignore()`) et affiche `ConfirmYNDialog` (`dialogs_qt.py` — non-modal, Oui/Non) avant de laisser fermer réellement. "Oui" repose `self._close_confirmed = True` puis rappelle `self.close()` ; "Non" ou fermeture du dialogue laisse la visionneuse ouverte, rien n'est perdu. Clés : `viewer.unvalidated_work_title` (via `_wt()`, règle CLAUDE.md n°7)/`viewer.unvalidated_work_message`. **Ordre de fermeture avec l'application entière — bug corrigé 2026-08-12** : fermer l'appli pendant qu'une visionneuse a du travail non validé fermait auparavant le fichier (`state.images_data` vidé) AVANT que la visionneuse ait pu vérifier/bloquer, faisant apparaître son dialogue de confirmation sur une BD déjà fermée. `MosaicView.closeEvent` (`MosaicView.py`) vérifie désormais en tout premier `image_viewer_refs` : toute visionneuse ouverte (panel1 ou panel2) avec du travail non validé est ramenée au premier plan et sa propre fermeture déclenchée en premier, bloquant celle de l'appli tant qu'elle n'a pas statué.
- **Activation d'un outil pendant un mode double/continu/webtoon** : contrairement à la décision de principe actée dans `idees.txt` ("l'activation de n'importe quel outil force le mode simple"), en pratique le retour forcé au mode simple ne se déclenche **qu'au moment où un tracé/stroke est effectivement complété** (relâchement de souris avec un rectangle/trait valide, premier coup de tampon pour le clonage, ou placement d'un bloc pour le texte), pas à la simple sélection de l'icône dans la barre — comportement du crop reproduit à l'identique pour straighten, clone et texte par cohérence, écart connu non corrigé.
- **Cohabitation avec `_mode_label`/`_zoom_label`** (labels flottants déjà existants, coins haut-gauche/haut-droite, toujours visibles en permanence) : décision actée de ne PAS y toucher pour ce chantier — la barre s'insère entre les deux sans changer leur comportement. Une éventuelle unification visuelle des 3 éléments est hors périmètre actuel.
- Le calcul d'angle de correction (`line_to_correction`, coordonnées image → angle) est extrait dans un module partagé `modules/qt/straighten_geometry.py` (fonction pure, sans dépendance Qt), importé par `straighten_tool_qt.py`.

### Le clonage : différent des trois autres outils

Contrairement au crop/straighten/text (une opération, validée une fois via un bouton "Valider"), le clonage **peint en continu** : chaque coup de tampon modifie déjà l'image et devient sa propre entrée d'historique au relâchement du clic gauche — pas de bouton "Valider" pour cet outil (`_VALIDATE_KEYS` n'a pas d'entrée `"clone"`), pas de persistance de travail non validé par page, pas de variante grise "conservée mais désélectionnée". Détail complet de la mécanique interne (modes fixe/relatif, calcul de décalage source/destination, image de travail intermédiaire, throttle d'affichage, undo/redo par stroke, points d'entrée UI) dans le skill `clone-zone`, sur le même principe que `page-crop`/`page-straighten`/`add-text-to-image` pour les trois autres outils migrés.

**Prochaine étape prévue** (pas commencée) : migrer le dernier outil restant, ajustements. Avant d'attaquer : lire ce document ET la partie "Design" retenue dans `idees.txt` pour ce chantier, ne pas réinventer les décisions déjà actées (composition de la barre, bouton "Image" pour les 8 modes d'ajustement, etc.) — et créer son propre module dès le départ (ex. `adjustments_tool_qt.py`), jamais dans `image_viewer_qt.py`, conformément à la règle architecturale ci-dessus.

## Piège transversal — `OverlayTooltip` et le thème dynamique (corrigé v1.7.3 sur 4 fenêtres, pas généralisé)

`OverlayTooltip._apply_style()` (`modules/qt/overlay_tooltip_qt.py`) lit `state.dark_mode` et applique un stylesheet **une seule fois**, au moment où elle est appelée — elle n'est PAS un widget qui suit le thème tout seul. Corrigé en v1.7.3 dans `image_viewer_qt.py` (`_ViewerToolbar._apply_theme`), `adjustments_dialog_qt.py`, `pdf_loading_qt.py` (`DpiDialog._retranslate`), `resize_dialog_qt.py` (`ResizeDialog._retranslate`) — un simple `self._overlay_tip.apply_theme()` ajouté dans la méthode de thème/retraduction existante de chaque fenêtre suffit. **Pas vérifié/corrigé au-delà de ces 4 fichiers** : `OverlayTooltip` est instancié dans 8 fichiers au total (`mosaic_canvas.py`, `icon_toolbar_qt.py`, `library_window.py`, `status_bar_qt.py`, `tabs_qt.py` étaient déjà corrects avant cette session) — si un nouveau bug de tooltip figé au mauvais thème est signalé ailleurs, vérifier en premier si l'instance concernée rappelle bien `apply_theme()`/`_apply_style()` depuis sa fonction de thème dynamique.

## Les 8 modes de `AdjustmentViewerDialog` (une seule classe, pas 8 fichiers)

`AdjustmentViewerDialog(parent, selected_entries, settings, mode, on_close_callback=None, on_cancel_callback=None, callbacks=None)` — le paramètre `mode` (`str`) sélectionne le comportement, toujours dans le même fichier `adjustments_viewers_qt.py` :

| `mode` | Réglage |
|---|---|
| `sharpness` | Netteté, réglette -100..+100 |
| `brightness` | Luminosité + contraste, réglettes -100..+100 |
| `compression` | Qualité JPEG, réglette 1..100 |
| `remove_colors` | Intensité de suppression de couleurs, réglette 0..100 |
| `saturation` | Saturation, réglette -100..+100 |
| `unsharp` | Unsharp Mask, 3 réglettes (radius, percent, threshold) |
| `levels` | Point noir / point blanc via pipettes |
| `transparency` | Rendre transparent (flood fill ou global) au clic |

Chercher `if self._mode == '...'`/`elif self._mode == '...'` dans `adjustments_viewers_qt.py` pour trouver le code spécifique à un mode donné — la logique de zoom/pan/affichage (`_ImageScrollWidget`) est en revanche partagée par tous les modes.

**Ce skill ne couvre que le comportement générique du viewer (zoom/pan/plein écran/navigation) commun aux 8 modes.** Pour la formule PIL exacte, les bornes de valeur et les pièges propres à un mode donné, voir la skill `adjust-*` correspondante : `adjust-sharpness` (modes `sharpness`/`unsharp`), `adjust-brightness-contrast` (mode `brightness`), `adjust-compression` (mode `compression`), `adjust-remove-colors` (mode `remove_colors`), `adjust-saturation` (mode `saturation`), `adjust-levels` (mode `levels`, pipettes), `adjust-transparency` (mode `transparency`, flood fill/global). Pour la fenêtre parente qui ouvre ce viewer et récupère ses valeurs au retour, voir `adjustments-panel`.

## Les 4 modes de lecture de la visionneuse principale (`ImageViewer.page_mode`)

Distinct des 8 modes d'ajustement ci-dessus — propre à `image_viewer_qt.py`, aucun rapport avec `AdjustmentViewerDialog`. Attribut `self.page_mode`, une simple chaîne (`"single"` / `"double"` / `"continuous"` / `"webtoon"`), pas d'enum.

| `page_mode` | Comportement |
|---|---|
| `single` | Une page à la fois |
| `double` | Page 1 seule, puis paires 2-3, 4-5, etc. |
| `continuous` | Page 1 seule, puis paires glissantes 2-3, 3-4, 4-5, etc. (chaque page réapparaît dans la paire suivante) |
| `webtoon` | Ajouté 2026-07. Page simple (jamais de paire), pensé pour les images verticales (webcomics). Zoom initial calé sur `min(WEBTOON_MAX_WIDTH_PX=900, viewer_w) / img_w` au lieu du fit largeur+hauteur classique — l'image déborde donc verticalement de la fenêtre par construction. |

- **Cycle** : touche `D` → `toggle_double_page()` fait tourner `single → double → continuous → webtoon → single`, dans cet ordre fixe et circulaire — pas de va-et-vient. Aussi accessible via le menu contextuel (clic droit → l'entrée affiche le mode *suivant* dans le cycle, pas le mode actuel : `context_menu.viewer.reading_mode_double/continuous/webtoon/single`).
- **Label affiché** : `_update_mode_label()` — traductions `viewer.mode_single`/`viewer.mode_double`/`viewer.mode_continuous`/`viewer.mode_webtoon` dans `locales/*.json`. Masqué automatiquement pour un GIF animé.
- **Routage vers l'affichage** : `display_image()` contient un `if self.page_mode == "double": ... elif self.page_mode == "continuous": ... else: ...` qui décide, pour chaque mode, quelles pages envoyer à `_display_single_page()` (une page — webtoon y tombe toujours via le `else`) ou `_display_double_page(left_idx, right_idx, ...)` (deux pages assemblées côte à côte, jamais utilisé par webtoon). La logique de pagination par paire diffère entre `double` (paires fixes 2-3/4-5) et `continuous` (paires glissantes) — voir `_double_page_pair_start()` pour le calcul des débuts de paire en mode `double`.
- **Cas particuliers déjà gérés, à ne pas casser en ajoutant un mode** : une page "multiple" (`is_multiple_page`, ex. une planche triple) s'affiche toujours seule même en mode `double`/`continuous` ; une "image large" (`is_wide_image`) idem en mode `continuous` ; la position 0 (première page) s'affiche toujours seule, jamais en paire.

**Pour ajouter un 5e mode de lecture** : ajouter la valeur à la chaîne de `toggle_double_page()`, un cas dans `_update_mode_label()` (+ nouvelle clé de traduction), et un bloc `elif self.page_mode == "nouveau_mode":` dans `display_image()` qui décide de la pagination — probablement une nouvelle méthode `_double_page_pair_start`-like si la logique de paire diffère des modes existants. Vérifier aussi le menu contextuel (`_show_context_menu`) et l'entrée `help.viewer_content` du mode d'emploi (skill `user-guide`) qui énumèrent explicitement les modes actuels. Pour l'ajout de clés de traduction dans les 3 langues fictives (tlh/sjn/qya) et leurs variantes CSUR, ne pas oublier `PRESERVE_RE` dans `conversion_tools/convert_piqad_csur.py`/`convert_tengwar_csur.py` si le nom du mode est un terme technique/nom propre à préserver tel quel (voir skill `add-translation`).

### Mode `webtoon` : molette = scroll vertical + changement de page en butée

Seul mode où la molette (sans Ctrl) ne navigue pas directement entre pages : `_on_wheel()` route vers `_on_webtoon_wheel()` qui scrolle `self._canvas.pan_offset_y` verticalement dans la page. Une fois en butée (haut ou bas), le **débordement** du delta au-delà de la limite (`overflow`, pas un simple compteur d'événements) s'accumule dans `self._webtoon_bound_scrolls` jusqu'à `WEBTOON_PAGE_TURN_THRESHOLD` (360, ≈3 crans de molette standard), puis déclenche `navigate()`. **Piège déjà corrigé** : compter le nombre d'événements plutôt que la magnitude du delta casse le mécanisme dès qu'un scroll rapide envoie un seul événement avec un delta énorme (plusieurs dizaines de crans agrégés par le driver) — ce gros événement dépassait la butée sans jamais être comptabilisé, forçant l'utilisateur à recommencer l'accumulation à zéro avec de petits crans. D'où la nécessité de calculer un `overflow` (portion du delta qui dépasse la limite) reporté dans l'accumulation dès le même événement, plutôt qu'un test binaire `at_bound`.

Offset vertical calé en haut de page (`offset_y = pan_offset_y`, jamais centré comme les autres modes) dans les 3 chemins d'affichage concernés : `_display_single_page`, `_animate_gif_frame` (GIF vertical). `_display_double_page` n'est jamais emprunté par ce mode. Le pan vertical est remis à zéro à chaque changement de page et à l'entrée dans le mode (sinon le pan de la page précédente reste appliqué à la nouvelle image).

Une fine barre de progression verticale (piste + curseur semi-transparents, non cliquable, collée au bord droit du canvas) est dessinée dans `_ViewerCanvas.paintEvent`, visible uniquement en mode `webtoon` et seulement si `display_height > height()` — volontairement pas une vraie scrollbar Qt (casserait l'esthétique plein-écran et interférerait avec le pan clic-droit).

## Architecture d'affichage : deux familles différentes

**Famille A — la visionneuse annexe restante** (`adjustments_viewers_qt.py` — `clone_zone_viewer_qt.py`, `straighten_viewer_qt.py` et `text_viewer_qt.py` ont été supprimées, leurs outils migrés dans la visionneuse principale) : a un petit widget interne (`_ImageScrollWidget`) dont le `paintEvent` fait :
```python
w = int(self._pixmap.width() * self._zoom)
h = int(self._pixmap.height() * self._zoom)
painter.drawPixmap(x, y, w, h, self._pixmap)
```
Le pixmap est stocké **une seule fois à sa résolution native** (`set_pixmap`) ; c'est Qt (`SmoothPixmapTransform`) qui fait l'étirement à l'affichage, à chaque frame, quel que soit le niveau de zoom. Rapide par construction — jamais de `resize()` PIL répété.

**Famille B — la visionneuse principale** (`image_viewer_qt.py`) : a été alignée sur ce même principe (2026-07, voir `CHANGELOG.md` v1.5.10) après avoir eu un mécanisme différent et plus coûteux (un `Image.resize()` PIL complet à chaque cran de zoom). Le canvas `_ViewerCanvas.paintEvent` fait désormais :
```python
target = QRectF(self.display_offset_x, self.display_offset_y, self.display_width, self.display_height)
painter.drawPixmap(target, pm, QRectF(pm.rect()))
```
avec `pm` stocké à résolution source (page simple, ou image combinée pour le mode double page). **Si un futur bug de lag réapparaît dans une de ces fenêtres, vérifier en premier qu'aucun `.resize()` PIL n'a été réintroduit dans le chemin de zoom** — c'est la régression la plus probable.

## Pan : toujours additionné au centrage, jamais recalculé à part

Dans ces visionneuses, le pan (clic droit + glisser) est un offset stocké séparément (`self._offset` dans les annexes, `pan_offset_x/y` dans la visionneuse principale) et **additionné** au centrage géométrique à chaque redessin :
```python
x = self._offset.x() + (self.width() - w) // 2
```
**Piège déjà rencontré** (visionneuse principale uniquement, avant le fix de 2026-07) : si le calcul d'offset ignore le pan et repart du centrage pur à chaque zoom, l'image se recentre à chaque cran de molette. Vérifier ce pattern avant de toucher au calcul d'offset dans n'importe laquelle de ces fenêtres.

### Piège transversal — overlays interactifs qui se désynchronisent de l'image au pan/zoom/resize

Les 3 outils migrés de la visionneuse principale dessinent chacun un **overlay superposé positionné** en plus de l'image elle-même : le rectangle de recadrage (`CropCanvasMixin`), le trait de référence du redressement manuel (`StraightenCanvasMixin`), le marqueur de source du tampon de clonage (`CloneCanvasMixin`) — tous les trois dans `_ViewerCanvas` via leurs mixins respectifs. Dans tous les cas, l'overlay est interactif (tracé/déplacé à la souris) donc naturellement défini au départ en **coordonnées widget** — mais si ces coordonnées ne sont jamais reconverties après un pan, un zoom, ou un redimensionnement de la fenêtre, l'overlay reste figé à sa position écran pendant que l'image glisse/zoome/se recentre dessous, donnant l'impression qu'il "ne suit pas" l'image.

**Correctif systématique (2026-08, v1.7.2)** sur les 3 overlays : stocker la position de l'overlay en coordonnées **image** (stables, indépendantes de l'affichage) en plus des coordonnées widget dérivées pour le dessin, et **reconvertir explicitement à chaque pan, zoom, et redimensionnement** — pas seulement au tracé initial. La reconversion se fait systématiquement en tête du `paintEvent` du canvas (`paint_crop_rect`/`paint_straighten_line`/`paint_clone_marker`, appelées depuis `_ViewerCanvas.paintEvent`), pas dupliquée dans chaque handler séparément — Qt rappelle `paintEvent` automatiquement après pan/zoom/resize.

**Si un nouvel overlay interactif est ajouté à un futur outil de la barre**, vérifier explicitement les trois cas avant de considérer la fonctionnalité terminée :
1. **Pan** (clic droit maintenu) — l'overlay doit se redessiner à jour à chaque `mouseMoveEvent` de pan, pas seulement au relâchement.
2. **Zoom** (molette, `Ctrl+Plus`/`Ctrl+Minus`, `Ctrl+0`, `Ctrl+1`) — reconversion après tout changement de `_zoom`/`zoom_level`.
3. **Redimensionnement de la fenêtre** — cas le plus facile à oublier (pas de `resizeEvent` par défaut sur `QWidget`) ; le plus sûr est de faire la reconversion en tête de `paintEvent` lui-même (Qt le rappelle automatiquement dans les trois cas ci-dessus), comme fait `_ViewerCanvas.paintEvent` pour les 3 overlays existants, plutôt que de dupliquer l'appel dans chaque handler séparément.

## Raccourcis clavier zoom — communs à ces visionneuses, à garder synchronisés

Chaque fenêtre câble ces raccourcis indépendamment (pas de table de raccourcis partagée) :

- `Ctrl+Plus` / `Ctrl+Minus` : `adjust_zoom(+0.1)` / `adjust_zoom(-0.1)` dans la visionneuse principale (pas de bouton +/- à l'écran, molette Ctrl+molette aussi disponible) ; `adjust_zoom(+0.15)` / `adjust_zoom(-0.15)` dans la visionneuse annexe restante (ajustements — même pas que ses boutons +/- à l'écran — toujours reprendre cette valeur, ne pas en improviser une autre).
- `Ctrl+0` : ajuste le zoom à la fenêtre (`fit_zoom_to_window()` / `fit_to_window()`).
- `Ctrl+1` : zoom à 100% = taille réelle des pixels de l'image (`reset_zoom()`).
- Molette seule : navigation entre pages (visionneuse principale uniquement) ou scroll vertical (les annexes).

**Piège vérifié** : dans certaines visionneuses annexes, les boutons +/- à l'écran passent par une méthode wrapper du dialog (`self._adjust_zoom(delta)` dans `adjustments_viewers_qt.py`) qui met aussi à jour le label de pourcentage — un raccourci clavier branché directement sur `self._img_widget.adjust_zoom()` sans passer par ce wrapper laisserait le label figé. Dans d'autres (clone/text), le widget expose `on_zoom_changed` (callback) déjà câblé sur la mise à jour du label, donc brancher directement sur le widget suffit. **Toujours vérifier lequel des deux mécanismes est utilisé dans le fichier concerné avant d'ajouter un raccourci**, plutôt que de copier le pattern d'un autre fichier au hasard.

## Sémantique du zoom : 100% = taille réelle des pixels

Dans ces visionneuses, `zoom_level = 1.0` signifie 1 pixel image = 1 pixel écran — jamais un multiple de la taille "ajustée à la fenêtre". Le fit-to-window est un calcul ponctuel (au premier affichage, ou sur demande via `fit_to_window()`/`fit_zoom_to_window()`), pas la référence du pourcentage affiché. Ne jamais réintroduire un calcul du type `final_w = img_w * ratio_fit * zoom_level` (upscale caché au-delà de la résolution native, source de lag et de confusion sur ce que "100%" veut dire).

## Fit-to-window qui suit le redimensionnement de la fenêtre (visionneuse principale uniquement, v1.7.3)

Dans `image_viewer_qt.py`, tant que l'utilisateur n'a fait aucun zoom manuel (`self._manual_zoom` reste `False`), le fit-to-window reste valable quelle que soit la taille ultérieure de la fenêtre — agrandir, maximiser, ou passer en plein écran (F11) recalcule le zoom pour continuer à remplir la fenêtre, au lieu de garder le zoom figé calculé pour la taille d'origine.

- **`_manual_zoom`** : `True` dès que l'utilisateur zoome explicitement (molette, `Ctrl+Plus`/`Ctrl+Minus`, `Ctrl+1`) — un resize après ça ne touche plus au zoom, comportement figé volontaire. **`Ctrl+0` (`fit_zoom_to_window()`) fait exception** : il pose `_manual_zoom = False` (pas `True`) puisqu'il *choisit* explicitement le mode auto-fit — un resize après un Ctrl+0 continue donc à re-fitter.
- **`_on_resize_debounced()`** : callback du timer de debounce resize (150 ms, `self._resize_timer`) — remplace l'ancien lambda direct. Si `_manual_zoom` est `False`, force `self._zoom_initialized = False` avant `display_image(keep_crop_rect=True)` pour déclencher le recalcul de fit déjà fait au premier affichage (`_display_single_page`/`_display_double_page`, `if not self._zoom_initialized: ...`).
- **`toggle_fullscreen()` (F11/double-clic)** applique la même logique de recalcul immédiatement (pas seulement via le debounce resize déclenché en cascade par `showFullScreen()`/`showNormal()`), pour éviter un bref affichage à l'ancien zoom avant que le debounce ne rattrape 150 ms plus tard.
- **Piège à ne pas réintroduire** : ne pas remettre `_manual_zoom = True` dans `fit_zoom_to_window()` — ça casserait le re-fit automatique après un Ctrl+0 suivi d'un agrandissement de fenêtre, en réintroduisant exactement le bug corrigé ici.
- **Non répliqué à la visionneuse annexe restante** (ajustements) — elle n'a pas ce fix (pas demandé, et son usage — zoom/pan sur un aperçu d'édition plutôt que lecture — rend le besoin moins net). Voir "Avant de modifier une de ces fenêtres" si une réplication est un jour demandée.

## Piège performance — `_make_checkerboard_pil` (fond damier transparence)

`modules/qt/entries.py::_make_checkerboard_pil(w, h, tile)` génère le fond en damier affiché derrière toute image avec canal alpha (`_compose_on_checkerboard`, appelé dans `_display_single_page` de la visionneuse principale, dans les miniatures de la mosaïque, et dans l'aperçu de la fenêtre d'ajustements). **Pas spécifique à une visionneuse ni à un mode** — touche les 3 points d'appel dès qu'une image transparente de grande taille est affichée.

Historique (2026-07) : implémentée à l'origine par une double boucle Python pixel par pixel (`for y: for x: pixels[x,y] = ...`), invisible sur une page de comics classique ou une miniature (peu de pixels), mais provoquant un gel UI de ~3,4 secondes sur une page verticale de webtoon (940×11075 ≈ 10,4M pixels) — découvert via le mode `webtoon` (seul cas ayant poussé la taille d'image assez haut pour rendre le coût perceptible), mais le correctif bénéficie à tous les appelants. Corrigée par un tuilage par blocs (motif de base 2×2 cases construit une fois, puis répété via `paste()`), ramenant le cas à ~240ms (gain ≈14×). **Si un lag réapparaît sur l'affichage d'une image transparente de grande taille (quelle que soit la fenêtre), vérifier en premier qu'aucune boucle pixel par pixel n'a été réintroduite dans `_make_checkerboard_pil` ou une fonction similaire.**

## Avant de modifier une de ces fenêtres

1. Identifier la bonne fenêtre (et le bon `mode` si c'est `AdjustmentViewerDialog`) — ne pas supposer qu'elles partagent du code, grep le nom de la classe/fichier pour confirmer.
2. Vérifier si le changement doit être répliqué dans les autres visionneuses ou seulement celle-ci — demander à l'utilisateur si ambigu (comme pour le zoom, propagé sur demande explicite après correction dans la principale).
3. Respecter les règles UI générales du projet (`CLAUDE.md`) : non-modale, thème dynamique, retraduction à la volée, `_wt()` pour le titre de fenêtre, tooltips via `OverlayTooltip`.

- `create-ico` — le cas particulier de sauvegarde `.ico` dans `AdjustmentViewerDialog` (`adjustments_viewers_qt.py:1401`, `fmt = 'ICO'` forcé pour ne pas perdre le format multi-résolution après un ajustement de transparence).

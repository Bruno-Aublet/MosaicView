# Bibliothèque — MosaicView

La Bibliothèque est un **catalogue** indépendant de la mosaïque : elle indexe en base SQLite tous les comics/ebooks/PDF/vidéos/etc. d'un ou plusieurs répertoires sur disque, permet de les rechercher par métadonnées ComicInfo, et ouvre le fichier choisi dans un panneau (`panel1`/`panel2`, voir skill `panels`). Elle ne touche jamais aux `images_data` d'un panneau réel tant que l'utilisateur n'a pas explicitement ouvert un fichier.

## Fichiers clés

- **`modules/qt/library_db.py`** — moteur SQLite pur (aucun Qt). Classe `LibraryDB` : création/ouverture de la base, scan incrémental du disque, recherche par critères, lecture/écriture `is_read`.
- **`modules/qt/library_window.py`** (~3965 lignes) — la fenêtre `LibraryWindow(QWidget)` : toute l'UI (toolbar, panneau de critères, prévisualisation, tableau de résultats), plus les workers Qt (`_ScanWorker`, `_PreviewWorker`).
- **`modules/qt/library_dialogs.py`** — dialogues annexes (ex. `NewDbDialog` pour créer une nouvelle base, accepte un paramètre `preset_dir` utilisé par le traitement batch de création de bibliothèque — voir skill `batch-library-create`).
- **`modules/qt/virtual_library_panel.py`** — `VirtualLibraryPanel`, le panneau logique (sans UI) que certaines opérations utilisent pour réutiliser le code panneau existant (ex. lecture ComicInfo) sans instancier un vrai `PanelWidget`. Voir skill `panels` section "La bibliothèque comme panneau virtuel".
- **`modules/qt/recent_dbs.py`** — liste des `.mvdb` récemment ouverts (persistée), utilisée par le sous-menu "Bases de données récentes" — voir skill `recent-items` pour ce module et son pendant `recent_files.py`.
- **`modules/qt/menubar_qt.py`** (`_populate_library_menu`) — construit le menu "Bibliothèque" (libellé « Base de données » en français, aussi monté dans le menu contextuel du canvas) : ouverture de la fenêtre, liste des DB récentes, puis les commandes de gestion de la base ajoutées au même niveau par `LibraryWindow.build_db_menu` — voir skill `menu-bar` pour la structure générale de la barre de menus.
- **`modules/qt/panel_widget.py`** (`_prewarm_library`, `_open_library`, `_open_library_db`) — point d'entrée depuis un panneau réel.

## Le fichier `.mvdb`

Une base bibliothèque est un fichier SQLite unique avec l'extension `.mvdb`. Il n'y a pas de format propriétaire : `sqlite3` suffit pour l'inspecter directement. `LibraryDB.rename()` est la seule opération qui renomme ce fichier ; `_backup()` copie systématiquement l'ancien contenu vers `<db>.mvdb.old` avant toute écriture destructive (scan, set_read, set_master_dir, add_directory, rename).

### Schéma (3 tables)

- **`comics`** — une ligne par fichier indexé. Colonnes fixes (`relative_path` UNIQUE, `filename`, `file_extension`, `file_size`, `file_modified_at`, `indexed_at`, `has_comicinfo`, `can_have_comicinfo`, `is_read`, `page_count`) + tous les champs ComicInfo (`_COMICINFO_FIELDS` : `series`, `writer`, `summary`, `characters`, etc.) stockés en TEXT même pour des valeurs numériques (`number`, `volume`, `year`...).
- **`directories`** — les répertoires indexés. `is_master=1` marque le répertoire maître (racine utilisée pour calculer `relative_path` de tous les fichiers, y compris ceux des répertoires additionnels `is_master=0`). Une seule ligne peut avoir `is_master=1`.
- **`meta`** — clé/valeur libre, utilisée aujourd'hui uniquement pour `columns_config` (liste JSON des colonnes visibles du tableau, par base).

### Extensions indexées

Le fichier définit des ensembles disjoints en tête (`_ARCHIVE_EXTS`, `_EBOOK_EXTS`, `_VIDEO_EXTS`, `_AUDIO_EXTS`, `_OTHER_SCAN_EXTS`) qui forment `_ALL_EXTS` (tout ce que le scan ramasse) et `_MEDIA_TYPE_*` (catégories du champ virtuel `media_type`, calculé à la volée depuis `file_extension`, jamais stocké). **Piège** : ajouter une extension à indexer nécessite de la mettre dans le bon set ET dans exactement une catégorie `_MEDIA_TYPE_*` (ou la laisser tomber dans `mt_other` par omission volontaire) — ne jamais dupliquer une extension dans deux catégories, elles doivent rester disjointes (commentaire explicite à côté de ces ensembles, en tête de `library_db.py`).

## Scan incrémental (`LibraryDB.scan`)

`scan(progress_callback, stop_event)` :
1. Parcourt tous les répertoires enregistrés (`utils.walk_without_links` : ni liens symboliques ni jonctions NTFS, qui feraient indexer des fichiers situés ailleurs ou plusieurs fois — skill `batch-processing`), construit `disk_files` (`relative_path → chemin absolu`) en ne gardant que les extensions de `_ALL_EXTS`.
2. Compare à `db_files` (ce qui est déjà en base) : un fichier absent de la DB → **nouveau** (`_index_file`) ; présent mais `file_modified_at` plus récent sur disque → **mis à jour** ; en DB mais absent du disque → **supprimé** (`DELETE`).
3. `_index_file()` : si l'extension est une archive (`_can_have_comicinfo`), tente de lire le `ComicInfo.xml` de l'archive (`_has_comicinfo_in_archive`, `_read_comicinfo_from_archive`) et parse via `modules.qt.comic_info.parse_comic_info_xml`. Compte aussi les pages réelles (`_count_pages`) plutôt que de faire confiance au `PageCount` du XML (plus fiable).

**Quel ComicInfo.xml est catalogué** : `_comicinfo_lookup(chemin, read)`, commune aux deux fonctions, retient le même que l'ouverture du comic (skill `comicinfo-metadata-editor`) : le **premier** fichier nommé exactement `ComicInfo.xml` à la racine, ou à défaut celui du dossier qui contient toutes les pages (`comic_info.comic_info_member`, règle de `comic_info_member_index`), nom TAR passé par `archive_names.tar_entry_name` (un `./ComicInfo.xml` compte), dossiers et liens exclus. Formats : `.cbz`/`.zip` par `archive_names.open_zip`, `.cbt` par `tarfile`, `.cbr` par `rarfile` si installé. Le membre se lit par son objet d'archive (`ZipInfo`, `RarInfo`, `TarInfo`), jamais par son nom : `read(nom)` rend le **dernier** homonyme, la Bibliothèque montrerait alors d'autres métadonnées que le comic ouvert. Avant la lecture, sa taille annoncée est contrôlée par `_check_comicinfo_size` contre `MAX_MEMBER_SIZE` (`archive_names.py`, la limite de tous les lecteurs, skill `archive-image-loading`) : au-delà, `ValueError`, et `_read_comicinfo_from_archive` catalogue le comic sans métadonnées (`_has_comicinfo_in_archive`, qui ne lit rien, le repère toujours comme ayant un ComicInfo.xml) — une archive piégée avec un ComicInfo.xml énorme épuiserait sinon la mémoire pendant le scan. **Piège** : `library_db` est testé sans Qt et ne peut pas importer les lecteurs communs d'`archive_loader.py` (qui importe PySide6) : il prend la constante dans `archive_names`, jamais dans `archive_loader`. Testé par `tests/test_library_db.py` (`test_comicinfo_beyond_the_size_limit_is_not_read`). `_count_pages` ne compte que des fichiers (`is_dir()` exclus en ZIP/RAR, `isfile()` en TAR).
4. **`is_read` est préservé** lors d'une mise à jour (relu depuis la ligne existante avant l'`UPDATE`) — un rescan ne remet jamais une lecture à zéro.

**PDF lus dans un process séparé** (`pdf_probe.PdfProbe`, skill `pdf-loading`, « Accès courts dans un process séparé ») : un PDF qui fait planter MuPDF ne ferme pas l'application, il reste simplement sans nombre de pages ni couverture. Nombre de pages : `_count_pages(chemin, pdf_probe)` ne lit un PDF que par le `PdfProbe` reçu (sans lui : `None`) ; `_index_file` lui passe celui de la `LibraryDB` (`self._pdf_probe`, créé au premier PDF, arrêté par `close()`). Couverture : `_PreviewWorker` reçoit le `PdfProbe` de la fenêtre (`self._preview_probe`, créé par `_start_preview_worker` au premier PDF, arrêté dans `closeEvent`). Jamais PyMuPDF dans `library_db.py` ni `library_window.py` (garde-fou `tests/test_check_pymupdf_separate_process.py`).

**Écritures du scan validées au fil de l'eau** : `LibraryDB.scan` valide sa transaction au plus toutes les `_SCAN_COMMIT_INTERVAL` secondes (0,2 s, `_commit_if_due` après chaque fichier indexé ou retiré), et une dernière fois à la fin. **Piège** : validées une seule fois à la fin, elles tiendraient le verrou d'écriture SQLite pendant tout le scan ; la fenêtre, qui a sa propre connexion, attendrait alors 5 s (thread UI figé) à chaque écriture (`set_read`, `reindex_files` après un enregistrement, ComicInfo.xml) avant d'échouer (« database is locked »). Testé par `tests/test_library_db.py` (`test_window_can_write_while_a_scan_is_running`).

**Aperçu** : `_PreviewWorker` émet une `QImage` (`.copy()`, nulle si échec), convertie en `QPixmap` par `_on_preview_ready` sur le thread de l'interface (jamais de `QPixmap` dans un worker). `_cancel_preview` n'attend pas le worker (`wait()` figeait l'interface à chaque changement de sélection sur un gros CBR ou PDF) : il pose `cancelled`, débranche `ready` et le confie à `park_qthread` (`utils.py`), qui le libère à sa fin. Si ce worker lit encore la couverture d'un PDF, son `PdfProbe` est arrêté (`shutdown()`, la lecture rend aussitôt `None`) et retiré de la fenêtre : l'aperçu suivant en crée un neuf au lieu d'attendre la fin d'une lecture devenue inutile. `_on_preview_ready` ignore le résultat d'un `_PreviewWorker` qui n'est plus `self._preview_worker` (`self.sender()`) — émis juste avant que `_cancel_preview` l'arrête, il serait livré quand même et afficherait la couverture du comic précédemment sélectionné. `_clear_preview()` vide tout le panneau d'aperçu (couverture, chemin et taille, métadonnées) et arrête l'aperçu en cours ; elle est appelée sans sélection unique (`_on_selection_changed`) et à chaque changement de base : `_action_close_db`, `_action_open_db` (qui remplace la base ouverte sans passer par `_action_close_db`) et `_on_new_db_accepted`. **Piège** : un chemin qui remplace la base sans la vider laisse l'aperçu d'un comic de l'ancienne base à côté du tableau de la nouvelle ; tout nouveau chemin de changement de base doit appeler `_clear_preview`. Testé par `tests/test_stale_async_results.py` (vraies méthodes `_start_preview_worker`, `_cancel_preview`, `_on_preview_ready`, `_clear_preview` : couverture d'une sélection précédente jamais affichée, ni à la place de « aperçu indisponible », ni après un changement de base).

**Métadonnées sous l'aperçu** (`_populate_meta`) : une ligne par champ non vide (libellé en gras à largeur fixe + valeur en `QLabel` à retour à la ligne, `Qt.PlainText` avant `setText`), séparées par une `QFrame`, dans `self._meta_layout`, contenu de `self._meta_scroll` (`_FitScrollArea`, `widgetResizable`). Le contenu étant étiré à toute la hauteur visible, la liste se termine par un ressort (`addStretch(1)`), et les valeurs gardent une politique verticale `Preferred` (leur hauteur vient de `heightForWidth`). **Piège** : une valeur en `MinimumExpanding` ou sans ressort final fait répartir la place libre entre les lignes — l'espacement varie alors d'un comic à l'autre selon son nombre de champs.

**Ce qui compte comme une page** : le nombre de pages (`library_db._count_pages`) et la couverture de l'aperçu (`library_window.py`) filtrent les fichiers d'une archive sur `IMAGE_EXTS`, la liste unique des extensions d'image (`archive_names.py`, skill `archive-image-loading`), comme la mosaïque : une page `.jfif`, `.pjpeg`, `.pjp` ou `.ico` compte, et peut servir de couverture. Jamais de liste locale : une copie plus courte faisait afficher à la Bibliothèque moins de pages que la mosaïque. Testé par `tests/test_library_db.py` (`test_page_count_uses_the_same_image_list_as_the_mosaic`).

**Noms des fichiers d'un CBZ ou d'un EPUB** : la couverture de l'aperçu (CBZ et EPUB, dont les chemins de l'OPF sont en UTF-8), la réécriture de ComicInfo.xml (`_rewrite_comicinfo_in_cbz`) et la liste des pages du panneau virtuel (`VirtualLibraryPanel`) ouvrent l'archive par `archive_names.open_zip`, comme l'ouverture d'un comic : un nom écrit sans le drapeau UTF-8 y est lu dans son vrai codage, et réécrit sous ce nom (skill `archive-image-loading`). **Taille des membres lus** : la couverture d'un EPUB (`container.xml` puis OPF, `_PreviewWorker.run`) et chaque membre recopié par `_rewrite_comicinfo_in_cbz` passent par `archive_loader._check_member_size` avant lecture (`MAX_MEMBER_SIZE`, limite de tous les lecteurs) : un membre piégé se décompressait sinon en entier en mémoire. Refusé, l'aperçu reste vide, ou la réécriture échoue avec son message et l'original reste intact.

Côté UI, `_ScanWorker(QThread)` dans `library_window.py` fait tourner `scan()` en arrière-plan et remonte des événements bruts non traduits `(kind, filename, pct)` par signal `progress` — la traduction se fait côté thread Qt principal dans `_on_scan_progress` pour pouvoir être rejouée si la langue change pendant le scan (voir `_disconnect_scan_lang_handler`).

**Arrêt du scan quand la base change** : `LibraryWindow._stop_scan(wait=False)` est appelé avant toute fermeture (`_action_close_db`), ouverture d'une autre base (`_action_open_db`), création (`_on_new_db_accepted`) ou suppression (`_on_delete_accepted`, avec `wait=True`). Il pose le `stop_event` du scan (`_ScanWorker.stop()`, testé par `LibraryDB.scan` entre deux fichiers), débranche les signaux du worker, masque l'overlay, puis le confie à `park_qthread` (`utils.py`) jusqu'à la fin réelle de son thread — `_ScanWorker` déclare son propre `finished = Signal(dict)`, qui masque `QThread.finished` natif. **Piège** : sans cet arrêt, `_on_scan_finished` s'exécute à la fin sur la base ouverte **à ce moment-là** — erreur si elle a été fermée, ou lignes de la nouvelle base retirées du tableau, puisque les identifiants (`id` autoincrémenté) d'une base à l'autre se recoupent. Pour la suppression, `wait=True` attend en plus la fin du thread : le scan ouvre sa propre connexion SQLite au `.mvdb` (`LibraryDB.open` dans `_ScanWorker.run`), qui doit être fermée avant de déplacer le fichier. À la fermeture de l'application, `stop_running_qthreads` (`utils.py`) pose ce même `_stop`.

**Création d'une base pendant le chargement d'une autre** : `NewDbDialog` est non modale ; `_on_new_db_accepted` commence par arrêter un chargement de la liste en cours (`_is_loading()` → `_cancel_db_load()`, qui lève `_load_cancelled` pour la boucle `_load_batch`). **Piège** : sans cela, la boucle par lots continuait sur la base fermée (erreur SQLite dans un `QTimer`), `_load_worker` restait vrai, la fenêtre restait « en chargement » et `_action_scan` refusait de scanner la nouvelle base.

**Bases récentes** : `add_to_recent_dbs(filepath)` (`recent_dbs.py`, skill `recent-items`) est appelée à l'ouverture (`_action_open_db`) **et** à la création (`_on_new_db_accepted`, juste après `LibraryDB.create`). **Piège** : sans l'appel de la création, une base qui vient d'être créée n'apparaît pas dans les récentes et ne se retrouve qu'en allant chercher son fichier `.mvdb`. Tout nouveau chemin qui crée ou ouvre une base l'appelle aussi.

**Bouton d'export** (`_btn_export`) : visible seulement si le tableau affiché contient des résultats. Sa visibilité est recalculée partout où le tableau change : `_populate_table`, `_populate_filter_table`, fin du chargement par lots (`_load_batch`), retour au tableau principal après un filtre, et fin du scan (`_on_scan_finished`, après `_set_result_count`). **Piège** : le tableau d'une base neuve est vide quand le bouton est masqué ; si la fin du scan ne le réaffiche pas, l'export reste impossible jusqu'à la réouverture de la base. Tout nouveau chemin qui modifie le tableau recalcule cette visibilité.

**Export Excel** (`_action_export`, `openpyxl`) : lignes affichées (`self._rows`, résultat du filtre s'il y en a un), toutes les colonnes, cachées comprises (masquées dans le classeur). Chaque ligne de données passe par `_excel_text_cells(ws[ligne])` (fonction de module), qui donne le type texte (`data_type = 's'`) à toute cellule dont la valeur est une chaîne. **Piège** : `openpyxl` fait d'une chaîne qui commence par `=` une formule, que le tableur calcule à l'ouverture ; les valeurs viennent du ComicInfo.xml de BD téléchargées (`=HYPERLINK(…)`, `=WEBSERVICE(…)` enverraient le contenu du classeur, chemins compris, vers un site). Le texte est gardé exact, sans apostrophe ajoutée ; les nombres (taille) restent numériques. Testé par `tests/test_library_excel_export.py` (classeur réellement écrit puis relu).

**Confirmations liées à la base ouverte** : « Supprimer la base » (`_action_delete_db` → `ConfirmDeleteDialog`, suite `_on_delete_accepted`) et « Renommer la base » (`_action_rename_db` → `RenameDbDialog`, suite `_on_rename_accepted`) sont non modales. Chacune capture la base visée (`db = self._db`) et s'inscrit dans `self._db_dialogs` par `_track_db_dialog`, qui l'en retire à sa fermeture (`finished`) — les trois fenêtres de `library_dialogs.py` sont en `WA_DeleteOnClose`, détruites à leur fermeture : la liste garderait sinon, la Bibliothèque restant ouverte toute la session, les fenêtres fermées et la base qu'elles visent ; `_close_db_dialogs()` les ferme (fermer vaut Annuler) aux quatre endroits où la base change, juste avant `_stop_scan` : `_on_new_db_accepted`, `_action_open_db`, `_action_close_db`, `_on_delete_accepted`. En filet, la suite ne s'applique que si `_same_db(self._db, db)` (même objet, ou même fichier `.mvdb` rouvert, comparé par `is_same_path`) — testé par `tests/test_library_deferred_db_actions.py`, `_same_db` seule et les vraies suites `_on_delete_accepted`/`_on_rename_accepted` sur de vraies bases (base B ouverte avant la réponse pour A : rien de supprimé ni de renommé). **Piège** : relire `self._db` à la validation supprimait la base ouverte **après** la question, pas celle annoncée ; et un simple refus silencieux laissait l'utilisateur croire la base supprimée. Toute nouvelle action différée sur la base suit ce modèle.

`reindex_files(abs_paths)` réindexe une liste ciblée de fichiers sans scan complet — utilisé après modification de métadonnées (ex. édition ComicInfo, conversion vers CBZ) pour éviter un rescan intégral du répertoire maître. Un chemin hors des répertoires de la base (`_is_in_library_dirs` : maître et additionnels, ceux que parcourt `scan()`, extension de `_ALL_EXTS`) est ignoré : un fichier enregistré ailleurs n'y est jamais ajouté. Testé par `tests/test_library_reindex.py`.

**Écritures dans un fichier, hors du thread de l'interface** : la réécriture du ComicInfo.xml, l'écriture du CBZ d'une conversion et sa relecture avant suppression passent par `LibraryWindow._run_file_task(task, on_finished, stop)` : `task()` s'exécute dans un `_FileTaskWorker` (QThread, signal `done(résultat, exception)`, `_cancelled` = l'Event `stop`, testé par `_stop_if_asked`, qui lève `_FileTaskStopped`, `expected_error = True`), puis `on_finished(résultat, exception)` sur le thread de l'interface. Une seule écriture à la fois (`_file_worker`), les suivantes attendent dans `_file_tasks`, et la suivante démarre même si la suite de la précédente échoue (`finally` de `_on_file_task_done`). La tâche ne touche qu'aux fichiers : base, tableau et fenêtres se mettent à jour dans `on_finished`. La relecture avant suppression (`reread_then_delete_source`) ne teste pas `stop` : à la fermeture de l'application, elle fait partie des workers non interruptibles qui mènent à la fin forcée, avant que l'original n'ait été touché tant qu'elle n'a pas fini.

**Opération en cours : texte rouge et commandes grisées** : `_file_task_running()` est vrai pendant une écriture (`_file_worker`) et pendant toute une conversion (`_convert_worker` : le `LoadWorker` pendant la lecture, puis `True` jusqu'à la fin de l'écriture, questions comprises, `_end_conversion` le remet à `None`). `_can_fetch_metadata()` (Récupérer, Vérifier, Convertir) et `_can_edit_comicinfo()` (en plus : aucun éditeur ouvert, comic avec un ComicInfo.xml) décident du grisage du menu contextuel et des boutons (`_update_file_commands`, rappelée à chaque changement d'état). Le texte rouge a un seul point d'affichage, `_refresh_file_text()`, d'après l'état courant : « Enregistrement en cours… » (`library.export_saving`) pendant une écriture, sinon « conversion en cours… » et le pourcentage (`labels.converting`, `_convert_percent`, `None` hors lecture, et pendant la question d'extension où la lecture attend) ; rappelé par `_retranslate` pour suivre la langue (skill `canvas-overlay-progress`). **Piège** : la lecture de l'archive est souvent l'étape la plus longue ; sans texte ni grisage pendant elle, la commande semble ne rien faire et un second clic part d'un état périmé. Tout nouvel état ou toute nouvelle commande qui écrit dans un fichier passe par ces fonctions. Les actions gardent leur test `_file_task_running()` : un menu déjà ouvert a pu être construit avant le début de l'opération. Une exception imprévue après la lecture termine quand même la conversion (`_on_load_finished_guarded`) : les commandes resteraient grisées jusqu'à la fermeture.

**Un seul éditeur de ComicInfo.xml** : `_comicinfo_editor` garde l'éditeur ouvert (`_comicinfo_editor_open`, avec `shiboken6.isValid`), remis à `None` par son signal `finished` (`_on_comicinfo_editor_closed`) ; la commande est grisée pendant ce temps. Deux éditeurs sur un même comic partiraient de la même version, et le dernier enregistré effacerait l'autre sans rien dire. En filet, `_bring_comicinfo_editor_to_front` ramène l'éditeur ouvert (menu construit avant son ouverture, éditeur demandé à la fin d'une conversion).

**Aperçu après l'édition du ComicInfo.xml** : la fin de l'écriture (`_after_edit_written` dans `_open_comicinfo_editor`) réindexe le fichier, met à jour `_main_rows`, `_rows` quand c'est une autre liste (liste filtrée, ou copie de `_main_rows` faite après une suppression) et les cellules des tableaux, puis rappelle `_on_selection_changed` si le comic édité est encore le seul sélectionné. **Piège** : l'aperçu (`_populate_meta`, `_update_preview_info`) lit sa ligne dans `_rows` et n'est relu qu'au changement de sélection — sans ce rappel, il montre les anciennes métadonnées ; sans la mise à jour de `_rows` hors filtre, même une nouvelle sélection les montre.

**Callbacks différés et changement de base** : une action dont la fin arrive plus tard (conversion `_convert_file_to_cbz` → `_after_choice`, éditeur ComicInfo `_after_edit_written`, vérification ComicVine `_write_comicinfo_and_reindex` → `_reindex_after_comicinfo_write`, métadonnées en lot `_on_batch_complete`, enregistrement depuis un panneau `PanelWidget._on_file_saved`) capture `db = self._db` au lancement et ne réindexe ni ne touche au tableau que si `db is self._db` à l'arrivée. Le fichier sur disque est écrit dans tous les cas. **Piège** : sans cette garde, la base a pu être fermée (`_conn` à `None` → exception) ou remplacée par une autre, dont le tableau recevrait des lignes d'une base étrangère (identifiants autoincrémentés qui se recoupent).

**Écritures dans les fichiers de l'utilisateur, testées** par `tests/test_library_file_writes.py` (méthodes extraites par `tests/ast_loader.load_methods` ; `LoadWorker`, fenêtres et base remplacés) : `_rewrite_comicinfo_in_cbz` (seul le ComicInfo.xml de la BD remplacé — racine, ou dossier des pages, à sa place : `test_comicinfo_of_the_pages_folder_is_replaced_in_place` —, annexes `ComicInfo_0002.xml` et ComicInfo.xml d'un autre dossier, pages homonymes et commentaire d'archive gardés ; second ComicInfo.xml de la racine gardé en annexe, `test_second_comicinfo_of_the_root_is_kept_as_an_annex` ; ancien ComicInfo.xml abîmé gardé sous un nom libre, `test_damaged_comicinfo_is_kept_next_to_the_new_one` ; original intact si `check_written_cbz_structure` échoue, si un lot traite le fichier, si l'écriture est arrêtée ou si un membre dépasse la limite de taille — `test_member_too_large_keeps_the_original` : la fixture `dialogs` place dans son faux `archive_loader` la vraie `_check_member_size`, extraite par AST, dont le test abaisse la limite) et `_convert_file_to_cbz` (toutes les pages écrites ; nom déjà pris remplacé par le suivant de libre ; question avant d'écrire une page altérée ; rien d'écrit si un fichier de l'archive est illisible ou si une page n'a pas de données ; extension corrigée suivie par la base ; original supprimé seulement sur « Oui » et après relecture, gardé si elle échoue ou si le CBZ a été réécrit avant la réponse ; base remplacée entre-temps non touchée ; opération en cours de la lecture à la fin de l'écriture). Le même fichier teste `_run_file_task`, `_FileTaskWorker`, `_refresh_file_text`, le grisage des commandes, `conversion_ext_texts` et le tableau trié de `_refresh_row_after_convert`. Dans la plupart de ces tests, l'écriture s'exécute aussitôt (`Library._run_file_task`). La Corbeille y est remplacée par `utils.send_to_trash` du test (`converted_cbz` la lit à l'appel), jamais la vraie.

## Recherche par critères

### Modèle de critère

Une recherche est une liste de dicts `{field, op, value, link}` :
- `field` — nom de colonne, whitelist stricte `LibraryDB._SEARCHABLE` **plus** deux champs virtuels non stockés : `media_type` (catégorie calculée depuis `file_extension`, clauses dans `_MEDIA_TYPE_CLAUSES`) et `comicvine_format` (ancien/nouveau format d'URL ComicVine, clauses dans `_COMICVINE_FORMAT_CLAUSES`, même logique de reconnaissance de domaine que `comicvine_url_dialog_qt.py::_parse_comicvine_url`).
- `op` — clé de `_OP_MAP` : `contains`/`not_contains`/`is`/`empty`/`not_empty`/`eq`/`neq`/`gt`/`lt`/`gte`/`lte`/`between`/`true`/`false`/`before`/`after`.
- `value` — valeur(s) ; pour `between`, un tuple `(v1, v2)`.
- `link` — `'and'` ou `'or'`, relie ce critère au précédent **au sein du même champ** (les critères sur des champs différents sont toujours reliés par `AND` entre eux, jamais par `OR` — voir construction des `group_sqls` dans `LibraryDB.search`).

**Piège whitelist** : `field` et `op` sont strictement filtrés contre ces ensembles avant toute construction SQL (`if field not in self._SEARCHABLE: continue`) — c'est la protection anti-injection. Ne jamais construire une clause SQL avec un nom de champ qui n'a pas d'abord traversé cette whitelist.

**Champs numériques stockés en TEXT** (`_INT_CAST_FIELDS` : `number`, `volume`, `year`, `month`, `day`, `page_count`, `file_size`...) sont comparés via `CAST(col AS INTEGER)` pour éviter un tri/comparaison lexicographique (`"9" > "10"` en TEXT).

**Champs booléens texte ComicInfo** (`_YESNO_TEXT_FIELDS` : `black_and_white`, `manga`, `series_complete`) stockent `"Yes"/"No"/"Unknown"/""` et non `0`/`1` — les opérateurs `true`/`false` comparent donc à ces littéraux pour ces champs précis, pas à `1`/`0`.

`search(criteria, order_by, order_asc, progress_callback)` charge tout en mémoire (utilisé pour l'export) ; `search_cursor(...)` retourne `(total, cursor)` pour un chargement par lots sans tout garder en RAM — c'est cette seconde méthode qu'utilise `LibraryWindow._action_open_db`/`_do_search` pour peupler le tableau par paquets de 500 lignes via `QTimer.singleShot(0, ...)` (ne bloque jamais l'event loop Qt).

### Côté UI (`library_window.py`)

- **`_FieldRow`** — une ligne de critère dans le panneau de gauche, un par champ recherché possible (`_ALL_FIELDS`). Gère l'ajout de sous-critères liés (`_SubField`, ET/OU), les cases spéciales media_type (`_MediaTypeSubField`), et expose `to_criteria()` qui produit la liste de dicts attendue par `LibraryDB.search*`.
- **`_do_search()`** — agrège `to_criteria()` de tous les `_FieldRow` actifs (`has_value()`) et appelle `search_cursor`.
- **Deux tableaux superposés** : `self._table` (résultats complets) et `self._filter_table` (résultats d'une recherche), un seul visible à la fois (`_filter_active`, propriété `_active_table`). Permet de revenir instantanément à la liste complète sans reconstruire quoi que ce soit.
- **Textes de cellule qui suivent la langue sans reconstruire les tableaux** : `_EmptyDelegate`, posé sur les deux tableaux, réécrit à chaque affichage les cellules vides (« non renseigné », `_EMPTY_ROLE`) et la colonne Taille : `_make_cell_item` range le nombre d'octets dans `_FILE_SIZE_ROLE`, et le délégué l'écrit par `utils.format_file_size` (unité et séparateur décimal de la langue). Le tri de cette colonne lit la valeur numérique (`_SORT_VALUE_ROLE`) ; l'export Excel écrit le nombre d'octets brut.

## Cycle de vie de la fenêtre

`LibraryWindow` est un **singleton module-level** : `_library_window` (variable module de `library_window.py`), créé une seule fois par `open_library_window(parent_panel=None, prewarm=False)`.

- **`prewarm=True`** — construit la fenêtre (35 widgets) sans l'afficher (`event.ignore()` dans `showEvent` tant que `_prewarmed`). Déclenché 2 secondes après le démarrage de chaque panel1 (`PanelWidget.__init__` → `QTimer.singleShot(2000, self._prewarm_library)`, **seulement si panel primaire**, voir skill `panels`) pour que la première ouverture réelle soit instantanée.
- **`closeEvent`** — ne détruit jamais la fenêtre : `event.ignore(); self.hide(); self._prewarmed = True`, puis arrête le process de lecture des couvertures PDF (`_preview_probe`, recréé au prochain aperçu d'un PDF). Rouvrir rappelle juste `showMaximized()`.
- **Thème, langue et police pendant que la fenêtre est masquée** — `LibraryWindow._on_language_signal` (redéfinition de celle d'`AppWindowMixin`, skill `window-title`) ne fait que poser `_language_pending` quand la fenêtre n'est pas visible (préchauffée ou fermée par la croix) ; `LibraryWindow.setVisible(True)` applique alors `_apply_theme()` puis `_retranslate()` **avant** de l'afficher, une seule fois pour tous les changements survenus entre-temps. Ses ~570 widgets coûtaient sinon plus d'une demi-seconde à chaque bascule de thème, de langue ou de police, fenêtre jamais ouverte. **Piège** : faite dans `showEvent`, cette mise à jour aurait lieu alors que la fenêtre est déjà en cours d'affichage. Fenêtre visible (réduite comprise) : mise à jour immédiate, comme toute fenêtre. Les textes « non renseigné » des cellules (`_empty_text`, `_empty_num`) sont lus par le délégué au dessin, donc à jour eux aussi. Les appels directs à `_retranslate` (titre après un changement de base) ne sont pas différés. À son tout premier affichage réel, la fenêtre reste transparente jusqu'à son premier dessin (code commun, `_CaptionBar.hide_until_painted`, skill `window-title`) : sans cela, sa première ouverture en thème sombre montrait un instant clair. La DB ouverte (`self._db`) reste chargée en arrière-plan même fenêtre cachée — c'est pourquoi `menubar_qt.py` construit les commandes de gestion de la base via `_library_window.build_db_menu(menu)` (état réel ; la méthode ajoute ses actions à la suite du menu reçu sans le vider) plutôt que de dépendre de la visibilité.
- **Commandes de menu qui affichent un label de progression** — `_menu_open_db` et `_menu_scan`, branchées dans `build_db_menu` à la place de `_action_open_db`/`_action_scan`. Une action appelée telle quelle pendant que la fenêtre est cachée dessinerait son label rouge (skill `canvas-overlay-progress`) dans une fenêtre invisible. `_menu_open_db` affiche d'abord le sélecteur de fichier (`_pick_db_file`, partagé avec `_action_open_db`), puis seulement si un fichier est choisi affiche la fenêtre (`open_library_window()`) et lance `_action_open_db(filepath)` au tick suivant, pour que le label se place sur la géométrie de la fenêtre affichée. `_menu_scan` affiche la fenêtre puis lance `_action_scan` au tick suivant. Le bouton de la barre d'outils de la fenêtre appelle directement `_action_open_db`, la fenêtre étant alors forcément visible.
- **Maximisée par défaut** au premier affichage réel (`_on_first_show` → `showMaximized`), split 3 colonnes redimensionné ensuite (`_debug_sizes`, tailles `[280, 260, reste]`).
- **`_parent_panel`** — le `PanelWidget` ciblé par la fenêtre ; utilisé par `_open_in_mosaicview()` pour savoir où charger le fichier choisi, et par les actions qui ont besoin des callbacks d'un panneau (`_get_batch_callbacks()`). La fenêtre étant unique pour les deux panneaux (split-view), `open_library_window` **réassigne `_parent_panel` à chaque ouverture non-préchauffage qui fournit un panneau** : elle cible le dernier panneau depuis lequel elle a été (ré)ouverte, pas celui qui l'a créée (le préchauffage la crée depuis panel1). **Piège** : si la fenêtre est créée par le menu Bibliothèque avant le préchauffage (moins de 2 s après le démarrage, « Nouvelle » ou « Ouvrir »), elle l'est sans panneau : `_parent_panel` reste `None` et « Ouvrir dans MosaicView » ne fait rien tant qu'elle n'a pas été rouverte depuis un panneau. Doit toujours être un `PanelWidget` (jamais un widget interne comme `_left_panel`, qui n'a pas de `_state`) : la colonne d'icônes et le menu Bibliothèque passent par `PanelWidget._open_library`, le drop de dossiers par le panneau lui-même (skill `batch-library-create`). Les appels sans panneau (sous-menu « Bases récentes » et commandes de gestion de la base du menu Bibliothèque, `menubar_qt.py`) conservent la cible courante.

## Chemin d'un fichier indexé — `LibraryDB.get_absolute_path(comic_id)`

Utilisé par toutes les actions sur un fichier de la base (ouvrir dans MosaicView, ouvrir avec l'application par défaut, montrer dans l'Explorateur, convertir en CBZ, éditer ComicInfo.xml, aperçu). `relative_path` est relatif au répertoire maître :
- fichier du maître → `safe_join(master, rel)` ;
- fichier d'un **répertoire additionnel** → chemin relatif en `../…`, ou absolu s'il est sur un autre lecteur (`os.path.relpath` lève `ValueError`, le scan garde alors le chemin absolu) : `safe_join` le refuse, et le chemin reconstruit (`normpath(join(master, rel))`) n'est accepté que s'il est dans l'un des répertoires de la base (`_is_in_library_dirs`) ;
- sinon `None` : les appelants ignorent l'action. Une ligne d'une base abîmée ou reçue d'un tiers ne peut ainsi pas livrer un fichier quelconque du disque à la conversion (qui supprime la source) ou à `os.startfile`. **Limite** : les répertoires sont eux-mêmes lus dans la base ; une `.mvdb` reste un fichier de l'utilisateur, de confiance.
Ne jamais supprimer le repli des répertoires additionnels (ils deviendraient inaccessibles). Testé par `tests/test_library_db.py` (répertoire additionnel accessible, chemins hors des répertoires refusés).

## Ouvrir un comic depuis la Bibliothèque vers un panneau

`LibraryWindow._open_in_mosaicview()` : récupère le premier id sélectionné, résout son chemin absolu (`LibraryDB.get_absolute_path`, voir ci-dessous), puis sur `self._parent_panel` :
- si un fichier est ouvert (`current_file` ou `images_data`), appelle `close_file(panel, state=panel._state, on_closed=_load, **panel._file_close_args())` (skill `file-close`) — le chargement n'est enchaîné **qu'une fois le fichier réellement fermé**, et jamais si l'utilisateur annule ;
- sinon appelle `_load()` directement.

`_load()` fait `panel._load_files([abs_path])` puis mémorise `panel._library_window = self` et `panel._library_db = db` (la base d'où vient le fichier). `PanelWidget._on_file_saved` s'en sert pour réindexer la ligne de la bibliothèque après une sauvegarde, seulement si cette même base est encore ouverte. Ce lien suit le document : `_load_files` ne le remet à `None` que pour un nouveau document (`not already_open`), une fusion dans le fichier ouvert le conserve. **Ne fait rien si `_parent_panel` est `None`**.

**Piège** : ne jamais enchaîner `_load_files` juste après `panel._close_file()` — la fermeture d'un fichier modifié passe par un dialogue non modal et rend la main aussitôt ; `_load_files` verrait alors le fichier encore ouvert (`already_open`) et **fusionnerait** le comic choisi dedans au lieu de le remplacer.

Trois autres actions sur la sélection : `_open_in_explorer()` (réutilise `_explorer_select`, voir skill `explorer-select`), `_open_with_default()` (`os.startfile`), et double-clic/Entrée sur une ligne du tableau routent aussi vers `_open_in_mosaicview`.

## Ajouter un nouveau champ de recherche/colonne

1. Ajouter la colonne dans `_CREATE_COMICS` (`library_db.py`) si c'est un nouveau champ ComicInfo — l'ajouter aussi à `_COMICINFO_FIELDS` pour qu'`_index_file` le peuple depuis le XML.
2. L'ajouter à `LibraryDB._SEARCHABLE` pour qu'il soit accepté par `search`/`search_cursor` (whitelist anti-injection — une omission ici rend le champ silencieusement ignoré, pas une erreur).
3. Si le champ est numérique stocké en TEXT, l'ajouter à `_INT_CAST_FIELDS`. Si c'est un booléen texte façon ComicInfo (`Yes`/`No`), l'ajouter à `_YESNO_TEXT_FIELDS`.
4. Côté UI : ajouter l'entrée à `_ALL_FIELDS`/`_ALL_COLUMNS`/`_DEFAULT_COLUMNS` (constantes en tête de `library_window.py`) pour qu'une `_FieldRow` et une colonne de tableau soient générées automatiquement.
5. Toute base `.mvdb` existante ne verra la nouvelle colonne remplie qu'après un rescan (`_action_scan`) — `CREATE TABLE IF NOT EXISTS` ne rajoute pas de colonne à une table déjà créée avec un schéma plus ancien (pas de migration `ALTER TABLE` en place aujourd'hui). Si une migration de schéma s'avère nécessaire, le signaler avant de l'implémenter plutôt que de supposer que `IF NOT EXISTS` suffit.

## Ce qui n'est PAS géré ici

- L'ouverture d'un `.mvdb` **double-cliqué dans l'Explorateur Windows** (association de fichier) : routée par le mécanisme single instance (`MosaicView.py::main()` → `_open_associated_path` → `open_library_window` + `_action_open_db`), y compris quand une instance MosaicView tourne déjà — voir skill `single-instance`. Côté bibliothèque, le point d'entrée reste `_action_open_db(filepath)`.
- L'édition des métadonnées ComicInfo d'un comic (`_action_edit_comicinfo`/`_open_comicinfo_editor`) — voir skill `comicinfo-metadata-editor` — et le scraping ComicVine (`_action_fetch_metadata`) — voir skill `comicvine-metadata-fetch` — délèguent à des modules dédiés déjà existants — pas un sujet propre à ce skill sauf pour le point de réindexation après écriture (`_write_comicinfo_and_reindex`, appelle `LibraryDB.reindex_files`).
- **Jamais d'échec silencieux** : archive illisible au chargement de la conversion (`_convert_file_to_cbz._on_error` → `library.convert_to_cbz_error_message` avec le texte de l'erreur du chargeur, `LoadWorker.error_text_fn`), seconde conversion demandée pendant une première, en filet seulement puisque les commandes sont grisées (`library.convert_already_running`), ComicInfo.xml illisible ou disparu depuis le dernier scan à l'ouverture de l'éditeur (`_open_comicinfo_editor` → `library.comicinfo_read_failed`, `library.comicinfo_missing`) : un message par `_show_error`, sans cri de Wilhelm. **Piège** : ces trois cas faisaient sembler la commande sans effet. Pages illisibles dans l'archive à convertir : rien n'est écrit, et le message les nomme avec leur raison traduite à chaque affichage (`read_errors.files_ignored_line`, dans la fonction de texte passée à `_show_error`), au lieu du message technique brut, figé dans la langue d'origine.
- La conversion CBR/CB7→CBZ (`_convert_file_to_cbz`) réutilise le pipeline de conversion existant de l'appli ; le point d'intégration bibliothèque est seulement `_refresh_row_after_convert` (met à jour la ligne DB + `remove_by_id` de l'ancien id si le chemin change). **Nom du CBZ** : dès le départ, elle réserve la source (`_claim_files_for_write`, refusée avant toute lecture si un lot la détient) et le premier nom libre (`claims.reserve(batch_claims.free_name_candidates(…))` : `Nom.cbz`, sinon `Nom (1).cbz`, comme les lots ; skill `batch-processing`) ; la réservation n'engage que les lots, donc un nom créé entre-temps par un autre programme ou un panneau est remplacé par le suivant juste avant l'écriture. **Piège** : réservé sans ce nouveau test, le fichier créé entre-temps serait écrasé. Réservations libérées à la fin de l'écriture (`_end_conversion`). **Correction d'extension** : `ConversionExtensionDialog` (`library_dialogs.py`, sous-classe d'`archive_loader.ExtensionCorrectionDialog`, mêmes réponses `rename`/`keep`/annuler, textes de `conversion_ext_texts`, clés `library.convert_ext_*`) : la fenêtre des panneaux propose « Ouvrir sans renommer » alors que rien n'est ouvert ici. Le nouveau nom vient de `LoadWorker.rename_target` (`_rename_target`, appelée dans le thread du worker) : un CBZ mal nommé prend le nom déjà réservé, un autre format le suivant de libre. `file_renamed` (`_on_file_renamed`) réserve le nouveau nom et fait suivre la ligne de la base, quelle que soit la suite. Source devenue `.cbz` : il n'y a plus rien à convertir, `_finish(source_path)`. Elle écrit via `replace_file_atomically` (`utils.py`, skill `save-export`) : un échec ne laisse aucun CBZ partiel. **Page altérée** (cadre orange, skill `corrupted-images`) : `_confirm_altered_pages_qt` pose la question avant d'écrire, comme un enregistrement depuis un panneau ; refusée, rien n'est écrit. **Elle n'écrit rien si le chargement a signalé une erreur** (`errors` de `LoadWorker` non vide : page illisible, archive partiellement lue — message `library.convert_to_cbz_error_message`) et passe ses entrées par `cbz_members` (`utils.py`, skill `save-export` : noms uniques, `MissingPageDataError` pour une entrée sans données) : la question « supprimer l'original ? » qui suit ne doit jamais porter sur un CBZ incomplet. Sur « Oui » (`_after_choice`, qui réserve de nouveau la source : la question a pu attendre), dans un thread (`_run_file_task`), `converted_cbz.reread_then_delete_source(new_path, len(cbz_members(entries)), source_path, written_signature=…)` (skill `batch-processing`, « Écrire, relire, supprimer » ; skill `save-export`, « Relecture avant suppression ») vérifie que le CBZ n'a pas changé depuis son écriture (`file_signature` relevée juste après `replace_file_atomically`), le relit, puis met l'original à la Corbeille (`utils.send_to_trash`). CBZ réécrit pendant la question : `ConvertedCbzChangedError` affichée par `_show_error` sans cri de Wilhelm, original gardé. CBZ qui ne se relit pas : `WrittenFileCheckError` affichée par `_show_error` (cri de Wilhelm), original gardé. Dans les deux cas, la ligne de l'ancien fichier reste dans la base. La suppression du fichier `.mvdb` (« Supprimer la base ») passe aussi par `utils.send_to_trash`, seule implémentation de la mise à la Corbeille. La réécriture du ComicInfo.xml d'un CBZ depuis la Bibliothèque (éditeur `_open_comicinfo_editor` et vérification ComicVine `_write_comicinfo_and_reindex`) passe par `_rewrite_comicinfo_in_cbz(abs_path, xml_name, xml_bytes, on_done=None)`, asynchrone (`_run_file_task`, `on_done(True)` si le CBZ a été réécrit, sinon `on_done(False)`) : remplacement de l'entrée ComicInfo.xml existante via `replace_file_atomically`, le CBZ produit étant contrôlé par `check_written_cbz_structure` avant de remplacer l'original (skill `save-export`) (seul le ComicInfo.xml de la BD — `comic_info.comic_info_member` : racine, ou dossier qui contient toutes les pages, règle de skill `comicinfo-metadata-editor` — est remplacé, à sa place, sous le nom `xml_name` lu à l'ouverture de l'éditeur : **piège**, l'éditeur rend toujours « ComicInfo.xml », et ce nom le déplacerait à la racine ; un autre fichier nommé `ComicInfo.xml` à la racine est gardé sous un nom d'annexe (`annex_comic_info_name`), comme à l'ouverture dans un panneau ; `ComicInfo_0002.xml` ou le ComicInfo.xml d'un autre dossier sont recopiés tels quels ; un ancien ComicInfo.xml lisible seulement réparé — `comic_info.comic_info_strictly_readable` faux — est recopié intact juste après, sous un nom libre de l'archive (`annex_comic_info_name`), puis une `InfoDialog` (`dialogs.comicinfo_repaired.*`, par `_show_dialog`) le signale ; `_open_comicinfo_editor` lit lui aussi celui de la BD, par son `ZipInfo` et avec `_check_member_size`, commentaire d'archive ZIP — métadonnées ComicBookInfo — recopié, autres membres recopiés par `ZipInfo` — `zin.read(item)`, jamais par nom, qui rendrait le dernier homonyme pour chacun), `ErrorDialog` (`messages.errors.save_failed.*`) et CBZ d'origine intact en cas d'échec, `on_done(False)` (pas de réindexation). Une archive sans ComicInfo.xml le reçoit à la racine (ses deux appelants partent normalement d'un CBZ qui en a déjà un ; sans cet ajout, la réécriture réussissait sans rien écrire). La vérification des mises à jour ComicVine part d'un `VirtualLibraryPanel` qui ne charge pas le contenu des fichiers : `write_comic_metadata_from_scraper` y construit le ComicInfo.xml à partir des seuls champs de ComicVine — choix voulu. `_rewrite_comicinfo_in_cbz` (le temps de l'écriture) et `_convert_file_to_cbz` (source et CBZ cible, de la lecture à la fin de l'écriture) réservent leurs fichiers auprès des traitements par lot (`file_operations_qt._claim_files_for_write`, skill `save-export`) : un fichier traité par un lot (conversion, import des métadonnées en lot) est refusé avec `messages.errors.file_in_batch`, le lot pouvant le réécrire ou le supprimer pendant l'écriture.
- Toutes les règles UI Qt obligatoires (non-modale, thème, langue à la volée, tooltips via `OverlayTooltip`) s'appliquent intégralement à `LibraryWindow` et ses dialogues (`NewDbDialog`, etc.) — voir CLAUDE.md, pas un mécanisme spécifique à la bibliothèque.
- **Barre de titre dessinée par Qt** (`AppWindowMixin`, skill `window-title`) pour `LibraryWindow` et ses trois dialogues ; `LibraryWindow` l'appelle avec `_setup_window(delete_on_close=False)` (fenêtre jamais détruite, voir plus haut) et garde sa traduction branchée tant qu'elle existe, masquée comprise. Le titre de `LibraryWindow` suit la base ouverte : `_retranslate` (rappelée à chaque changement de base et de langue) appelle `set_window_title('library.window_title', name=…)` ou `set_window_title('library.window_title_no_db')`. Sans fenêtre parente, elle a Réduire, Agrandir et Fermer, et son bouton dans la barre des tâches. Créée à l'avance sans être affichée (`prewarm`), son cadre Windows n'est installé qu'à son premier affichage réel (`FramedWindowMixin.setVisible`) ; masquée à la fermeture, jamais détruite (exception à `WA_DeleteOnClose`, règle UI n° 4 de CLAUDE.md).
- **Placement des fenêtres de la Bibliothèque** : toute fenêtre qu'elle ouvre (`NewDbDialog`, `RenameDbDialog`, `ConfirmDeleteDialog`, `_show_error`, fin de scan) s'affiche par `LibraryWindow._show_dialog(dlg)`, qui pose `dlg.set_center_widget(self._dialog_anchor())` puis appelle `show_nonmodal()` ; la fenêtre de choix de fichier (`file_picker_qt` : ouvrir une base, `_pick_db_file(on_chosen)` ; ajouter un dossier ; changer le dossier principal ; export Excel, suite dans `_export_to(path)`) a la Bibliothèque pour parent et `center_on=self._dialog_anchor()`. Sa réponse est différée : ajouter un dossier et changer le dossier principal vérifient que la base ouverte est encore la même (`self._db is db`) et qu'aucun chargement n'a démarré ; l'export Excel, que la liste n'est pas vide. `NewDbDialog` (`library_dialogs.py`) ouvre la même fenêtre pour ses deux champs de dossier (parent : elle-même, fermée avec elle). Fenêtre de choix : skill `file-picker`, qui refuse de renommer ou de supprimer la base ouverte (`_db.db_path`) ou son dossier. `_dialog_anchor()` rend la Bibliothèque si elle est visible ; masquée (préchauffée ou fermée par la croix), elle garde une géométrie sans rapport avec l'écran (640×480 en (0, 0) avant son premier affichage), et l'ancre devient le panneau dont le menu a lancé l'action (`_menu_panel`), sinon `_parent_panel` (chacun contrôlé par `shiboken6.isValid` : le panneau 2 est détruit à la fermeture du double panneau), sinon elle-même. `_menu_panel` est posé par `_run_menu_action`, par lequel passent toutes les actions de `build_db_menu(menu, panel)` ; `menubar_qt._populate_library_menu` lui passe le panneau du menu ouvert (callback `get_panel` de `menubar_callbacks_qt`, rangé dans `FREE_WHILE_BUSY` de `tests/test_operation_running.py`). **Piège** : un nouvel affichage de fenêtre dans `library_window.py` par `dlg.show_nonmodal()` direct se centre sur la Bibliothèque masquée quand l'action vient du menu, au coin de l'écran ou hors du panneau d'où vient la commande. Restent en `show_nonmodal()` direct les fenêtres qui ne s'ouvrent que depuis la Bibliothèque affichée : l'erreur d'écriture de `_rewrite_comicinfo_in_cbz` et le message de fin d'export Excel.

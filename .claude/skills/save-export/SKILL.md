# Sauvegarde et export CBZ — MosaicView

Toutes les opérations qui écrivent un fichier CBZ (ou exportent des pages en dehors d'une archive) sont regroupées dans un seul fichier : `modules/qt/file_operations_qt.py`. Cinq fonctions publiques (dont `apply_new_names`, qui couvre deux cas), une chaîne de validation asynchrone partagée, et une dizaine de dialogues non-modaux dédiés.

## Les 5 fonctions publiques

| Fonction | Déclenchée quand | Résultat |
|---|---|---|
| `save_as_cbz(parent, canvas, callbacks)` | Archive ouverte (CBZ ou autre format), **modifiée ou non**, "Enregistrer sous" (menu Fichier, menu contextuel) ; aussi l'icône Enregistrer (`apply_save`, skill `icon-toolbar`) en mode « Enregistrer sous » — mode par défaut sur une archive non modifiée | Nouveau fichier CBZ écrit depuis l'état en mémoire (modifications comprises), ancien optionnellement supprimé — sauf si le fichier choisi est le fichier ouvert (voir "Pièges") |
| `save_selection_as_cbz(parent, callbacks, canvas=None)` | Sélection non vide, "Enregistrer la sélection en CBZ" | Nouveau CBZ contenant uniquement les entrées sélectionnées |
| `save_selection_to_folder(parent, callbacks)` | Sélection non vide, "Exporter la sélection" | Fichier unique (1 sélection) ou dossier (plusieurs), bytes écrits sans conversion (avec la résolution de la page, `_bytes_with_entry_dpi`), chaque fichier par `_write_file_safely` (voir « Export vers un dossier ») |
| `create_cbz_from_images(parent, canvas, callbacks, on_complete=None)` | Pas d'archive ouverte, images chargées, "Créer une archive CBZ" ; aussi « Oui » à la fermeture d'images modifiées (skill `file-close`) | Nouveau CBZ à partir d'images isolées |
| `apply_new_names(parent, canvas, callbacks, on_complete)` | Bouton "Appliquer" après renommage/modification | Écrase le `.cbz` existant, **ou** convertit CBR/CB7/CBT/EPUB/PDF → nouveau `.cbz` |

Tous les points d'entrée sont câblés dans `menubar_callbacks_qt.py` vers des méthodes de `PanelWidget` (`_save_as_cbz`, `_save_selection_as_cbz`, `_save_selection_to_folder`, `_create_cbz_from_images`, `_apply_new_names`, dans `panel_widget.py`), elles-mêmes appelées depuis la barre de menu, la colonne d'icônes et/ou le menu contextuel selon la fonction, ainsi que par le flux de fermeture (`create_cbz_cb`/`apply_new_names_cb`, skill `file-close`). Toutes passent `self._file_op_callbacks()` comme `callbacks`.

## State du panneau — toujours `callbacks["state"]`, jamais le singleton

`PanelWidget._file_op_callbacks()` fournit `"state": self._state`. Chaque fonction publique le lit en tête (`state = callbacks.get("state") or _state_module.state`, le singleton n'étant qu'un repli pour un appelant qui ne le fournirait pas) puis **propage ce `state` local partout** : `_check_no_ico(parent, state)`, `_check_no_video(parent, state)`, les lambdas de la chaîne de validation, et `_write_apply_new_names(parent, canvas, callbacks, _done, state)`.

**Why** : ces fonctions s'exécutent souvent en différé — appelées par un dialogue de fermeture non modal, ou poursuivies après les dialogues non modaux de la chaîne de validation. Pendant ce temps l'utilisateur peut cliquer dans l'autre panneau, ce qui repointe le singleton `modules.qt.state.state` (voir skill `panels`). Relire le singleton à ce moment-là fait écrire le fichier de l'autre panneau, puis fermer le premier sans l'avoir sauvegardé. Garde-fou : `tests/test_check_no_deferred_singleton.py` (scan AST) échoue sur toute lecture de `_state_module.state` dans ce fichier qui n'est ni `x or _state_module.state` ni dans un `if state is None:`.

## Vérifications pré-sauvegarde communes (`_run_validation_chain`)

`save_as_cbz`, `create_cbz_from_images` et `apply_new_names` (première moitié) enchaînent la même série de validations **non modales**, chacune avec un callback `on_done(bool)` :

1. **`_validate_filenames_qt`** — cherche des caractères interdits (`<>:"|?*`), des caractères de contrôle, et un segment de chemin égal à `..` (`_has_parent_dir_segment` : sortie du dossier d'extraction) dans `orig_name` — des points dans un nom (`Fin...jpg`) ne sont pas signalés, seul le segment entier compte ; la correction retire ces segments (`_without_parent_dir_segments`), testées par `tests/test_parent_dir_segment.py`. Détecte automatiquement si l'archive a une **structure de sous-dossiers légitime** (`has_subdirectory_structure` — un `/` dans `orig_name` d'un fichier qui n'est pas une entrée `is_dir`) : si oui, `/` n'est pas traité comme un caractère interdit. Propose une correction automatique via `QuestionYNCDialog` (remplace les caractères invalides par `_`) — Oui/Non/Annuler, pas juste Oui/Non.
2. **`_check_animated_gifs_qt`** — avertit si la mosaïque contient une image animée, quel que soit son format (`_has_animated_gifs`, qui teste `image_ops.is_animated_entry` : GIF, WebP, PNG ou AVIF animé). Les bytes sont écrits tels quels dans le CBZ, mais les lecteurs de BD (CDisplayEx, YACReader…) n'en affichent que la première frame. Texte `messages.warnings.animated_gif_in_comic` (nom de clé conservé, texte « image animée »). `ConfirmDialog` Oui/Non.
3. **`_handle_duplicate_filenames_qt`** — détecte les doublons de noms via `detect_duplicate_filenames_for_save` (`dialogs_qt.py`), propose `DuplicateFilenameDialog` avec 3 choix : **renuméroter** (appelle `callbacks['renumber_btn_action']`, voir skill `renumbering`), **ignorer et sauvegarder quand même** (les homonymes reçoivent alors un suffixe `_2`, `_3`… dans le fichier écrit, `cbz_members`, sans changer les noms en mémoire), ou **annuler**. `DuplicateFilenameDialog._retranslate` (rappelée par `language_signal` : langue, thème, taille de police) réapplique le thème (`get_current_theme`, titre en orange d'avertissement) et `get_current_font()` sur le titre, le message et les trois boutons — police toujours par `setFont`, jamais de `font-size` dans un stylesheet, qui l'écraserait. Fenêtre à largeur fixe (520) avec libellé à retour automatique : la hauteur du message est imposée après `setFont` (`setMinimumHeight(heightForWidth(...))`, piège WordWrap de `CLAUDE.md`, règle UI n° 5). Le message ne parle pas de « doublons » : plusieurs fichiers (2, 3 ou plus) peuvent porter le même nom, tous sauf le premier reçoivent un suffixe.

`_run_validation_chain(steps, on_all_passed, state=None)` exécute les steps en séquence (pas en parallèle) et s'arrête au premier échec — remplace une cascade de `if not X(): return` synchrones, impossible ici puisque chaque validation ouvre potentiellement une fenêtre non-modale et doit attendre la réponse de l'utilisateur avant de continuer (voir règle CLAUDE.md n°4, non-modalité obligatoire). Les trois fonctions publiques lui passent leur `state` : elle capture `state.doc_generation` et s'arrête en silence avant chaque étape et avant `on_all_passed` si le document a été fermé ou remplacé. **Piège** : la fermeture du document ferme aussi la fenêtre de l'étape en cours, et la fenêtre d'information « Correction effectuée » de `_validate_filenames_qt` appelle `on_done(True)` à sa fermeture (`finished`) ; sans cette garde, la chaîne continuait sur l'état vidé (`TypeError` sur `current_file`, ou fenêtre « Créer un CBZ » pour un panneau vide).

`_validate_filenames_qt`, `_check_animated_gifs_qt` (et `_has_animated_gifs` qu'elle appelle), `_handle_duplicate_filenames_qt` (et `detect_duplicate_filenames_for_save` dans `dialogs_qt.py` qu'elle appelle), ainsi que `_auto_update_page_count_qt`, acceptent toutes un paramètre `state=None` (repli sur le singleton si omis). **Toujours leur passer le `state` local de la fonction publique** (`lambda done: _validate_filenames_qt(parent, render_mosaic, done, state)`, etc.), jamais laisser une étape de la chaîne relire le singleton elle-même (voir section précédente). **Toute nouvelle validation ajoutée à la chaîne doit suivre ce même pattern.**

`save_selection_as_cbz`/`save_selection_to_folder` ne passent que par l'étape 3 (doublons), pas les étapes 1/2 — cohérent, puisqu'exporter une sélection ne réécrit pas l'archive complète.

Avant les validations, `_check_no_ico`/`_check_no_video` bloquent purement et simplement la sauvegarde CBZ (pas de correction possible) si la mosaïque contient un `.ico` (voir skill `create-ico`) ou une vidéo (extensions listées dans `_VIDEO_EXTENSIONS`) — `MsgDialog`/`ErrorDialog` immédiat, la chaîne de validation n'est même pas lancée.

## Écriture effective du ZIP

- **`cbz_members(entries)`** (`utils.py`) — **point de passage de toute écriture de CBZ à partir d'entrées** (`_write_zip_with_progress`, conversion CBZ de la Bibliothèque) : renvoie `[(nom dans le ZIP, entrée)]`, dossiers exclus, dans l'ordre.
  - **Lève `MissingPageDataError` si une entrée n'a pas de données** (`bytes is None` : fichier illisible à l'ouverture de l'archive, marqué corrompu, skill `archive-image-loading`). Autrefois ces entrées étaient sautées en silence : enregistrer réécrivait le CBZ ouvert sans elles (alors que leurs données, même endommagées, restaient récupérables dans l'original), et une conversion proposait ensuite de supprimer l'original. `MissingPageDataError.__str__` traduit `messages.errors.pages_without_data` (liste de 10 noms au plus) à chaque affichage. **`_check_pages_have_data(parent, entries)`** fait la même vérification avant toute question à l'utilisateur, en tête de `save_as_cbz`, `create_cbz_from_images`, `apply_new_names` (tout le document) et `save_selection_as_cbz` (la sélection) : `ErrorDialog` et abandon. L'export vers un dossier n'est pas concerné (il ne réécrit pas l'original).
  - **Noms uniques** : deux entrées de même nom reçoivent des noms distincts dans le ZIP (`_2`, `_3`… sur la seconde, jamais un nom déjà porté par une autre entrée) ; les noms en mémoire ne changent pas. Dans un ZIP, la lecture par nom rend le contenu du dernier homonyme pour tous : le premier serait perdu à la réouverture puis au prochain enregistrement. C'est ce que fait « Ignorer et sauvegarder » de `DuplicateFilenameDialog`, dont le texte (`dialogs.duplicate_filenames.message`) l'annonce.
  - Testé par `tests/test_utils_atomic_write.py` (`test_entry_without_data_is_refused`, `test_homonyms_get_distinct_names`, `test_written_homonyms_are_all_readable`).
- **Commentaire d'archive ZIP — `_zip_comment(path)`** : champ de texte libre d'un ZIP, où ComicRack et ComicTagger rangent des métadonnées (ComicBookInfo). Toute réécriture d'un CBZ le recopie : `_write_zip_with_progress` prend un paramètre `comment` (posé sur `zf.comment`). Lu sur le fichier ouvert **avant** l'écriture (il peut être la destination) par `_write_document_unlocked`, pour tout enregistrement du document entier (« Enregistrer sous », y compris par-dessus le fichier ouvert, et `_write_apply_new_names`). `b""` si le fichier ouvert n'est pas un ZIP (conversion CBR/PDF…) ou s'il n'y en a pas (création à partir d'images). Une sélection enregistrée en CBZ ne le reprend pas (il décrit le comic entier). Même règle hors de ce fichier : recompression (skill `batch-processing`), réécriture du ComicInfo par la Bibliothèque (skill `library`), import de métadonnées en lot (skill `batch-metadata-import`).
- **`_write_zip_with_progress(filepath, images_data, overlay, compression_level)`** — seul écrivain ZIP de ce fichier, appelé par `_write_document_unlocked`. Écrit chaque membre de `cbz_members(images_data)` via `zf.writestr(nom, _bytes_with_entry_dpi(entry))` ; une entrée vidée pendant l'écriture (fermeture du document) lève `MissingPageDataError`, convertie en `_DocumentChangedDuringSave` par `_write_document_with_progress` si `doc_generation` a changé. `_bytes_with_entry_dpi` donne les bytes à écrire quand `entry["dpi"]` est défini et diffère du DPI encodé dans les bytes — cas des pages issues d'un PDF, dont `dpi` est la résolution de rendu (skill `pdf-loading`) — **sans jamais modifier la page en mémoire** (aucun changement hors historique) :
  - **JPEG et synonymes** (`_JPEG_EXTS`) : `jpeg_bytes_with_dpi(data, dpi)` écrit la densité dans le segment JFIF (APP0), en le créant après le marqueur de début s'il manque, **sans ré-encoder** l'image. **Piège** : un ré-encodage (`save_image_to_bytes`) pour inscrire la résolution coûterait une perte de qualité à chaque enregistrement.
  - **PNG, TIFF** : ré-encodage sans perte par `save_image_to_bytes` sur une copie de l'entrée.
  - **Uniquement pour les extensions de `_DPI_WRITABLE_EXTS`** (les seules pour lesquelles `save_image_to_bytes` écrit le DPI) : pour WebP/AVIF/GIF/BMP/ICO, le DPI relu ne correspondrait jamais, l'image serait ré-encodée à chaque sauvegarde. Si une extension est ajoutée au DPI écrit par `save_image_to_bytes`, l'ajouter aussi à cet ensemble.
  - **Jamais pour une image animée** (`image_ops.is_animated_entry`, cas du PNG animé) : `save_image_to_bytes` n'écrirait que sa première frame.
  - En cas d'erreur, les bytes d'origine sont écrits.
  - Testé par `tests/test_save_dpi_bytes.py` (fonctions extraites par AST : toute nouvelle dépendance de `jpeg_bytes_with_dpi`/`_bytes_with_entry_dpi` doit être ajoutée à son espace de noms). Met à jour `_SavingOverlay` (overlay rouge "Sauvegarde X%" sur le canvas, classe locale à ce fichier — **pas** le mécanisme `canvas_overlay_qt.py` habituel, voir "Pièges" plus bas) après chaque entrée.
- **`_write_document_with_progress(filepath, state, overlay, compression_level, entries=None)`** — **point de passage de tout enregistrement d'un CBZ depuis un panneau** : `save_as_cbz` et `create_cbz_from_images` directement, `save_selection_as_cbz` et les trois branches de `_write_apply_new_names` via **`_write_cbz_with_overlay(canvas, filepath, state, compression_level, entries=None)`** (crée et retire le `_SavingOverlay`, rend `False` sans message si `_document_still_writable(state)` est faux — une opération a pu démarrer pendant la boîte native d'enregistrement — ou si `_DocumentChangedDuringSave` est levée ; une erreur d'écriture remonte à l'appelant). `entries` : pages à écrire à la place du document entier (la sélection), alors sans le commentaire d'archive du fichier ouvert. Toutes traitent les événements en cours de route (`_SavingOverlay.update` → `QApplication.processEvents()`, indispensable pour que l'application et l'autre panneau restent utilisables : **ne jamais bloquer clavier/souris pendant une sauvegarde**, ce serait l'équivalent d'une fenêtre modale ; une écriture d'un bloc, sans progression, fige les deux panneaux sur un gros comic). `save_selection_as_cbz(parent, callbacks, canvas=None)` reçoit le canvas du panneau pour la progression. Elle capture `state.doc_generation` et le sommet de l'historique (`history_top`) avant d'écrire, appelle `_write_zip_with_progress` via `replace_file_atomically`, puis :
  - si `doc_generation` a changé (document fermé ou remplacé pendant l'écriture : ses pages restantes ont été vidées par `force_close_file`, skill `file-close`), lève `_DocumentChangedDuringSave` dans l'écriture → temporaire supprimé, destination intacte ; l'appelant abandonne sans message (`save_as_cbz` : `return` ; `create_cbz_from_images` : `on_complete(False)`) ;
  - retourne `False` si une action a été enregistrée dans l'historique pendant l'écriture, ou si un ajout mis en attente pendant l'écriture (numérisation, import web… — `state.run_when_idle`, skill `undo-redo`) a été appliqué par l'`end_operation` du verrou : l'appelant ne remet alors **pas** `modified` à `False` ni n'appelle `mark_history_saved`, l'état courant pouvant différer du fichier écrit (testé par `tests/test_operation_running.py`, `test_addition_during_write_is_not_marked_saved`).
  `_write_zip_with_progress` parcourt la liste figée par `cbz_members` (une copie), pour qu'une page supprimée pendant l'écriture ne décale pas l'itération.
  - **Verrou du document pendant l'écriture** : `_write_document_with_progress` inscrit l'écriture comme opération en cours (`state.begin_operation(token)` / `end_operation` dans un `finally`, skill `undo-redo`) puis appelle `_write_document_unlocked`, qui contient l'écriture proprement dite. Pendant les `processEvents`, toutes les commandes de `panel_widget.BUSY_BLOCKED_COMMANDS` (dont un second enregistrement, la suppression, le déplacement, les modifications d'images) sont sans effet et grisées, et Annuler/Refaire aussi. Sans ce verrou, un second clic sur Enregistrer lançait une écriture imbriquée du même fichier. La navigation (entrer dans un sous-dossier, faire défiler) reste permise. Testé par `tests/test_operation_running.py` (fonction extraite par AST, `_write_document_unlocked` remplacée).
- **Enregistrement pendant une opération en arrière-plan (rotation, redimensionnement…)** : les commandes d'enregistrement sont grisées (`BUSY_BLOCKED_COMMANDS`), mais `apply_new_names` et `create_cbz_from_images` sont aussi appelées directement par la fermeture (« Enregistrer et fermer », « Oui, créer un CBZ », skill `file-close`) : elles refusent d'entrée (`state.operation_running()` → `_done(False)`, le comic reste ouvert). Et chaque suite différée d'un enregistrement — fin de la chaîne de validation (`_on_validated` de `save_as_cbz`, `save_selection_as_cbz`, `save_selection_to_folder`, `create_cbz_from_images`, `apply_new_names`), réponse à `_confirm_if_changed_on_disk` (`_write_and_finish`, `_write_cbz`) — commence par `_document_still_writable(state)`, sans effet si une opération a démarré pendant que la question non modale était affichée. **Piège** : sans ces gardes, le fichier était écrit avec des pages à moitié traitées, « Enregistré » s'affichait, puis le comic restait ouvert sans explication.
- **Toute écriture de CBZ de ce fichier passe par deux étapes communes**, à reproduire pour toute nouvelle écriture :
  1. **`_check_disk_space(parent, dest, entries)`**, avant l'écriture : compare `estimate_cbz_size(entries)` (`utils.py`, majorant : données + en-têtes ZIP) à l'espace libre du dossier de `dest` ; sinon `ErrorDialog` `messages.errors.disk_full.message` (nécessaire/disponible) et abandon. Le temporaire et le fichier remplacé coexistent jusqu'au remplacement : il faut la taille complète du nouveau CBZ.
  2. **`replace_file_atomically(dest, write_to)`** (`utils.py`) : `write_to(tmp)` écrit dans un fichier temporaire `.~mosaicview_*.tmp` créé **dans le dossier de `dest`** (`make_temp_path`, voir ci-dessous), dont le contenu est forcé sur le disque (`fsync_file`, `utils.py` — sinon une coupure de courant peut laisser un fichier vide sous le nom final, l'ancien étant déjà perdu), puis `replace_file_retrying` le substitue d'un seul coup (retenté 5 fois à 0,2 s d'intervalle si `dest` est verrouillé par un autre programme — erreurs Windows 5/32/33 ; s'il le reste, `FileInUseError`, dont le texte `messages.errors.file_in_use` est traduit à chaque `str()` : un dialogue qui l'affiche via `lambda err=e: _(…, error=err)` suit la langue, jamais `err=str(e)` qui le figerait ; testé par `tests/test_utils_replace_retry.py`) ; en cas d'échec (y compris `BaseException`), le temporaire est supprimé et `dest` reste intact.
     - **Fichier en lecture seule** : `ReadOnlyFileError` (sous-classe de `PermissionError`, texte `messages.errors.file_read_only` traduit à chaque `str()`, comme `FileInUseError`) au lieu du message système brut « [WinError 5] Accès refusé », écrit dans la langue de Windows et non celle de l'application.
     - **Identité du fichier remplacé** : `_replace_keeping_identity` passe par `ReplaceFileW` (Windows) quand `dest` existe, qui transfère au nouveau contenu la date de création, les attributs (caché, archive), les droits d'accès et les flux annexes de l'ancien fichier ; `os.replace` en ferait un fichier neuf. Erreurs 5/32/33 → `PermissionError` pour la boucle de nouvelles tentatives ; autre erreur (volume qui ne la prend pas en charge, certains partages réseau) → repli sur `os.replace`. **Piège** : sans fichier de sauvegarde, les erreurs 1176/1177 de `ReplaceFileW` peuvent avoir déjà retiré `dest` de son nom ; le temporaire, seul contenu complet, doit alors prendre sa place (`os.replace` réessayé tant que `dest` est absent), puisque l'appelant le supprime en cas d'échec. Testé par `tests/test_utils_atomic_write.py` (date de création, attribut caché).
     - **Lien symbolique** : un `dest` qui est un lien est résolu (`os.path.realpath`) : c'est sa cible qui reçoit le nouveau contenu, le lien reste un lien.
     - **Temporaires abandonnés** : `make_temp_path(dossier)` (`utils.py`) crée le temporaire, l'inscrit parmi les écritures en cours du processus (`release_temp_path` le retire), et appelle d'abord `remove_stale_temp_files(dossier)` : un plantage ou une coupure de courant pendant une écriture laisse un `.~mosaicview_*.tmp` à côté des comics, supprimé à la prochaine écriture dans ce dossier s'il n'appartient à aucune écriture en cours et n'a pas été modifié depuis `STALE_TEMP_AGE` (600 s). Seuls les noms `TEMP_FILE_PREFIX` + `TEMP_FILE_SUFFIX` sont visés ; ménage facultatif, sans erreur s'il échoue. **Tout temporaire écrit à côté d'un fichier de l'utilisateur passe par `make_temp_path`/`release_temp_path`** (aussi `_interruptible_zip_writer` des lots, la recompression et l'import de métadonnées en lot), pour être nettoyé de la même façon. **Jamais `shutil.move` vers un fichier existant** : sous Windows, `os.rename` refuse une destination existante et `shutil.move` bascule alors sur une copie qui tronque l'original avant de le réécrire. Jamais de temporaire dans `%TEMP%` pour un fichier destiné à remplacer un fichier de l'utilisateur : autre volume, donc copie, et `cleanup_all_temp_files` l'effacerait à la fermeture. Testé par `tests/test_utils_atomic_write.py`. **Garde-fou** : `tests/test_check_atomic_file_writes.py` (scan AST de `modules/qt/` et `MosaicView.py`) échoue sur tout `shutil.move`, sur toute écriture `zipfile.ZipFile(..., "w"/"a"/"x")` hors de sa liste d'écrivains autorisés (`ALLOWED_ZIP_WRITERS`, chacun justifié), et sur tout appel à `_write_zip_with_progress` qui ne serait pas dans une fonction ou un lambda passé à `replace_file_atomically`. Une nouvelle écriture de CBZ doit passer par `replace_file_atomically` ; ne l'ajouter à la liste d'exceptions du test qu'avec une justification équivalente.
- **`_register_document_file(parent, callbacks, filepath)`** — à appeler dès que le document du panneau prend un nouveau chemin (`save_as_cbz`, `create_cbz_from_images`, conversions de `_write_apply_new_names`) : ajout aux fichiers récents (`recent_files.add_to_recent_files` + `_sync_recent_menus`) et rafraîchissement du titre de la fenêtre (`callbacks["update_window_title"]`). L'enregistrement du CBZ ouvert (même chemin) n'en a pas besoin.
- **`_write_apply_new_names`** (appelée par `apply_new_names`) a sa propre logique selon l'extension d'origine :
  - **`.cbz`** — remplace le fichier ouvert via les deux étapes ci-dessus.
  - **`.cbr`/`.cb7`/`.cbt`/`.epub`** — demande un nouveau nom de fichier `.cbz` (conversion, l'ancien format ne peut pas être réécrit), propose ensuite de supprimer l'original via `SaveSuccessDialog`.
  - **`.pdf`** — même principe que ci-dessus mais avec ses propres clés de traduction (`cbz_converted_from_pdf.*`).

## Export vers un dossier (`save_selection_to_folder`)

- **Dossier de départ** : réglage `last_export_dir` (`ConfigManager.get/set`, propre à l'export, enregistré à chaque export d'une ou plusieurs pages) s'il existe encore ; sinon dossier du comic, des premières images, puis `last_open_dir`. L'export n'écrit jamais `last_open_dir` : les fenêtres d'ouverture et d'export gardent chacune leur dossier.
- **Une seule page** : boîte native `_get_save_filename`, qui confirme elle-même l'écrasement d'un fichier existant. **Les octets sont écrits tels quels, jamais convertis** (convertir est le rôle de « Convertir », skill `image-format-conversion`) : si l'extension tapée ne désigne pas le format de la page (`archive_names.same_image_format`, qui tient `.jpg`/`.jpeg` ou `.tif`/`.tiff` pour un même format), l'extension de la page est **ajoutée** à la fin, sans rien retirer de ce qui a été tapé (`xxx.png` pour un JPEG → `xxx.png.jpg`). Sans cela, la boîte native permettait d'écrire un JPEG nommé `.png`. La boîte n'a pas porté sur ce nom complété : s'il existe déjà, `ExistingFilesDialog` demande avant de le remplacer.
- **Résolution** : chaque page exportée (une ou plusieurs) passe par `_bytes_with_entry_dpi(entry)`, comme dans un CBZ (voir plus bas) — une page issue d'un PDF porte sa résolution de rendu.
- **Plusieurs pages** : après le choix du dossier, les cibles `(chemin, bytes)` sont figées (la question qui suit est non modale, la sélection peut changer avant la réponse). Si des fichiers de même nom existent déjà, `ExistingFilesDialog` (non modal, `ask_async(on_result)` → `True` remplacer / `False` annuler, liste de 10 noms au plus puis `dialogs.existing_files.more`) pose **une seule question pour tous**. **Tout ou rien** : jamais d'option « exporter seulement les pages au nom libre », qui ferait croire que toutes les pages ont été exportées alors que certaines manquent dans le dossier.
- **`_write_file_safely(path, data)`** écrit chaque fichier par `replace_file_atomically` (temporaire dans le dossier de destination puis `os.replace`) et crée le dossier parent si besoin : un échec en cours d'écriture ne tronque jamais un fichier existant de ce nom.

## `safe_join()` — protection Zip Slip (export multi-fichiers)

`save_selection_to_folder`, quand plusieurs fichiers sont exportés vers un dossier, utilise `safe_join(folder, entry["orig_name"])` (`utils.py`) plutôt qu'un simple `os.path.join`. Un `orig_name` piégé contenant `../` ou un chemin absolu produirait normalement une écriture hors du dossier choisi (vulnérabilité Zip Slip classique sur les archives non fiables) — `safe_join` renvoie `None` dans ce cas, et l'entrée est comptée dans `skipped_count` plutôt qu'écrite. Ce garde-fou ne s'applique **pas** à `_write_zip_with_progress`/`_write_apply_new_names`, qui écrivent dans un ZIP (où `zf.writestr(entry["orig_name"], ...)` ne peut pas s'échapper d'un dossier réel — le risque Zip Slip existe seulement à la **lecture** d'une archive, pas à l'écriture, voir skill `archive-image-loading` pour ce côté-là).

## `_get_save_filename()` — recentrage du dialogue natif Windows

`QFileDialog.getSaveFileName()` est un dialogue natif Windows, donc pas centré sur `parent` par le mécanisme Qt habituel (`_center_on_widget`/`position_dialog_on_parent`, voir règle CLAUDE.md n°5). Ce fichier contourne la limitation avec un thread `ctypes` séparé qui : énumère les fenêtres Windows (`EnumWindows`) à la recherche d'une classe `#32770` (dialogue Windows générique) dont le titre correspond exactement au `title` passé, attend qu'elle devienne visible, puis la repositionne via `SetWindowPos` au centre du `parent`. Fonctionne par **titre de fenêtre exact** — si un autre dialogue Windows partage le même titre au même moment, le mauvais pourrait être déplacé (scénario improbable mais à garder en tête si le recentrage semble aléatoirement rater).

## Dialogues Qt dédiés (tous non-modaux, tous dans ce fichier)

- **`InfoDialogClickablePath`** — info + lien cliquable vers l'emplacement du fichier sauvegardé (ouvre l'Explorateur, voir skill `explorer-select`... en réalité ici un `subprocess.Popen(["explorer", "/select,", ...])` direct dans `_open_file_location`, **pas** `_explorer_select()` — écart à signaler si on unifie un jour, voir "Pièges"). `on_done` optionnel, appelé à la fermeture (`finished`).
- **Thème et police des trois confirmations à lien** (`InfoDialogClickablePath`, `SaveSuccessDialog`, `FileSavedDialog`) — leur `_retranslate()` appelle deux helpers communs : `_apply_confirmation_theme(dialog, text_labels, link_label, link_href, link_text, buttons)` (fond, textes et boutons via `get_current_theme()`, lien en `theme["link"]`) et `_apply_confirmation_font(widgets)` (`get_current_font()` sur les textes traduits et les boutons). Le changement de thème émettant aussi `language_signal`, ces fenêtres suivent thème, langue et police. La couleur du lien est posée **dans la balise `<a style="color:…">`** : celle d'un lien de `QLabel` ne suit pas le stylesheet du label. Le texte du lien est échappé par `html.escape` et garde la police par défaut (c'est un chemin, pas un texte traduit). Toute nouvelle confirmation avec lien de ce fichier doit passer par ces deux helpers plutôt qu'une couleur en dur.
- **`SaveSuccessDialog`** — info + lien cliquable + question Oui/Non ("supprimer l'ancien fichier ?"), résultat via callback `on_done(bool)`.
- **`DuplicateNamesErrorDialog`** — erreur bloquante (OK seulement) pour des doublons de noms détectés tardivement dans `apply_new_names` (différent de `DuplicateFilenameDialog` : ici pas de choix, juste un blocage).
- **`DuplicateFilenameDialog`** — 3 boutons (renuméroter/ignorer/annuler), résultat via `Signal(object)` + `ask_async(on_result)`.
- **`ExistingFilesDialog`** — export de plusieurs pages vers un dossier où des fichiers de même nom existent, ou d'une seule page dont le nom a été complété par son extension et existe déjà : 2 boutons (Remplacer / Annuler), résultat `bool` via `ask_async(on_result)`. Thème, `get_current_font()` et texte réappliqués sur `language_signal` (langue, thème, taille de police) ; titre par `_wt()` ; fermeture par `hide()` + `deleteLater()`, donc `language_signal` déconnecté explicitement dans `_finish`/`closeEvent`.
- **`FileSavedDialog`** / **`ThumbnailSavedDialog`** — confirmation avec lien vers un dossier (export multi-fichiers / export de vignettes — cette dernière semble utilisée ailleurs pour un export de vignettes non couvert par ce skill, à vérifier si une tâche future la concerne).

Tous sont ponctuels (créés à chaque usage, jamais réaffichés) et portent `WA_DeleteOnClose` : détruits à leur fermeture (`close()`, `accept()`, `reject()`), au lieu d'être seulement masqués et de s'accumuler comme enfants du panneau pendant toute la session. Ne jamais garder une référence à l'un d'eux pour s'en resservir après sa fermeture. Tous suivent le pattern standard : `setModal(False)`, connexion/déconnexion de `language_signal.changed` dans `_retranslate`/`_on_close`, centrage via `_center_on_widget` ou `position_dialog_on_parent`.

## Comment modifier

- **Ajouter une nouvelle validation pré-sauvegarde** : écrire une fonction `_ma_validation_qt(parent, ..., on_done)` suivant le pattern `on_done(True/False)`, l'ajouter à la liste passée à `_run_validation_chain` dans `save_as_cbz`/`create_cbz_from_images`/`apply_new_names` (les 3 endroits, pas un seul, si la validation doit s'appliquer partout).
- **Changer le niveau de compression utilisé à la sauvegarde** : ne touche pas ce fichier — voir skill `zip-compression`, `zip_compression_kwargs(comp_level)` est déjà le point de passage central, appelé ici depuis `parent._zip_compression_config().get_zip_compression_level()`.
- **Changer le comportement de suppression de l'ancien fichier** : `_safe_delete()` (fin de fichier) appelle `utils.send_to_trash`, **seule implémentation de la mise à la Corbeille de l'application** (send2trash, repli sur `SHFileOperationW` avec `FOF_ALLOWUNDO`, jamais de suppression définitive à la place ; `OSError` si le fichier n'a pas été déplacé). Garde-fou : `tests/test_check_single_trash.py` échoue sur tout import de send2trash ou appel à `SHFileOperationW` hors d'`utils.py`. Utilisé par `save_as_cbz`/`_write_apply_new_names`, jamais appelé sans confirmation préalable de l'utilisateur (toujours derrière un `SaveSuccessDialog`/`on_done(True)`).
- **Relecture avant suppression de l'original** : avant `_safe_delete(ancien fichier)`, `save_as_cbz` (`_after_save_as`) et les conversions de `_write_apply_new_names` (`_after_cbz_converted`, `_after_pdf_converted`) appellent `verify_written_cbz(nouveau CBZ, written_count)` (`utils.py`) : relecture complète du CBZ écrit (`ZipFile.testzip`, CRC de chaque fichier) et nombre de fichiers égal à `written_count = len(cbz_members(state.images_data))`, compté juste après l'écriture. Échec → `WrittenFileCheckError` (texte `messages.errors.written_file_check_failed`, détail `messages.errors.written_file_count` pour un nombre faux, traduit à chaque `str()`), `ErrorDialog` avec cri de Wilhelm, et **l'original n'est pas supprimé**. Un CBZ abîmé à l'écriture (disque défaillant, support amovible retiré) passerait sinon pour réussi, et l'original, seule copie intacte, partirait à la Corbeille. Toute nouvelle suppression de source après conversion doit passer par cette relecture (voir aussi skills `batch-processing`, `batch-metadata-import`, `library`). Testé par `tests/test_utils_atomic_write.py`.
- **Ajouter un nouveau format source pour `apply_new_names`** (ex. un futur format d'archive) : ajouter une branche `elif ext == ".xxx":` dans `_write_apply_new_names`, suivant le pattern CBR/CB7/CBT/EPUB (demande un nouveau nom `.cbz`, refuse le nom du fichier ouvert lui-même — `_is_conversion_source`, `is_same_path`, message `messages.errors.convert_target_is_source` : il serait écrasé, puis « Supprimer l'original ? » supprimerait le fichier qu'on vient d'écrire —, écrit, propose suppression de l'original via `SaveSuccessDialog`).

## Pièges connus

- **Le texte « Sauvegarde X% » (`_SavingOverlay`) passe par le mécanisme commun** (`show_canvas_text`/`hide_canvas_text`, skill `canvas-overlay-progress`) : `update(percent)` met à jour le texte puis traite les événements (`processEvents`), `remove()` le retire (sans effet s'il l'est déjà). Il s'empile ainsi avec un import ou une numérisation en cours au lieu de les recouvrir. **Piège** : ne jamais le dessiner comme item de la scène de la mosaïque (`QGraphicsTextItem`) — toute reconstruction de la mosaïque pendant les `processEvents` (entrer dans un sous-dossier, changer la taille des vignettes) le détruisait avec les autres items, et l'enregistrement échouait sur « Internal C++ object already deleted ». Le label du mécanisme commun est un widget posé sur le canvas, que cette reconstruction ne touche pas.
- **`_open_file_location` réimplémente l'ouverture Explorateur au lieu de réutiliser `_explorer_select()`** (skill `explorer-select`, qui dit explicitement "toujours réutiliser, jamais réimplémenter un appel explorer /select ad hoc") — cet écart existait déjà dans le code avant la création de ce skill ; à signaler/corriger si une tâche touche ce fichier, mais hors du périmètre d'une simple documentation.
- **Deux dialogues de "doublons" différents** — `DuplicateFilenameDialog` (3 choix, avant sauvegarde normale) et `DuplicateNamesErrorDialog` (blocage simple, dans `apply_new_names` seulement, pour des doublons détectés après application des noms modifiés depuis les `NameEdit`). Ne pas les confondre en cherchant "le" dialogue de doublons de noms.
- **`_finish_apply_new_names` n'est jamais appelée dès l'écriture** — elle est différée jusqu'à la fermeture de la confirmation : `InfoDialogClickablePath` (`on_done`) pour `.cbz`, réponse de `SaveSuccessDialog` pour les conversions CBR/CB7/CBT/EPUB/PDF. Appeler `_done(True)` trop tôt déclencherait la fermeture en cascade des fenêtres liées au comic (« Enregistrer et fermer », skill `file-close`) avant que l'utilisateur ait lu la confirmation ou répondu à la question de suppression. **`create_cbz_from_images` suit la même règle** : `on_complete(True)` n'est émis qu'à la fermeture de « CBZ créé ».
- **Le document a pu changer pendant ces confirmations** — elles sont non modales : l'utilisateur peut supprimer une page, pivoter… entre l'écriture et la fermeture de la confirmation, ou fermer le document (`_close_comic_child_dialogs` referme alors la confirmation, ce qui déclenche sa fin). Juste avant chaque écriture, `_write_apply_new_names` capture `written = (content_snapshot(state), state.doc_generation)` (`undo_redo.py`, skill `undo-redo`) et le passe à `_finish_apply_new_names(state, callbacks, _done, written)`. Celle-ci ne remet `modified` à `False` et n'appelle `mark_history_saved` que si `doc_generation` est inchangé et `content_unchanged(state, snapshot)` ; sinon elle appelle `_done(False)`, ce qui empêche « Enregistrer et fermer » (`_apply_and_close`, skill `file-close`) de fermer un document dont les dernières modifications ne sont pas dans le fichier. `create_cbz_from_images` fait de même : `on_complete` reçoit `unchanged and doc_generation inchangé and content_unchanged(...)`, contenu capturé après l'écriture. Toute nouvelle sauvegarde dont la fin est différée doit suivre ce modèle ; ne pas se fier à `history_top` seul, qu'un renommage ou une modification sans `save_state` ne déplace pas.
- **Le fichier ouvert a pu être réécrit ailleurs** — chaque panneau garde son propre exemplaire du comic en mémoire, et d'autres écrivains peuvent réécrire `current_file` pendant ce temps : l'autre panneau ouvert sur le même fichier (cas légitime, jamais bloqué à l'ouverture), la Bibliothèque (édition du ComicInfo.xml), l'import de métadonnées en lot, un autre programme. `state.disk_signature` (`state.py`) mémorise `file_signature(current_file)` (`utils.py` : date de modification en ns, taille) à la fin du chargement d'archive (`ArchiveLoader._on_finished`, skill `archive-image-loading`) et après chaque écriture qui fait de ce fichier celui du document (`_write_apply_new_names` branche `.cbz` et conversions, `save_as_cbz`, `create_cbz_from_images`) ; il est remis à `None` au début d'un chargement et par `force_close_file` (skill `file-close`). **Avant de réécrire le fichier ouvert** — branche `.cbz` de `_write_apply_new_names`, et `save_as_cbz` quand la destination est le fichier ouvert (`same_file`) — `_confirm_if_changed_on_disk(parent, state, filepath, proceed, cancel)` compare la signature mémorisée à celle du disque : identique ou inconnue → `proceed()` ; différente → `ConfirmYNDialog` non modal `messages.questions.file_changed_on_disk` (« Non » par défaut, positionné avant affichage), puis `proceed()` sur Oui, `cancel()` sur Non ou fermeture (`_done(False)` pour « Enregistrer et fermer », qui ne ferme donc pas), une seule réponse prise en compte. Abandon aussi si `doc_generation` a changé avant la réponse : écrire un document vidé par la fermeture détruirait le fichier. Une écriture vers un **autre** fichier existant n'est pas concernée : la boîte native de `_get_save_filename` confirme déjà l'écrasement. Toute nouvelle écriture qui réécrit `current_file` doit passer par cette vérification et mettre `disk_signature` à jour après coup.
- **Fichier traité par un lot — `_claim_files_for_write(parent, paths)`** : la vérification de signature est faite avant l'écriture, elle ne voit pas un lot (conversion, import des métadonnées en lot) qui réécrit ou supprime le fichier **pendant** l'enregistrement. Chaque écriture du fichier du document réserve donc les fichiers qu'elle lit, remplace ou crée auprès des lots (`batch_claims.BatchClaims.claim`, skill `batch-processing`) le temps de l'écriture, et les libère dans un `finally` (`release_all`) : `_write_and_finish` de `save_as_cbz` (destination et fichier ouvert), `create_cbz_from_images`, et les trois branches de `_write_apply_new_names` (`.cbz` ; destination et source des conversions CBR/CB7/CBT/EPUB et PDF). Un fichier détenu par un lot → `ErrorDialog` `messages.errors.file_in_batch` (`{name}`), rien n'est écrit (`_done(False)` le cas échéant). La Bibliothèque fait de même (`_rewrite_comicinfo_in_cbz`, `_convert_file_to_cbz`, skill `library`). **Piège** : sans réservation, un import de métadonnées qui relit l'ancien fichier pendant l'enregistrement le remplace ensuite par les anciennes pages avec le nouveau ComicInfo.xml, et le panneau, qui a mémorisé `disk_signature` juste après sa propre écriture, se croit enregistré.
- **Enregistrer sous vers le fichier déjà ouvert** — le nom proposé par défaut est exactement le fichier ouvert (même dossier, même nom `.cbz`). `save_as_cbz` le détecte avant l'écriture avec `is_same_path` (`utils.py` : `samefile` si les deux existent, sinon chemins normalisés et `normcase` ; testé par `tests/test_utils_is_same_path.py`) et affiche alors la confirmation simple « Fichier CBZ sauvegardé » au lieu de `SaveSuccessDialog` : sa question « supprimer le fichier d'origine ? » supprimerait le fichier qu'on vient d'écrire. Ne jamais comparer deux chemins par `==` pour décider d'une suppression. **Seulement si le fichier ouvert est un `.cbz`** : un CBR/CB7/CBT/EPUB/PDF choisi comme destination (cas réel : icône « Enregistrer » sur un CBR non modifié, qui lance « Enregistrer sous », puis nom du CBR tapé dans la fenêtre de Windows) serait remplacé par un CBZ qui garde son extension, l'original perdu. `save_as_cbz` le refuse avec `_is_conversion_source` (même message `messages.errors.convert_target_is_source` que les conversions d'`apply_new_names`), juste après le calcul de `same_file`.
- **`mark_history_saved(state)` après chaque sauvegarde réussie** — appelée juste après `state.modified = False` dans `save_as_cbz`, `create_cbz_from_images` et `_finish_apply_new_names`, pour qu'un Annuler après la sauvegarde ramène bien un état « modifié » (skill `undo-redo`). Toute nouvelle fonction qui écrit le document sur disque doit faire de même.
- **`_apply_name_edits(state)` avant toute sauvegarde du document** — appelée par `save_as_cbz`, `create_cbz_from_images` et `apply_new_names`, juste après `_auto_update_page_count_qt` : recopie dans `orig_name` le texte du champ de nom de chaque vignette (`entry["name_entry"]`, widget `NameEdit` de `mosaic_canvas.py`), espaces de bord retirés. `NameEdit._on_text_changed` met déjà `orig_name` à jour à chaque frappe, mais sans retirer ces espaces et en ignorant un champ vide. Un champ vide garde le nom en mémoire (sinon la page s'appellerait `.jpg` dans le CBZ) ; un champ détruit par une reconstruction de la mosaïque (`RuntimeError`) est ignoré. Toute nouvelle sauvegarde du document entier doit l'appeler aussi ; un changement du format de nom se fait dans cette seule fonction.
- **`safe_join` protège uniquement l'export vers un dossier réel**, pas l'écriture dans un ZIP — ne pas supposer qu'il s'agit d'une protection Zip Slip générale utilisée partout dans le fichier.

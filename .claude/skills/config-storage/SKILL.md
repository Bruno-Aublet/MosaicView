# Fichiers de configuration — MosaicView

Stockage persistant de tous les réglages applicatifs, distinct des vrais fichiers temporaires (voir skill `temp-files`). Ne jamais confondre les deux : la config est faite pour survivre indéfiniment entre les sessions, les fichiers temporaires sont jetables et effacés à chaque fermeture.

## Emplacement — `%APPDATA%\MosaicView\`

Deux fichiers y vivent :
- `.mosaicview_config.json` — la config principale (voir `ConfigManager.CONFIG_FILENAME`, [modules/qt/config_manager.py](../../../modules/qt/config_manager.py))
- `.mosaicview_icon_toolbar.json` — config séparée de la barre d'icônes, volontairement non effacée par "reset aux valeurs par défaut" (voir section dédiée plus bas)

Le sous-dossier `errors\` contient le journal des erreurs inattendues (section dédiée plus bas) ; il n'est pas touché par « Effacer le fichier de configuration ».

**Pourquoi pas `%TEMP%`** : Windows purge périodiquement `%TEMP%` (Nettoyage de disque, Storage Sense), ce qui effacerait silencieusement toute la config — y compris les marque-pages — sans avertissement. `%APPDATA%` est fait pour survivre indéfiniment, contrairement à `%TEMP%`.

## Fichier central — `modules/qt/config_manager.py`

Une seule classe, `ConfigManager`, instanciée une fois comme singleton global via `init_config_manager()` / récupérée partout via `get_config_manager()`. Un wrapper, `Panel2Config` (même fichier), redirige certaines méthodes vers des clés `*_panel2` pour ne pas écraser la config de panel1 — voir skill `panels`.

### Construction du chemin et migration — `ConfigManager.__init__`

```python
config_dir = default_config_dir()   # os.path.join(os.environ["APPDATA"], "MosaicView")
```

`default_config_dir()` (même module) est la seule définition de ce dossier : le journal des erreurs (`error_log.log_dir`) l'utilise aussi, sans instancier `ConfigManager`. Créé avec `os.makedirs(exist_ok=True)` si absent. **Avant** le premier `load_config()`, `_migrate_from_temp()` s'exécute :

- Ne fait rien si `.mosaicview_config.json` existe déjà dans `%APPDATA%\MosaicView\` (migration déjà faite, ou nouvelle installation).
- Sinon, **déplace** (`shutil.move`, pas copie) `.mosaicview_config.json` et `.mosaicview_icon_toolbar.json` depuis `%TEMP%\MosaicViewTemp\` s'ils y existent encore.
- Silencieuse (`except Exception: pass`) — une migration ratée ne doit jamais empêcher le démarrage de l'application ; dans le pire cas, l'utilisateur repart avec une config par défaut.

**Piège pour toute modification touchant ce chemin** : ne jamais coder en dur `os.path.join(tempfile.gettempdir(), "MosaicViewTemp")` pour la config — cet emplacement est réservé aux vrais fichiers temporaires (skill `temp-files`). Toujours passer par `get_config_manager().config_dir` / `get_config_manager().get_config_file_path()`, jamais reconstruire le chemin à la main dans un nouveau call site.

### Lecture/écriture

`load_config()` fusionne le JSON chargé avec `DEFAULT_CONFIG` (une clé absente du fichier existant retombe sur sa valeur par défaut, pas d'erreur — permet d'ajouter de nouvelles clés sans migration explicite). `save_config()` réécrit le fichier entier à chaque `set()`, par **`write_json_atomically(path, data)`** (fonction de module de `config_manager.py`, bibliothèque standard seule : ce module est chargé sans Qt) : le JSON complet va dans un temporaire `.~mosaicview_*.tmp` du même dossier, forcé sur le disque (`fsync`), qui remplace le fichier d'un coup (`os.replace`) ; en cas d'échec, temporaire supprimé, fichier intact, exception relancée (`save_config` retourne alors `False`, après avoir passé l'exception à **`ConfigManager.save_failed_handler`** s'il est posé). **Échec signalé à l'utilisateur** : `MainWindow.__init__` (`MosaicView.py`) pose ce handler, qui émet le signal `_ConfigSaveRelay.failed` (`save_config` peut être appelée depuis un thread de travail) ; `MainWindow._on_config_save_failed` affiche un seul `ErrorDialog` par session (`messages.errors.config_save_failed`, raison par `str(e)` ou le nom du type) — marque-pages, récents et réglages changés pendant la session seraient perdus à la fermeture, et `save_config` est appelée très souvent (taille de fenêtre…). Testé par `tests/test_audit7_p3.py`. **Ne jamais réécrire un fichier de configuration par `open(path, 'w')`** : l'ouverture le vide aussitôt, et un plantage, une coupure de courant ou un disque plein pendant l'écriture laisse un JSON illisible — `load_config` repart alors des valeurs par défaut et tout est perdu (récents, marque-pages, clé API). Coût mesuré : quelques millisecondes par écriture. Utilisée aussi par `_write_icon_toolbar_config` et `macro_engine.save_macro` (skill `macro-tool`). Testé par `tests/test_config_manager.py`. Tous les getters/setters typés (`get_dark_mode()`, `set_window_size()`, `get_bookmark()`, `set_comicvine_api_key()`...) passent par ce dict interne — **ne jamais lire/écrire `cfg.config['xxx']` directement** depuis un autre module, toujours utiliser un getter/setter dédié ou en ajouter un.

### Clé API ComicVine — chiffrement DPAPI

`get_comicvine_api_key()` / `set_comicvine_api_key()` chiffrent/déchiffrent via `win32crypt.CryptProtectData`/`CryptUnprotectData` (DPAPI Windows, liée au compte utilisateur — illisible sur une autre machine ou un autre compte). Migration automatique et silencieuse d'une éventuelle ancienne valeur en clair au premier `get()`. `set_comicvine_api_key` rend `False` sans rien modifier si le chiffrement échoue (`_dpapi_encrypt` rend `''`) — sinon une clé vide serait enregistrée à la place de la clé saisie —, et `False` aussi si l'écriture échoue ; la fenêtre de la clé (`comicvine_apikey_dialog_qt._ApiKeyDialog._on_validate`/`_on_clear`) lit ce retour et affiche alors `comicvine.api_key_dialog.error_save`, fenêtre ouverte (skill `comicvine-metadata-fetch`). Voir skill `comicvine-metadata-fetch` pour l'usage de cette clé.

### Config icon-toolbar — fichier séparé

`_icon_toolbar_config_file` (attribut de `ConfigManager`) vit dans le même dossier mais dans un fichier JSON à part, lu/écrit par `_read_icon_toolbar_config()`/`_write_icon_toolbar_config()`. Voir skill `icon-toolbar` pour ce qu'il contient et pourquoi il est séparé de `reset_to_defaults()`.

## Journal des erreurs — `%APPDATA%\MosaicView\errors\errors.log`

Garde la trace des erreurs : exception Python non interceptée (y compris dans un slot Qt ou un thread), erreur rattrapée et affichée par `ErrorDialog`, plantage natif (Qt, Pillow, 7-Zip, MuPDF). Actif dans l'exécutable comme en mode développement : l'exe n'a pas de console (`console=False` dans les `.spec`, `sys.stderr` vaut `None`), une telle erreur n'y laisserait aucune trace ; depuis les sources, la trace du terminal est noyée parmi les prints et perdue à la fermeture.

### Partie sans Qt — [modules/qt/error_log.py](../../../modules/qt/error_log.py)

- **Un seul fichier**, `log_path()` = `log_dir()` (`default_config_dir()` + `errors`) + `LOG_NAME` (`errors.log`). On n'y écrit que lorsqu'une erreur se produit : un démarrage sans erreur n'écrit rien. Chaque entrée commence par une ligne `===== <date et heure à la milliseconde> — MosaicView <version> — <processus N> — <nature> =====` (`_HEADER_RE`, qui sert aussi à découper le fichier : `split_entries` ; heure écrite par `_milliseconds`). `_HEADER_RE` accepte aussi l'en-tête sans millisecondes des entrées plus anciennes : un changement de format d'en-tête doit toujours rester lisible par cette expression, sinon les anciennes entrées disparaîtraient de la fenêtre, du ménage et du mail.
- **`append_entry(title, body, …)`** : écrit une entrée sous le verrou, la force sur le disque (`flush` + `os.fsync` : la fin du process peut être brutale) et fait le ménage si le fichier dépasse `MAX_BYTES`. Ne lève jamais.
  - **Configuration en deuxième ligne** de chaque entrée, juste sous l'en-tête (`_environment_line`, titre `error_log.entry.environment` : Windows `platform.platform()`, versions de Python, PySide6, Pillow, `MosaicView.exe` ou `.py`). Les valeurs sont calculées une fois par process (`_environment_values`), le texte est traduit à chaque écriture. Le mail reprend les entrées, donc la configuration.
  - **Dernières actions** (bloc « Dernières actions : », entre le message de la fenêtre et la pile) : `record_action(key, panel=None, **params)` garde en mémoire les `TRAIL_SIZE` (20) dernières actions importantes du process (`_trail`, `collections.deque` sous `_trail_lock`). Rien n'est écrit sur le disque sans erreur. `_trail_text()` les rend à l'écriture d'une entrée : heure à la milliseconde, `panneau N —` si connu, texte `error_log.trail.<key>` traduit par `_text`, paramètres aux caractères de contrôle échappés (`_visible`). Le bloc est joint aux entrées complètes de `_Journal.write_error`, de `log_qt_message` et de `log_forced_exit`, pas aux entrées « répétée N fois » ; il est vide dans un process enfant.
    - Points d'enregistrement : `PanelWidget._load_files` (`open`/`add`, nom par `describe_paths`) ; `file_close_qt.force_close_file` (`close`) ; `file_operations_qt._write_cbz_with_overlay` (`save`) ; `save_selection_to_folder` (`export`) ; `BatchClaims.start` (`batch`) ; `AppState.begin_operation`/`end_operation` (`operation_start`/`operation_end`, classe du worker). Le panneau vient de `AppState.panel_number` (1 ou 2, posé par `PanelWidget` ; `None` ailleurs).
    - **Ajouter une action** : une clé `error_log.trail.<key>` (paramètres nommés), puis `record_action("<key>", state.panel_number, …)` par un import local à l'endroit où elle a lieu. On n'enregistre que des actions qui situent une erreur (fichier, panneau, opération), jamais des événements fréquents (survol, rafraîchissement) qui chasseraient les autres du fil.
    - **Limite** : le fil est en mémoire, il est perdu avec le process lors d'un plantage natif (seule la trace de `faulthandler` reste).
  - **Corps nettoyé** (`_clean_body`, pour toute entrée, fichiers de secours compris) :
    - **Chemins** (`_shorten_paths`) : le dossier de l'exe (`sys._MEIPASS`) devient `<MosaicView>`, le dossier du profil `%USERPROFILE%`. Les formes longue, courte 8.3 (`_short_path`) et à barres obliques sont toutes remplacées, sans tenir compte de la casse ; les motifs sont calculés une fois (`_path_names`). Le nom du compte Windows, souvent le nom réel de l'utilisateur, ne part pas dans le mail ; les noms de fichiers restent, car ils servent au diagnostic.
    - **Secrets** (`_redact`, `_SECRET_RE` : `api_key=`, `apikey=`, `access_token=`, `token=`, `password=` → `***`). Le journal est envoyé par mail, et une exception réseau chaînée (`comicvine_scraper._get_json` : `raise … from last_exc`) garde dans sa cause l'URL appelée, clé ComicVine comprise. Un nouveau secret passé dans une URL s'ajoute à `_SECRET_RE`.
    - **Taille** : au-delà de `MAX_ENTRY_CHARS`, le milieu est remplacé par `[… N …]`. Une entrée plus grosse que `PRUNE_TARGET_BYTES` serait retirée par le ménage aussitôt écrite, et tout le journal avec elle.
    - **Fausse entrée** : une ligne qui commence par `=====` est décalée d'une espace (`_FAKE_HEADER_RE`). Un nom de fichier ou un message extérieur créerait sinon une entrée à la date de son choix.
  - **Pas d'écriture imbriquée** : une entrée demandée pendant une écriture du même thread est abandonnée (drapeau `_writing`, `threading.local`). Un `__del__` appelé par le ramasse-miettes pendant l'écriture passe par `sys.unraisablehook` ; `_lock` n'étant pas réentrant, l'écriture imbriquée attendrait indéfiniment.
- **Verrou entre process** (`_FileLock`) : `msvcrt.locking` sur `errors.lock`, plus un `threading.Lock` pour les threads du process. Deux MosaicView ouverts et les process PDF écrivent dans le même fichier ; toute lecture ou écriture se fait sous le verrou, et seul son détenteur ouvre le journal — ce qui permet au ménage de le remplacer d'un coup (temporaire puis `os.replace`) sans jamais le tronquer. Testé avec deux vrais process. Attente du verrou : `MAIN_THREAD_LOCK_TIMEOUT` (2 s) depuis le thread principal, pour ne pas figer les deux panneaux si un autre process le garde ; `LOCK_TIMEOUT` (10 s) ailleurs. Au-delà, l'entrée est abandonnée.
- **Limites** : `MAX_AGE_DAYS = 15`, `MAX_BYTES = 5 Mo`. `prune()` (au démarrage) retire les entrées trop vieilles ; au-delà de `MAX_BYTES`, les plus anciennes sont retirées jusqu'à `PRUNE_TARGET_BYTES` (80 %), marge qui évite un ménage à chaque écriture suivante.
- **Textes jamais en alphabet pIqaD ou tengwar** : le journal est lu dans le Bloc-notes ou un mail. En-têtes par `_text()` (`_wt()` ; clés `error_log.entry.*`) ; trace mise en forme sous `localization.latin_texts()`, qui fait de même pour un message d'exception traduit (`FileInUseError`…). Traces Python en anglais. Avant le chargement des traductions, un en-tête porte le nom de sa clé.
- **Crochets** (`make_excepthook`, `make_thread_excepthook`, `make_unraisablehook`, `_Journal.write_error`) : écrivent la trace puis appellent le crochet précédent, donc la trace s'affiche toujours aussi dans le terminal en mode développement (choix assumé). `KeyboardInterrupt` et `SystemExit` ne sont pas journalisés. `sys.unraisablehook` reçoit les exceptions que Python ne peut pas lever (`__del__`, callback de weakref, fermeture d'un générateur) : sans lui, elles ne vont que sur `sys.stderr`, qui vaut `None` dans l'exe.
- **Erreur répétée** : `_Journal.write_error` compte les occurrences de chaque erreur (`_occurrence` : type et suite des `(fichier, fonction, ligne)` de la pile, par process). Elle n'écrit l'entrée complète que les `MAX_REPEATS` premières fois. Ensuite, à chaque palier de `REPEAT_MARKS`, elle écrit seulement la ligne de l'exception, sous le titre `error_log.entry.repeated` ; entre deux paliers, rien. Une erreur levée à chaque rafraîchissement (peinture, minuteur) figerait sinon l'interface et chasserait du journal la première erreur, souvent la cause. Tous les chemins d'écriture d'une erreur passent par `write_error`. Un test qui lève plusieurs fois la même erreur remet `_occurrences` à zéro.
- **Erreurs signalées à l'utilisateur** : `log_handled_error(exc, title=None, message=None)` écrit la pile d'une erreur rattrapée, précédée du titre et du message de la fenêtre (texte ou fonction `() -> str`, résolus par `_dialog_text` sous `latin_texts()`). Elle ne fait rien tant que le journal n'est pas en place. `dialogs_qt.ErrorDialog.__init__` l'appelle avec `sys.exc_info()[1]`, son titre et son message : ouverte dans un bloc `except`, une fenêtre d'erreur laisse sa pile au journal ; ouverte depuis le slot d'un worker (exception déjà terminée), elle n'écrit rien — c'est au worker de l'avoir fait (point suivant).
- **Erreur rattrapée loin de sa fenêtre** : une exception transmise en texte (`self.error.emit(str(e))` d'un worker, `out_queue.send(('error', …))` d'un process PDF, ligne ajoutée à la liste d'erreurs d'un lot ou d'un chargement) perd sa pile. Le `except` l'écrit lui-même, là où l'exception existe encore, **avant** l'envoi :
  - `log_if_unexpected(exc, title_key="error_log.entry.handled")` : cas normal. N'écrit rien pour une erreur attendue (`is_expected_error` : `OSError`, `EOFError`, `MemoryError` ; classe d'un module de `_EXPECTED_MODULES` — zipfile, tarfile, PIL, rarfile, py7zr, fitz/pymupdf, requests, urllib3 —, reconnue par le nom du module, sans l'importer : PyMuPDF ne se charge jamais dans l'application ; exception du projet qui déclare `expected_error = True` : `ComicVineNetworkError`, `pdf_unlock_qt._ProbeFailed`, `AlteredMemberError`, `archive_names.ArchiveRefusedError`/`ArchiveToolError` (refus des lecteurs d'archive, sous-classes de `ValueError`/`RuntimeError`), `FileTooLargeError`, `ScanError`, `DownloadTooLargeError`, `MissingPageDataError`, `batch_dialogs_qt._IncompleteCbz`). Un défaut du programme (`KeyError`, `TypeError`…) est écrit. Dans une boucle par élément (fichier d'un lot, membre d'archive, page), c'est ce qui sépare un fichier abîmé, qui n'a pas de pile utile, d'un défaut répété sur chaque fichier.
  - `log_exception(exc, title_key)` : écrit toujours. Pour un `except` qui ne rattrape que des défauts du programme (ajouts différés d'`AppState.end_operation`, étape de macro : titre `error_log.entry.caught`). Remplace `traceback.print_exc()`, perdu dans l'exe.
  - Les deux affichent aussi la pile dans le terminal, même sans journal en place.
  - Une nouvelle exception du projet qui signale un cas normal (fichier refusé, réponse d'un service) déclare `expected_error = True`.
  - Aides qui écrivent au journal en même temps qu'elles mettent l'erreur en texte : `batch_dialogs_qt._failure_text` (lignes des journaux de lot), `archive_loader._archive_read_error` et `ArchiveLoader._emit_read_error`, `pdf_loading_qt._send_request_error` et `_send_page_error`.
  - Garde-fous (`tests/test_error_log_capture.py`) :
    - tout `except` large de `modules/qt/` qui transmet l'exception par `.emit`, `.send` ou `.append` appelle `log_exception`, `log_if_unexpected` ou `log_handled_error`, directement ou par une fonction du module qui en appelle une. Les exemptions (`_NOT_LOGGED`) sont justifiées une à une : seul `scan_wia._log_item_properties`, un relevé de diagnostic ;
    - aucun `print_exc`/`print_exception` hors `error_log.py` ;
    - les exceptions du projet listées ci-dessus déclarent `expected_error = True`.
- **Plantages natifs — fichiers de secours** : `faulthandler` exige un fichier ouvert à l'avance, où il écrit sans en-tête possible. Chaque process ouvre donc un fichier caché `.crash_<app|pdf>_<pid>_<version>.tmp` (`_open_crash_buffer`), supprimé à sa fermeture normale (`atexit`). `collect_crash_buffers()` verse la trace d'un fichier resté dans le journal, avec l'en-tête « plantage de l'application » ou « plantage du moteur PDF » (date du plantage = date du fichier), puis le supprime ; vide, il est seulement supprimé ; encore ouvert par un process vivant, Windows refuse sa suppression et il est laissé. Ramassage : par `MosaicView.main` juste après la création de la fenêtre principale (traductions chargées), par `pdf_loading_qt._stopped` dès qu'un process PDF est vu mort, et à la fermeture (`atexit`).
- **Process enfants (moteur PDF)** — trois éléments, à reprendre pour tout nouveau process enfant :
  - `start_child_crash_log()` en tête de `pdf_loading_qt._pdf_persistent_process` et `pdf_probe._probe_process` : fichier de secours de `faulthandler`, et journal du process (`_journal`), qui permet à `log_if_unexpected` d'y écrire directement (`pdf_loading_qt._send_request_error`, `except` de `_probe_process` ; titre `error_log.entry.pdf_error`). Version reçue par la variable d'environnement `MOSAICVIEW_VERSION`, posée par `start()`.
  - Décorateur `@logged_child_process` sur la fonction du process : une exception qui en sort est écrite (`error_log.entry.pdf_uncaught`) puis relancée. **Piège** : `multiprocessing` rattrape lui-même cette exception (`BaseProcess._bootstrap`) et l'écrit sur la sortie d'erreur du process ; `sys.excepthook` n'est jamais appelé dans un process enfant, un crochet n'y servirait à rien. Le décorateur garde le nom de la fonction (`functools.wraps`), par lequel `multiprocessing` la retrouve ; les garde-fous qui repèrent ces fonctions par leur nom restent valables.
  - `pass_titles_to_children()` juste avant le lancement (`pdf_loading_qt._spawn_pdf_process`, `PdfProbe._ensure_process`) : un process enfant n'a pas de traductions chargées. Les titres de ses entrées (`_CHILD_TITLE_KEYS`), traduits par `_wt()` dans la langue du moment, lui sont transmis par la variable d'environnement `MOSAICVIEW_LOG_TITLES`, que `_text()` lit quand les traductions manquent (sinon : nom de la clé). Un nouveau titre écrit par un process enfant s'ajoute à `_CHILD_TITLE_KEYS`.
- **`start(version)`** : appelée une seule fois par `MosaicView.main`, juste après `try_forward_to_running_instance` (une seconde instance, qui se ferme aussitôt, n'y touche pas). Supprime les fichiers `errors_*.log` (un journal par session : ils ne sont plus lus), fait le ménage, ouvre le fichier de secours, installe `sys.excepthook`, `threading.excepthook` et `sys.unraisablehook`. En cas d'échec, rend `None` et l'application démarre sans journal.
- **Messages de Qt** : juste après `start()`, `MosaicView._install_qt_message_handler()` pose un gestionnaire `qInstallMessageHandler`. Les messages `critical` et `fatal` vont à `error_log.log_qt_message` (titre `error_log.entry.qt_message`, même limite de répétitions que les erreurs) ; les avertissements sont trop bavards pour le journal. Tous gardent leur destination habituelle (gestionnaire précédent, sinon sortie d'erreur). Pour un `qFatal` (« QThread: Destroyed while thread is still running »), `faulthandler` ne garde que la pile Python, et ce texte est la seule indication de la cause ; il est écrit avant le retour, Qt arrêtant le process juste après. La conversion des types Qt reste dans `MosaicView.py` : `error_log` est sans Qt.
- **Fermeture forcée** : si des workers tournent encore après `stop_running_qthreads`, `main` écrit leurs classes (`utils.running_qthread_names`) par `error_log.log_forced_exit` (titre `error_log.entry.forced_exit`) avant `os._exit`.
- **Lecture** : `read_log_text(folder, newest_first=True, since=None, max_bytes=None)` rend `(texte, nombre d'entrées omises)`, de l'erreur la plus récente à la plus ancienne ; `existing_log_path()` (le journal s'il contient une erreur, pour le sélectionner dans l'Explorateur).

### Fenêtre — [modules/qt/error_log_dialog_qt.py](../../../modules/qt/error_log_dialog_qt.py)

- **`show_error_log(parent)`** : ouvre `_ErrorLogDialog` (une seule à la fois, relue et ramenée au premier plan si elle est déjà ouverte), ou un `InfoDialog` « aucune erreur » (`error_log.no_errors`) si le journal est vide. Appelée par le callback `show_error_log` (`menubar_callbacks_qt.py`), consommé par le menu « À propos » de la barre de menus et du menu contextuel du canvas vide (skill `menu-bar`), et par le bouton « Ouvrir le journal d'erreurs » du mode d'emploi (skill `user-guide`).
- **Contenu** : `read_log_text()` en lecture seule dans un `QPlainTextEdit`, en Consolas (exception assumée à `get_current_font()` : trace technique, alignée en colonnes) ; au-dessus, le dossier du journal, cliquable (Explorateur, journal sélectionné) ; sous le texte, l'avertissement `error_log.privacy_note` (`_privacy_lbl`, gras et italique, couleur de texte du thème : le journal peut contenir des noms de fichiers et de dossiers, à relire avant l'envoi) ; boutons Copier / Envoyer / Fermer.
- **`send_error_log_by_mail(parent)`** : copie `mail_content()` dans le presse-papiers puis ouvre `mailto:` avec la consigne de collage `error_log.mail_body_hint` (par `_wt()`), sur le modèle de `scan_dialog_qt._send_scan_log_by_mail` — un lien `mailto:` ne peut pas joindre de fichier. `mail_content()` ne garde que les erreurs des `MAIL_DAYS` (7) derniers jours, au plus `MAIL_MAX_BYTES` (500 Ko) — le journal peut atteindre 5 Mo, trop lourd à coller dans un mail — et, s'il en a laissé, commence par `error_log.mail_partial` (chemin du journal complet).
- **Mode d'emploi** : paragraphe `help.config_error_log_note`, suivi de `error_log.privacy_note`, et ses deux boutons dans la section « Fichiers temporaires » (`_build_config_section`, `_error_log_note_html`, skill `user-guide`) ; le journal n'est pourtant pas un fichier temporaire (skill `temp-files`).

### Pièges

- **Ne jamais réassigner `sys.excepthook` / `threading.excepthook` / `sys.unraisablehook`, ni rappeler `faulthandler.enable` ou `qInstallMessageHandler` après `start()`** : le journal ne recevrait plus rien. L'appel `faulthandler.enable()` vers le terminal au tout début de `main` est voulu : il couvre le démarrage avant l'ouverture du journal, et `start()` le redirige vers le fichier.
- **Ne pas lire `sys.stderr` pour décider d'activer le journal** : il vaut `None` dans l'exe, justement là où le journal est indispensable.
- **Signal de langue de la fenêtre débranché une seule fois** (`_disconnect_language`, qui retire le gestionnaire de `_lang_link`) : `closeEvent`, `finished` et `destroyed` y mènent tous, et un second `disconnect` fait afficher un `RuntimeWarning` par PySide (pas une exception, donc pas rattrapé par `try/except`).
- **Fenêtre détruite avec son parent** : ouverte depuis le mode d'emploi, elle est détruite à sa fermeture sans passer par `closeEvent` ni `finished` — d'où le branchement sur `destroyed` et le contrôle `shiboken6.isValid(_dialog)` dans `show_error_log`.

### Modifier

- Limites : les constantes en tête d'`error_log.py` (`MAX_AGE_DAYS`, `MAX_BYTES`, `PRUNE_TARGET_BYTES`, `MAX_ENTRY_CHARS`, `MAX_REPEATS`, `REPEAT_MARKS`, `LOCK_TIMEOUT`, `MAIN_THREAD_LOCK_TIMEOUT`, `TRAIL_SIZE`) ; pour l'envoi, `MAIL_DAYS` et `MAIL_MAX_BYTES` d'`error_log_dialog_qt.py`.
- Nouvelle nature d'entrée : une clé `error_log.entry.<nom>`, passée par `_text()` (titre écrit par un process enfant : l'ajouter aussi à `_CHILD_TITLE_KEYS`).
- Contenu affiché : `read_log_text()` ; envoyé : `mail_content()`.
- Tests : `tests/test_error_log.py` (en-tête, crochets, ménage par âge et par taille, threads et vrais process en même temps, fichiers de secours, aucun caractère pIqaD dans le journal, contenu du mail), `tests/test_error_log_capture.py` (erreurs rattrapées depuis un thread et un vrai process enfant, tri attendu / inattendu, secrets masqués, chemins du profil et de l'exe, erreurs répétées, message de la fenêtre, entrée géante, fausse entrée, configuration en deuxième ligne, dernières actions, heures à la milliseconde et anciennes entrées, messages de Qt, fermeture forcée, attente du verrou, `unraisablehook`, écriture imbriquée, titres transmis aux process enfants, garde-fous ci-dessus) et `tests/test_audit7_p3.py` (erreur signalée, appels présents), sans Qt. Toute la suite tourne avec `APPDATA` redirigé vers un dossier temporaire (`tests/conftest.py`, process démarrés par les tests compris) : configuration et journal n'y touchent jamais le vrai `%APPDATA%\MosaicView` (garde-fou `tests/test_check_tests_isolated.py`) — un test ne contourne jamais cette redirection.

## Ajouter un nouveau réglage persistant

1. Ajouter une entrée dans `ConfigManager.DEFAULT_CONFIG` avec sa valeur par défaut.
2. Ajouter un getter/setter typé dédié (suivre le pattern existant, ex. `get_thumbnail_size()`/`set_thumbnail_size()`), pas un accès direct au dict.
3. Si le réglage doit être restauré au démarrage ou remis à zéro par « Réinitialiser l'application » : voir skill `session-restore`.
4. Si le réglage doit avoir un équivalent séparé pour panel2 : ajouter la clé `*_panel2` correspondante + son relais dans `Panel2Config` (voir skill `panels`). Exemple : `bookmarks_enabled` / `bookmarks_enabled_panel2`, lus par `PanelWidget._bookmarks_config()` (skill `bookmarks`).

## Effacer/ouvrir le fichier de config — points d'entrée UI

- **Effacer** : `PanelWidget._clear_config_file()` ([modules/qt/panel_widget.py](../../../modules/qt/panel_widget.py)) — met `get_config_manager().get_config_file_path()` à la Corbeille si présent ; succès ou échec affiché par `PanelWidget._show_clear_result` (échec : `help.config_config_not_cleared` avec la raison, jamais « effacé avec succès »). L'application garde sa configuration en mémoire et la réécrit au prochain réglage modifié et à la fermeture (comportement voulu). Lit le chemin dynamiquement, donc suit automatiquement tout changement d'emplacement futur sans modification de code.
- **Ouvrir le dossier** : `PanelWidget._open_config_folder()` — `subprocess.Popen(["explorer", get_config_manager().config_dir])`.
- Les deux sont câblés dans `menubar_callbacks_qt.py` (clés `clear_config_file`/`open_config_folder`), consommés par la barre de menus ([modules/qt/menubar_qt.py](../../../modules/qt/menubar_qt.py), section "À propos") et le menu contextuel ([modules/qt/context_menus_qt.py](../../../modules/qt/context_menus_qt.py)) — regroupés ensemble, séparés par un `addSeparator()` des commandes de fichiers temporaires.
- **Mode d'emploi** : section dédiée "Fichiers de configuration" (clé `help.config_dir`/`help.config_dir_content`), juste avant la section "Fichiers temporaires" (`help.config_files`). Builder : `_HelpDialog._build_config_dir_section()` ([modules/qt/user_guide_qt.py](../../../modules/qt/user_guide_qt.py)), retraduction : `_retranslate_config_dir_section()`. Cette section contient aussi les notes single-instance et registre Windows (`config_single_instance_note`/`config_registry_note`) : elles décrivent un comportement au démarrage lié à l'identité de l'application, pas des fichiers temporaires, et n'ont donc pas leur place dans la section "Fichiers temporaires".

## Référencements croisés

- **`session-restore`** — lit/écrit la config via `ConfigManager` pour restaurer la fenêtre au démarrage, et `reset_to_defaults` qui remet une partie des réglages à leur valeur par défaut.
- **`temp-files`** — les vrais fichiers temporaires, dans `%TEMP%\MosaicViewTemp\`.
- **`bookmarks`** — les marque-pages (`get_bookmark()`/`set_bookmark()`, dict commun aux deux panneaux) et le mode marque-pages on/off (`bookmarks_enabled` / `bookmarks_enabled_panel2`, un par panneau) sont stockés dans la config.
- **`comicvine-metadata-fetch`** — utilise `get_comicvine_api_key()`/`set_comicvine_api_key()`.
- **`recent-items`** — `recent_files.py`/`recent_dbs.py` sont de simples façades autour des getters/setters `get_recent_files()`/`get_recent_dbs()` etc. de `ConfigManager` ; toute la logique de nettoyage (`clean_recent_files`/`clean_recent_dbs`) vit ici, pas dans les deux modules façade.
- **`icon-toolbar`** — le fichier de config séparé de la barre d'icônes.
- **`panels`** — `Panel2Config`, réglages dédoublés par panneau.
- **`user-guide`** — la section "Fichiers de configuration" du mode d'emploi, et le paragraphe du journal des erreurs dans la section "Fichiers temporaires".
- **`menu-bar`** — l'entrée « Ouvrir le journal d'erreurs » du menu « À propos ».

## Pièges connus

- **Ne jamais coder en dur `%TEMP%\MosaicViewTemp` pour un besoin de config** — ce dossier est purgé par Windows ; toujours `get_config_manager().config_dir`.
- **`_migrate_from_temp()` déplace, ne copie pas** — après une migration réussie, l'ancien fichier dans `%TEMP%` n'existe plus. Ne pas s'étonner de son absence lors d'un debug.
- **Le nettoyage `cleanup_all_temp_files()`** (skill `temp-files`) ne contient aucune exclusion pour `.mosaicview_config.json` : le fichier n'est pas dans le dossier balayé. N'y en ajouter une que si la config revenait dans ce dossier, ce qui est à proscrire.
- **Réglage par panneau : ne jamais le lire via `get_config_manager()` en dur** — la méthode de `ConfigManager` ne renvoie que la valeur de panel1. Passer par l'objet config du panneau (`_renumber_config()`, `_zip_compression_config()`, `_bookmarks_config()`…).

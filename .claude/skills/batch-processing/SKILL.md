# Traitements par lot (batch) — MosaicView

Sept traitements qui parcourent un **dossier entier** (récursivement) et agissent sur chaque fichier trouvé, avec confirmation → progression → résumé. Deux points d'entrée : le menu **Fichier > Batch**, et le **drag & drop d'un dossier** sur l'application.

## Les trois fichiers

| Fichier | Rôle |
|---|---|
| `modules/qt/batch_dialogs_qt.py` (~2940 lignes) | Conversions CBR/CB7/CBT/PDF/IMG → CBZ, et recompression ZIP en lot. Le plus gros fichier, très répétitif (5 flux de conversion quasi identiques). |
| `modules/qt/batch_metadata_dialog_qt.py` | Import de métadonnées ComicVine en lot (orchestre l'ouverture séquentielle de la fenêtre ComicVine pour chaque fichier). |
| `modules/qt/batch_drop_dialog_qt.py` | Fenêtre de choix du traitement (`BatchDropDialog`) affichée uniquement quand le déclencheur est un drop de dossier(s) — pas depuis le menu, où le type est déjà choisi par l'entrée de menu cliquée. |

Un huitième traitement (**Bibliothèque**) ne vit pas dans ces fichiers : il ouvre `LibraryWindow` avec un `NewDbDialog` pré-rempli — voir skill `library`.

## Les deux points d'entrée

### 1. Menu Fichier > Batch (`menubar_qt.py` : sous-menu `batch_menu` de `_populate_file_menu` ; `buttons.batch_metadata` dans `_populate_metadata_menu`)

Chaque entrée de menu appelle directement une méthode `PanelWidget._batch_convert_*` (`panel_widget.py`) qui demande le dossier (`QFileDialog.getExistingDirectory`) puis lance directement le bon flux — pas de passage par `BatchDropDialog`, le choix est déjà fait par l'entrée de menu cliquée.

```
menubar_qt.py → callbacks["batch_convert_cbr_to_cbz"] → mw._batch_convert_cbr_to_cbz()
              → PanelWidget._batch_convert_cbr_to_cbz → _qt_batch_cbr(self, self._get_batch_callbacks())
              → batch_dialogs_qt.batch_convert_cbr_to_cbz(parent, callbacks, directory=None)
```

`batch_metadata` (menu) appelle `PanelWidget._batch_metadata()`, qui gère lui-même la sélection de dossier avant d'appeler `show_batch_metadata_dialog` ; un dossier sans CBZ/CBR/CB7/CBT/PDF affiche `ErrorDialog` (clés `dialogs.batch_metadata.no_files_title`/`_message`, les mêmes que `_make_batch_metadata` du drop).

### 2. Drag & drop d'un dossier (`drop_handler_qt.py`)

Point d'entrée unique : `handle_dropped_paths(parent, paths, load_files_callback, batch_callbacks, from_drop)`.
- Sépare `paths` en `dirs`/`files`. Si mélange dossiers+fichiers → message d'erreur, rien ne se passe.
- Si un ou plusieurs dossiers → `_show_batch_drop_dialog(parent, dirs, batch_callbacks)`, qui affiche `BatchDropDialog` (choix radio parmi les 8 traitements) puis, une fois choisi, scanne `dirs` (tous les dossiers droppés en une passe, récursivement) et appelle le flux correspondant avec `directories=dirs` (pour l'affichage des liens dans le résumé — plusieurs dossiers possibles ici, contrairement au menu qui n'en a qu'un).
- Si des fichiers seuls (pas de dossier) → passe directement à `load_files_callback` (ouverture normale, pas de batch).
- **Piège** : les imports de `_show_batch_drop_dialog` sont locaux à la fonction ; un nom supprimé ou renommé dans `batch_dialogs_qt.py` lève une `ImportError` au drop, avalée par Qt — le drop de dossier ne fait alors plus rien, sans message (skill `drag-and-drop`, flux 4).

**Différence clé menu vs drop** : le menu ouvre un seul dossier choisi via dialogue (`directory` singulier, `directories=None`), le drop peut agrafer plusieurs dossiers déposés simultanément (`directories=[...]`, affichés comme liens multiples dans le résumé via `_add_dir_links`).

## Le dict `batch_callbacks` — contrat obligatoire

Toute fonction `batch_convert_*`/`batch_recompress_cbz_confirm`/`show_batch_metadata_dialog` reçoit un dict `callbacks` fourni par `PanelWidget._get_batch_callbacks()` (`panel_widget.py`) :

```python
{
    "natural_sort_key":          lambda s: ...,   # tri naturel des noms de fichiers
    "create_centered_thumbnail": ...,              # génère la vignette PIL affichée en progression
    "safe_delete_file":          self._safe_delete_file,   # suppression (corbeille sauf permanent_delete)
    "get_mosaicview_temp_dir":   self._get_temp_dir,        # dossier pour écrire les logs d'erreurs
    "compute_auto_multipliers":  ...,   # renumérotation auto (utilisé par le flux PDF, voir skill renumbering)
    "generate_auto_filenames":   ...,
    "state":                     self._state,   # AppState du panneau (utilisé par le flux PDF pour renumber_mode)
}
```

Si tu ajoutes un nouveau flux batch qui a besoin d'une info supplémentaire (ex. un nouveau callback), l'ajouter à ce dict central plutôt que de le passer en paramètre séparé — tous les appelants (menu ET drop) passent par cette même fonction.

## Anatomie d'un flux de conversion (CBR→CBZ pris comme référence, `batch_dialogs_qt.py`, de `batch_convert_cbr_to_cbz` à `show_batch_cbr_summary`)

Chaque flux (CBR, CB7, CBT, PDF, IMG, recompress) suit exactement la même mécanique en 4 étapes. **Si tu modifies un flux, vérifie si le même bug/besoin existe dans les 5 autres** — c'est du code dupliqué volontairement (voir section "Pourquoi pas de factorisation").

1. **Point d'entrée public** `batch_convert_XXX_to_cbz(parent, callbacks, directory=None)` : si `directory` est `None`, ouvre `QFileDialog.getExistingDirectory` ; sinon utilise le paramètre (cas drop, dossier déjà connu). Scanne récursivement tous les fichiers de l'extension concernée par **`utils.walk_without_links(directory)`**, jamais `os.walk` direct, puis trie par `natural_sort_key`. `os.walk` (Python 3.11) traverse les jonctions NTFS : le lot traiterait — et supprimerait après conversion — des fichiers situés hors du dossier choisi, et une jonction vers un dossier parent ferait traiter les mêmes fichiers plusieurs fois. `walk_without_links` n'entre ni dans les liens symboliques ni dans les jonctions (`st_reparse_tag`), mais garde les autres points d'analyse, qui sont de vrais dossiers (OneDrive à la demande). Même règle pour tout parcours d'un dossier de l'utilisateur (dépôt de dossiers `drop_handler_qt.py`, import de métadonnées en lot, scan de la Bibliothèque). Testé par `tests/test_untrusted_names.py` (jonction créée par `mklink /J`). Si aucun fichier trouvé → `InfoDialog`. Sinon → `_confirm`.

2. **`batch_convert_XXX_to_cbz_confirm(parent, files, directory, callbacks, directories=None)`** : refuse d'abord le lot si l'un des fichiers est déjà traité par un lot en cours (`_refuse_if_batch_running`, voir « Un seul lot à la fois sur les mêmes fichiers »), puis affiche `_ConfirmDialog` (nombre de fichiers, taille totale, checkbox "suppression permanente" — sauf recompress qui n'en a pas puisqu'il ne supprime rien). Si confirmé → `_run_XXX_conversion`.

3. **`_run_XXX_conversion(...)`** : démarre le lot (`claims = _start_batch_claims(parent, files)`, rien n'est lancé s'il vaut `None`), ouvre `_ProgressDialog` (vignette + nom fichier + barre de pages optionnelle + progression globale + bouton Annuler), lance, via `_start_batch_thread(do_conversion, parent, claims, prog, signals)`, un **`threading.Thread` daemon** qui fait le travail réel (enregistré dans `_batch_threads`, et avec son panneau `parent` dans `_batch_thread_parents`, pour la confirmation et l'arrêt à la fermeture de l'application, voir ci-dessous), communique avec l'UI via `_ThreadSignals` (QObject avec des `Signal`, jamais d'accès direct aux widgets depuis le thread). La vignette est une `QImage` (`_pil_to_qimage`, `.copy()` pour la détacher du tampon PIL), convertie en `QPixmap` par `_ProgressDialog.set_thumbnail` sur le thread de l'interface : **jamais de `QPixmap` créé dans le thread du lot**. Les textes de progression (`update_progress`, `update_page_bar`, déclarés `Signal(object)` et `Signal(float, object)`) sont envoyés comme **fonctions `() -> str`** capturant leurs valeurs (`lambda c=idx + 1, t=total: _("dialogs.batch_cbr.converting_progress").format(current=c, total=t)`), jamais comme texte déjà traduit : le thread travaille sous `latin_texts()` (voir « Journal lisible »), qui rendrait le texte en latin dans une fenêtre en pIqaD, et un texte figé ne suivrait pas un changement de langue. `_ProgressDialog.set_progress` / `set_page_progress` gardent la fonction (`_progress_fn`, `_page_fn` ; un texte fixe, comme `""` ou `label_map[...]`, est accepté tel quel), la résolvent sur le thread de l'interface et la rejouent dans `_retranslate`, qui réapplique aussi la police aux deux libellés (règle UI n° 2). Garde-fou : `tests/test_batch_logs_latin.py` (aucun `_()`/`_wt()` hors d'une `lambda` dans ces envois). À la fin, `signals.conversion_done.emit()` déclenche `on_done()` (dans le thread UI) qui ferme la progression, écrit un log si erreurs/renommages, puis affiche le résumé.

4. **`_XXxSummaryDialog`** : affiche le compte de conversions réussies, les compteurs de renommage (voir ci-dessous), un lien cliquable vers le log si erreurs.

### Arrêt à la fermeture de l'application

Les threads de lot sont des démons : sans arrêt coopératif, l'interpréteur les tue en pleine écriture à la sortie et laisse un CBZ tronqué (illisible) à côté de la source. Mécanisme, dans `batch_dialogs_qt.py` :
- **`_interruptible_zip_writer(path, verify=True, **zip_kwargs)`** (context manager) remplace `zipfile.ZipFile(path, 'w', ...)` pour **tout** fichier de sortie d'un lot (y compris le fichier temporaire de la recompression) : il fournit un `_InterruptibleZip`, dont chaque `writestr`/`write` lève `_BatchInterrupted` si `_batch_shutdown` est posé. Le ZIP est écrit dans un temporaire `.~mosaicview_*.tmp` du dossier de `path` (même volume, créé par `utils.make_temp_path` et libéré par `release_temp_path`), qui ne prend le nom `path` (`replace_file_retrying`) qu'une fois l'écriture et la fermeture du ZIP réussies, puis, avec `verify=True`, sa relecture complète (voir « Relecture du CBZ avant qu'il prenne son nom ») ; sur toute exception (interruption, erreur d'écriture, disque plein à la fermeture du ZIP), le temporaire est supprimé — sauf s'il est devenu la seule copie (`utils.is_kept_temp`, skill `save-export`) — et `path` n'est jamais créé. **Piège** : écrire directement sous le nom final laisserait, après un crash ou un disque plein, un CBZ tronqué portant le nom d'un CBZ valide. Un crash du processus peut au pire laisser un `.~mosaicview_*.tmp`, supprimé à la prochaine écriture dans ce dossier (`remove_stale_temp_files`, skill `save-export`). Testé par `tests/test_batch_zip_writer.py`, avec `_normalized_page_bytes` (extraction AST, comme `test_batch_copy_pages.py` : même règle pour toute nouvelle dépendance, voir « Pièges connus »).
- **`_BatchInterrupted` hérite de `BaseException`** pour traverser les `except Exception` des boucles de conversion (qui passeraient sinon à la page ou au fichier suivant) ; `_start_batch_thread` l'intercepte en sortie de thread (fin silencieuse, sans `conversion_done`), et termine le lot (`claims.finish()`) dans son `finally`, quelle que soit la fin du thread. **Erreur imprévue** dans le thread (toute autre `Exception`) : `_start_batch_thread` émet quand même `signals.conversion_done` (résumé des fichiers déjà traités, fenêtre de progression fermée), puis relance l'erreur pour le journal des erreurs. **Piège** : sans cela, `_ProgressDialog`, jamais marqué terminé, refusait sa croix et restait ouvert jusqu'à la fermeture de l'application.
- **Textes du journal d'un lot** : tous par `_()` — format d'archive non reconnu ou fichier introuvable (`messages.errors.batch_unknown_format`), archive vide (`batch_empty_archive`), original impossible à supprimer après conversion (`batch_source_delete_failed`, avec `{error}`), CBZ de « Images → un seul CBZ » impossible à créer (`batch_cbz_creation_failed`, ligne précédée du nom du CBZ) ; refus d'une image par les lots d'images (`batch_image_unreadable` avec `{error}`, `batch_image_ico`, `batch_image_multiframe` avec `{format}` et `{count}`, dans `_run_img_conversion` et `_run_imgs_to_single_cbz`) ; jamais de texte en dur. Ces refus sont levés par `_UnusableImage` (`expected_error = True`) : un cas normal, consigné dans le journal du lot et jamais dans le journal des erreurs. **Piège** : une `Exception` nue y passerait par `_failure_text` comme un défaut du programme, avec sa pile, à chaque image refusée. Le détail technique cité entre parenthèses (message de Pillow) reste dans sa langue d'origine.
- **Journal lisible dans le Bloc-notes, en toute langue** : un journal de lot (`Log_*.txt`) s'ouvre dans le Bloc-notes, qui affiche en carrés le pIqaD et les tengwar (`tlh-piqad`, `sjn-tengwar`, `qya-tengwar`). Deux mécanismes, sans exception (règle CLAUDE.md « Texte écrit dans un journal ») :
  - **Lignes d'erreur** : `_start_batch_thread` exécute le corps du lot sous `localization.latin_texts()` (contexte propre au thread, qui fait rendre à `_()` la version latine, comme `_wt()`) : tout message traduit construit dans le thread, exceptions traduites comprises, est en latin. Les lignes ajoutées depuis le thread de l'interface (hors de ce contexte) passent par `_wt()`.
  - **En-têtes** (titre, date, dossier, compteurs, titres de sections) : uniquement par `log_title(clé)` (`"MosaicView - " + titre`) et `log_line(clé, **params)` (une ligne terminée par `\n`), en haut de `batch_dialogs_qt.py`, qui lisent le bloc `dialogs.batch_log` par `_wt()` — 23 clés : `title_cbr`/`cb7`/`cbt`/`pdf`/`img`/`img_single`/`recompress`/`metadata`, `date` (`{date}`, format `AAAA-MM-JJ HH:MM` fixé par le code), `directory`/`output` (`{path}`), `total_files`, `converted`, `renamed_kind` (`{kind}` = `"ZIP→CBZ"`, `"RAR→CBR"`, `"7z→CB7"`, `"TAR→CBT"`, fixé par le code), `renamed_misnamed`, `recompressed`, `already_optimal`, `ignored_not_cbz`, `processed`, `skipped`, `errors` (`{count}`), `renamed_files`, `error_details`. Seuls les séparateurs (`'='*60`, `"  - "`) restent écrits en dur. Un nouveau journal ajoute ses titres et compteurs dans ce bloc (46 langues), jamais un texte anglais ni un `_()` dans `lf.write`.
  - Garde-fou `tests/test_batch_logs_latin.py` : aucun texte autre que la mise en forme ni `_()` dans un `lf.write` des deux modules de lots, `log_line` en latin pour une langue pIqaD, `latin_texts()` présent dans `_start_batch_thread` et les workers de l'import de métadonnées.
- **Annulation par l'utilisateur** : bouton Annuler de `_ProgressDialog` (ou croix de la fenêtre : `closeEvent` appelle `request_cancel` et ignore la fermeture tant que le lot tourne ; Échap aussi, `reject` appelant `close()` — `QDialog.reject` masque la fenêtre sans passer par `closeEvent`, et `WA_DeleteOnClose` la détruirait pendant que le thread du lot la met à jour) → `prog.cancel_event` (`threading.Event`), bouton grisé. `_start_batch_thread` range cet Event dans `_batch_local` (`threading.local`) du thread du lot ; `_raise_if_batch_stopped()` (appelée par `_InterruptibleZip.writestr`/`write` et en tête de `_claim_file`, donc avant chaque écriture et au début de chaque fichier) lève `_BatchInterrupted` à la fermeture de l'application, ou **`_BatchCancelled`** (sous-classe) si le lot est annulé. Même chemin de sortie (CBZ en cours jeté par `_interruptible_zip_writer`, source gardée), mais `_start_batch_thread` intercepte `_BatchCancelled` en premier et émet `signals.conversion_done` : `on_done` affiche le résumé des fichiers déjà traités. **Piège** : ces deux points d'arrêt ne tombent jamais entre l'écriture d'un CBZ et la suppression de sa source ; un nouveau point d'arrêt doit respecter la même règle. Un fichier sans écriture (renommage d'un CBR mal nommé) ou une attente du process PDF retardent l'arrêt jusqu'au point suivant. Testé par `tests/test_batch_zip_writer.py` (`test_cancel_button_leaves_nothing_and_keeps_existing_file`).
- **`stop_batches_on_exit()`**, connecté à `aboutToQuit` dans `MosaicView.py` (en premier, avant `shutdown_pdf_probes`, `stop_running_qthreads` et `shutdown_pdf_process`) : pose `_batch_shutdown` puis attend les threads de `_batch_threads` (5 s au total au maximum). La source n'est jamais touchée : elle n'est supprimée qu'après l'écriture complète du CBZ.
- **Confirmation avant fermeture** : `MainWindow.closeEvent` (`MosaicView.py`) appelle `running_batch_panel()` ; si un lot tourne, il ignore l'événement et affiche un `ConfirmYNDialog` (clés `messages.warnings.batch_running_on_exit.title`/`.message`) centré sur ce panneau (`position_dialog_on_parent` avant `show()`). « Oui » pose `_batch_exit_accepted` puis relance `self.close()` ; « Non » ne fait rien, le lot continue. **La question est reposée à chaque clic sur la croix** : `_batch_exit_accepted` n'autorise que la reprise de fermeture qui suit immédiatement le « Oui », et il est consommé **en tête** de `closeEvent`, avant tout retour anticipé (visionneuse avec travail non validé, etc.) — consommé plus bas, un retour anticipé le laisserait actif pour un clic ultérieur. Ne jamais mémoriser l'accord au-delà de cette reprise : la situation a pu changer entre deux clics.
- **`running_batch_panel()`** : panneau ayant lancé le premier lot encore en cours trouvé (`_batch_thread_parents`, renseigné par `_start_batch_thread`), `None` si aucun. `parent` des fonctions `_run_XXX_conversion` est toujours le `PanelWidget` (menu comme dépôt de dossier, via `handle_dropped_paths(self, ...)`).

### Un seul lot à la fois sur les mêmes fichiers — `batch_claims.py`

Module sans Qt [modules/qt/batch_claims.py](../../../modules/qt/batch_claims.py), commun à tous les lots de `batch_dialogs_qt.py` et à l'import des métadonnées en lot (skill `batch-metadata-import`). Thread-safe (un verrou unique pour toutes les opérations).
- **`BatchClaims.start(files)`** : inscrit le lot sur sa liste de fichiers, ou rend `None` si l'un d'eux appartient à un lot encore en cours (test et inscription sous le même verrou : deux lancements simultanés ne démarrent jamais tous les deux). **`finish()`** termine le lot (fichiers à nouveau disponibles). **`files_in_running_batch(files)`** : contrôle sans inscription.
- **Refus du second lot** : `_refuse_if_batch_running(parent, files)` au début de chaque `batch_convert_XXX_to_cbz_confirm` (avant d'afficher la confirmation), puis `_start_batch_claims(parent, files)` au début de chaque `_run_XXX_conversion` (la confirmation est non modale, un autre lot a pu démarrer pendant qu'elle était affichée). Les deux affichent `_show_batch_running` : `MsgDialog` non modal, clés `dialogs.batch_running.title`/`.message`.
- **Réservations par fichier** : en tête de chaque itération, `claims.release_all()` puis `_claim_file(claims, path, conversion_errors)` réserve le fichier traité ; s'il est réservé par un autre lot, il est laissé de côté avec `messages.errors.batch_file_in_other_batch` dans le journal (filet de sécurité : le refus au démarrage couvre normalement ce cas).
- **Nom du CBZ à créer** : `claims.reserve(free_name_candidates(base_path, ".cbz"))` rend le premier nom qui n'existe ni sur le disque ni dans les réservations d'un autre lot, et le réserve (voir « Collision de nom de sortie »).
- **Piège** : sans cette coordination, le même dossier lancé deux fois (un lot par panneau) ferait traiter le même CBR aux deux lots, avec le même nom de CBZ (pas encore créé sur le disque quand le second le choisit). Le premier supprime le CBR après sa conversion ; le second, qui le lit encore page par page (rarfile et 7z rouvrent l'archive à chaque page), perd ses pages suivantes : si son CBZ incomplet prenait le nom final, il remplacerait le CBZ complet du premier puis serait supprimé avec lui (voir aussi `_IncompleteCbz`). Les lots CBT et PDF gardent leur source ouverte, ce qui en empêche la suppression sous Windows, mais la même coordination s'applique à tous.
- **Écritures hors lots** : l'enregistrement d'un panneau et les écritures de la Bibliothèque réservent aussi les fichiers qu'elles écrivent, le temps de l'écriture (`file_operations_qt._claim_files_for_write`, skill `save-export`) ; un fichier détenu par un lot y est refusé (`messages.errors.file_in_batch`), et un lot qui démarre pendant cette écriture laisse le fichier de côté (`_claim_file`).
- Testé par `tests/test_batch_claims.py` (refus, nom non attribué deux fois, deux lancements simultanés synchronisés par `threading.Barrier`). **Piège pour les tests** : le registre est global au module ; un test qui démarre un lot (`BatchClaims.start`) le termine (`finish()`), et la fixture automatique `_no_batch_left_running` de `tests/conftest.py` termine après chaque test tout lot resté en cours, pour qu'il ne réserve pas ses fichiers pour les tests suivants.

### Détection du vrai format avant conversion (`detect_archive_type`)

Avant de traiter un fichier `.cbr`/`.cb7`/`.cbt` comme "vraiment RAR/7z/TAR", chaque flux appelle `detect_archive_type(path)` (magic bytes, `archive_type_detector.py`) — un fichier mal nommé (ex. un vrai ZIP renommé `.cbr` par erreur) est **simplement renommé** vers la bonne extension (`.cbz`/`.cb7`/`.cbt`) au lieu d'être "converti", et compté séparément (`renamed_cbz`/`renamed_cb7`/`renamed_cbt` selon le flux). Le résumé affiche ces compteurs seulement s'ils sont > 0. Un format totalement inconnu → erreur loggée, fichier ignoré.

### Registre anti-GC (`_active_batches`)

`_register_batch(prog, signals)` / `_unregister_batch(prog)` (haut de `batch_dialogs_qt.py`) maintiennent une référence Python vivante sur `prog`/`signals` pendant que le thread tourne — sans ça, le garbage collector pourrait détruire ces objets avant la fin du thread (crash silencieux). **Ne jamais retirer cet enregistrement** dans un nouveau flux ; toujours appeler `_register_batch` juste après avoir créé `_ProgressDialog`+`_ThreadSignals`, et `_unregister_batch` dans `on_done()`.

### Écriture du CBZ de sortie

Tous les flux utilisent le réglage utilisateur via `zip_compression_kwargs(get_config_manager().get_zip_compression_level())` — voir skill `zip-compression`. Normalisation des modes couleur non standard (`CMYK`/`YCbCr`/`I`/`F`) avant écriture par `_normalized_page_bytes` (CBR/CB7/CBT et IMG ; CMYK par profil ICC, `I`/`F` remis à l'échelle sans écrêtage — détail dans skill `batch-cbr-convert`) ; ne jamais réintroduire un `convert("RGB")` direct dans un lot. **Un fichier à plusieurs images (TIFF multipage) est toujours écrit tel quel** (`n_frames > 1`) : le réencoder n'en garderait que la première page, sans échec signalé, et la source serait supprimée — testé par `tests/test_batch_zip_writer.py` (`test_multipage_cmyk_tiff_keeps_every_page`). `gc.collect()` appelé tous les 20 pages pendant l'écriture pour limiter le pic mémoire sur les grosses archives.

**Copie des pages CBR/CB7/CBT — `_copy_pages_to_cbz(cbz, pages, read_page, name_of, on_page)`** (haut de `batch_dialogs_qt.py`, juste après `_unique_flat_name`) : boucle commune aux trois flux « archive classique ». Chaque flux ne fournit que sa façon de lire une page (`archive.read`, `_read_7z_file(cb7_path, f)`, `archive.extractfile(m).read()`), le chemin d'une page (`name_of`, `m.name` pour CBT) et la mise à jour de sa barre de pages (`on_page(courant, total)`, avec sa propre clé `dialogs.batch_xxx.page_progress`). Elle normalise le mode couleur, donne à une page mal nommée l'extension de son vrai format (`archive_names.name_for_real_format`, comme à l'ouverture d'un comic, skill `archive-image-loading`), aplatit le nom via `_unique_flat_name`, fait le `gc.collect()` périodique, et **retourne la liste des pages en échec** `[(chemin, message)]` — lecture impossible (CRC, mot de passe, 7z en erreur) ou écriture impossible. Une page en échec n'arrête pas la copie des suivantes, mais ne passe jamais inaperçue. `_BatchInterrupted` (BaseException) la traverse sans être intercepté. Testée par `tests/test_batch_copy_pages.py` (extraction AST, sans import Qt), y compris sur un vrai CB7 chiffré créé avec le 7z.exe embarqué.

### Suppression de la source — uniquement après une sortie complète

**Lignes des journaux** : chaque ligne variable d'un journal de lot (`  - {entrée}` des fichiers renommés, `  - {erreur}`, et `  - {fichier}: {message}` de l'import de métadonnées) passe par `temp_files.log_text`, qui écrit chaque caractère de contrôle sous sa forme échappée (`\n`) : une erreur cite souvent un nom de membre d'archive, et un nom piégé couperait sinon la ligne et créerait une fausse ligne dans le journal (skill `temp-files`). Toute nouvelle ligne de journal qui écrit un nom ou un message doit y passer. Une exception y est citée par `temp_files.exception_text(e)` (`str(e)`, ou le nom du type pour `EOFError`, `MemoryError`… qui n'ont pas de texte : sinon la ligne « X.cbr: » reste vide). Dans le `except` d'un fichier ou d'une page du lot, l'erreur passe par **`_failure_text(e)`** (haut de `batch_dialogs_qt.py`), qui rend ce même texte et écrit en plus la pile d'une erreur inattendue dans le journal des erreurs (`error_log.log_if_unexpected` ; un fichier abîmé ou refusé n'y va pas, skill `config-storage`) : le journal du lot ne garde que le message, et un défaut du programme répété sur chaque fichier y serait sinon impossible à diagnostiquer. Une fonction de lot exécutée par un test hors de son module (`test_batch_copy_pages.py`, `test_error_reporting.py`) en a besoin dans son espace de noms.

**Journal impossible à écrire** (dossier temporaire plein ou protégé) : chaque `on_done` garde la raison dans `log_error` (`exception_text`), transmise au résumé avec `log_path = None`. Les six fenêtres de résumé composent leur libellé par **`_log_label_text(data, link_text, error_text=None)`** (haut de `batch_dialogs_qt.py`) : lien `link_text` si le journal existe (ouvert par `linkActivated`, jamais par l'adresse du lien) ; sinon `error_text` (nombre d'erreurs) suivi de `dialogs.batch_log_failed` (raison échappée par `html.escape`, le tout dans une balise englobante pour que le libellé soit lu en HTML) ; le libellé est créé aussi quand seul `log_error` est connu. Résumé de l'import de métadonnées : même règle dans `_MetadataSummaryDialog` (skill `batch-metadata-import`). **Piège** : l'échec était avalé, et le résumé « renommages seulement » pointait vers `file:///None`. Testé par `tests/test_audit7_p3.py`.

Règle commune à tous les flux qui suppriment leur source : **la source n'est supprimée que si le CBZ a été entièrement écrit et fermé**. Sinon le CBZ incomplet est jeté, la source conservée, l'erreur consignée dans le journal du lot, et le fichier n'est pas compté comme converti.

**Un CBZ incomplet ne prend jamais le nom final — `_IncompleteCbz`** : l'incomplétude est constatée **dans** le bloc `with _interruptible_zip_writer(...)`, qui lève alors `_IncompleteCbz(failures)` ; le temporaire est supprimé par l'écrivain et aucun fichier ne porte le nom du CBZ. **Piège** : constater l'échec après la sortie du `with` puis supprimer le CBZ par son nom final supprime ce qui porte ce nom à ce moment-là — après `replace_file_retrying`, le CBZ incomplet a remplacé tout fichier de ce nom apparu entre-temps (CBZ complet d'un autre traitement). Ne jamais supprimer par son nom un CBZ de sortie incomplet. Testé par `tests/test_batch_zip_writer.py` (`test_incomplete_cbz_never_replaces_an_existing_file`).
- **CBR/CB7/CBT** : si `_copy_pages_to_cbz` retourne des échecs, `raise _IncompleteCbz(failed_pages)` dans le `with` ; l'`except _IncompleteCbz` de la boucle appelle `_log_incomplete_cbz(basename, failures, conversion_errors)`, qui ajoute au journal `"{fichier}: "` suivi de `messages.errors.batch_incomplete_kept` (`count` = nombre de pages en échec, `detail` = première page et son erreur ; « Pages non converties : {count}. Fichier d'origine conservé ({detail}) »), traduit dans la langue courante au moment du traitement (ni suppression ni `converted_count`). Elle ne touche à aucun fichier.
- **PDF** : un `timeout` de `_recv` ou un message `('error', …)` du process en cours de document pose `pdf_incomplete` ; pages en échec ou nombre de pages écrites différent du total aussi. Dans tous les cas `_IncompleteCbz` est levée dans le `with`, et le PDF conservé.
- **IMG, mode un seul CBZ** (`_run_imgs_to_single_cbz`) : si aucune image n'a pu être écrite, `_IncompleteCbz` est levée dans le `with` (aucun CBZ vide créé ; chaque échec est déjà au journal, l'`except _IncompleteCbz` ne fait rien d'autre). Les images écrites sont accumulées dans `written_images` et supprimées (et comptées) seulement **après** la fermeture réussie du ZIP. Supprimer chaque image juste après son `writestr` les perdait toutes si le ZIP n'était pas fermé : interruption à la fermeture de l'application (`_interruptible_zip_writer` supprime alors le CBZ) ou échec d'écriture du répertoire central.
- **IMG, mode un CBZ par image** : la suppression a déjà lieu après la sortie du `with` de chaque CBZ.
- **Relecture du CBZ avant qu'il prenne son nom** : `_interruptible_zip_writer` (avec `verify=True`, valeur par défaut) relit entièrement le temporaire par `utils.verify_written_cbz(tmp, expected_count, shown_path=path)` (CRC de chaque fichier) **avant** `replace_file_retrying`. Chaque flux de conversion pose dans son bloc `with` le nombre de fichiers attendu, `cbz.expected_count` : `total_pages` (CBR, CB7, CBT), `pages_written` (PDF), 1 par image, `len(written_images)` (un seul CBZ). Échec → `WrittenFileCheckError`, temporaire supprimé, aucun fichier ne porte le nom du CBZ ; l'`except` de la boucle consigne `"{fichier}: "` + le texte de l'erreur (`messages.errors.written_file_check_failed`, nommant le CBZ final), la source est gardée et le fichier non compté (le lot PDF a son propre `except WrittenFileCheckError`, sans redémarrer le process PDF). Une fois le `with` passé, le CBZ qui porte son nom est donc toujours relu : la source peut être supprimée. **Piège** : relire le CBZ après lui avoir donné son nom obligerait à le supprimer par ce nom s'il est abîmé — or `batch_claims` ne réserve le nom qu'auprès des autres lots ; un « Enregistrer sous » depuis un panneau, l'Explorateur ou un autre programme peut y avoir écrit entre-temps, et ce fichier serait supprimé. `verify=False` est réservé à la recompression, qui contrôle sa structure avant de remplacer l'original. Voir skill `save-export` (« Relecture avant suppression »).
- **Mise à la Corbeille** : `callbacks['safe_delete_file']` (`PanelWidget._safe_delete_file`) appelle `utils.send_to_trash`, seule implémentation de l'application (jamais de suppression définitive en repli ; garde-fou `tests/test_check_single_trash.py`).

Tout nouveau flux qui supprime sa source doit suivre cette règle : jamais de `except Exception: continue` qui ignore une page en silence avant une suppression, CBZ écrit par `_interruptible_zip_writer` avec sa relecture (jamais `verify=False`) et `cbz.expected_count` posé dans le bloc, suppression de la source après la sortie du `with`. Garde-fou : `tests/test_check_atomic_file_writes.py` (règle 4) exige, dans la fonction qui supprime une source (Corbeille ou `os.remove` du même chemin), une relecture placée avant la suppression, et que l'écrivain relise avant de renommer et ne supprime jamais que son temporaire. Les boucles complètes des lots sont testées par `tests/test_batch_loops.py`.

**CBZ aplati — ordre de lecture conservé** (CBR/CB7/CBT, et mode « un seul CBZ » du lot d'images, qui parcourt les sous-dossiers par `walk_without_links`) :
- **Tri par chemin complet** (dossier puis nom, `natural_sort_key(chemin.lower())`), jamais par le seul nom de fichier : `Ch1/001`, `Ch2/001`, `Ch1/002`… se suivraient, chapitres entrelacés. Lot d'images : chemins relatifs au dossier commun des images (`os.path.commonpath`, repli sur le chemin sans lecteur si les images sont sur plusieurs lecteurs).
- **`_flat_names(member_paths)`** : nom à plat qui garde le dossier devant le nom (`Chapitre 1/001.jpg` → `Chapitre 1_001.jpg`), pour que l'ordre alphabétique du CBZ (celui des lecteurs de BD) reste l'ordre de lecture ; le dossier commun à tous les membres (archive entièrement rangée dans `MonComic/`) est retiré. Les segments étant joints par `_`, un nom piégé de l'archive source (`../x.jpg`) devient `.._x.jpg`, sans séparateur : le CBZ produit ne contient jamais de nom qui sortirait du dossier d'extraction d'un autre lecteur. Chaque caractère de contrôle (retour à la ligne, tabulation…) d'un segment devient `_` (`archive_names.without_control_chars`, importée dans la fonction : les tests l'extraient par AST) — Windows le refuse dans un nom de fichier, et d'autres lecteurs échoueraient à extraire la page ; testé par `test_control_characters_are_replaced`. L'import de métadonnées en lot, qui garde les sous-dossiers, applique à la place `archive_names.contained_member_name` puis un nom unique (skill `batch-metadata-import`). `_copy_pages_to_cbz` le calcule une fois pour toutes les pages, puis passe chaque nom par `_unique_flat_name`.

**Noms uniques — `_unique_flat_name(member_path, written_names)`** (haut de `batch_dialogs_qt.py`) : reçoit le nom à plat (son nom de base, s'il contient encore un chemin). Deux membres homonymes dans des dossiers différents (`A/p.jpg`, `B/p.jpg`) donneraient deux entrées ZIP de même nom dont une seule est lisible — perte de page définitive puisque l'archive source est supprimée ensuite. Le doublon reçoit donc un suffixe `_2`, `_3`… (comparaison insensible à la casse, séparateurs `/` et `\` gérés), qui le trie juste après l'original par `natural_sort_key`. Un nom sans collision est écrit inchangé. `written_names` est un `set()` créé juste avant la boucle d'écriture de chaque archive. Tout nouveau flux qui aplatit les chemins d'une archive doit passer par `_flat_names` puis cette fonction plutôt que `os.path.basename` direct. Testé par `tests/test_batch_unique_flat_name.py` (extraction AST, sans import Qt, dont `test_chapters_are_not_interleaved`).

**Commentaire d'archive ZIP conservé** : la recompression recopie `zin.comment` (métadonnées ComicBookInfo de ComicRack/ComicTagger) ; `_InterruptibleZip` a un setter `comment` qui le transmet au vrai ZIP — sans lui, l'affectation créerait un attribut de l'enveloppe et rien ne serait écrit. Testé par `tests/test_batch_zip_writer.py` (`test_archive_comment_is_written`).

### Collision de nom de sortie

Le nom du `.cbz` de destination (et le nouveau nom d'un fichier mal nommé à renommer) est obtenu par `claims.reserve(free_name_candidates(base_path, ext))` (`batch_claims.py`) : premier nom de la suite `base.ext`, `base (1).ext`, `base (2).ext`… (format `"{base}_{n:02d}{ext}"` pour le lot d'images) qui n'existe pas sur le disque **et** n'est réservé par aucun autre lot — ne jamais écraser un fichier existant silencieusement. **Piège** : un simple `os.path.exists` ne voit pas le CBZ qu'un autre lot est en train d'écrire dans un temporaire ; les deux lots choisiraient le même nom.

## Spécificités par flux

Résumé condensé ci-dessous — chaque flux a son propre skill détaillé (calcul exact, pièges, sections "comment étendre" dédiées) ; lien direct depuis chaque puce.

- **CBR→CBZ** (`batch_convert_cbr_to_cbz`) : nécessite `rarfile` (sinon `ErrorDialog` immédiat, pas de scan). Vignette lue via `rarfile.RarFile`. Détail complet : skill `batch-cbr-convert`.
- **CB7→CBZ** (`batch_convert_cb7_to_cbz`) : vignette/lecture via `_list_7z_files`/`_read_7z_file` (`archive_loader.py`, wrapper autour du binaire `7zip/`). Détail complet : skill `batch-cb7-convert`.
- **CBT→CBZ** (`batch_convert_cbt_to_cbz`) : utilise `tarfile` stdlib, pas de dépendance externe. Détail complet : skill `batch-cbt-convert`.
- **PDF→CBZ** (`batch_convert_pdf_to_cbz`) : nécessite `PDF_AVAILABLE` (import `pymupdf` réussi). Lance bien un `threading.Thread` comme les autres, mais ce thread ne décode aucun PDF lui-même : il communique avec un **process dédié au batch** (`modules/qt/pdf_loading_qt.py`, `_spawn_pdf_process`/`_kill_pdf_process`, protocole de messages `batch_open`/`batch_ready`/`batch_convert`/`batch_page`/`done`/`error`/`password_error`), créé une fois pour toute la durée du lot puis détruit à la fin — jamais partagé avec un panneau ni un autre batch, voir skill `pdf-loading` pour l'architecture PDF complète. Gère la renumérotation auto des noms de page selon `state.renumber_mode` (skill `renumbering`) et les PDF protégés par owner-password (convertis, mais source jamais supprimée). Détail complet : skill `batch-pdf-convert`.
- **IMG→CBZ** (`batch_convert_img_to_cbz`) : seul flux avec un choix préalable de **mode** (`_ImgModeDialog` : une image = un CBZ, ou toutes les images du dossier = un seul CBZ multi-pages). Rejette les ICO et les images multi-frames (GIF animé, etc. — `n_frames > 1`, sauf JPEG MPO, une photo ordinaire) avec une erreur explicite plutôt qu'une conversion silencieusement fausse. Détail complet : skill `batch-img-convert`.
- **Recompression CBZ** (`batch_recompress_cbz_confirm`) : seul flux qui ne supprime ni ne convertit un format différent — relit chaque CBZ et le réécrit avec `zip_compression_kwargs(level)` courant. Pas de checkbox suppression (rien à supprimer). Skip les archives déjà au niveau optimal (`_detect_zip_compression_state`) pour éviter un travail inutile. Le CBZ réécrit est contrôlé (`check_written_cbz_structure`, nombre de fichiers de la source) avant de remplacer l'original, et un temporaire devenu la seule copie (`is_kept_temp`) n'est pas supprimé (skill `save-export`). Renomme aussi les fichiers mal étiquetés (extension ≠ `.cbz` mais contenu réellement ZIP), comme les autres flux. Détail complet : skill `batch-recompress`.
- **Import métadonnées ComicVine** (`batch_metadata_dialog_qt.py`) : seul flux qui n'écrit pas en arrière-plan silencieux — ouvre la **fenêtre ComicVine interactive** (`comicvine_dialog_qt.py`, voir skill `comicvine-metadata-fetch` pour le détail du scraping réseau/wizard) séquentiellement pour chaque fichier, avec caches de recherche partagés entre fichiers (`_search_cache`/`_issues_cache`) pour éviter de re-interroger l'API pour une série déjà vue dans le lot. `_BatchMetadataOrchestrator` pilote la séquence : charge un `AppState` allégé du fichier courant dans un `QThread` (`_LoadWorker`, via `parse_comic_info_xml` — voir skill `comicinfo-metadata-editor`), affiche/actualise la fenêtre ComicVine (au lieu d'en recréer une à chaque fichier), sauvegarde en `QThread` (`_SaveWorker`, via `write_comic_metadata_from_scraper` — voir skill `comicinfo-metadata-editor`) à la validation, avance au suivant. Option "ignorer les fichiers ayant déjà un ComicInfo.xml" (`skip_existing`). Bouton Annuler pendant le traitement → `_CancelConfirmDialog` (continuer/arrêter), arrêt propre qui garde acquis les fichiers déjà traités. Détail complet : skill `batch-metadata-import`.
- **Bibliothèque** (`_make_batch_library`, `drop_handler_qt.py`) : le plus atypique des 8 — pas de scan, pas de confirmation/progression/résumé propres, ouvre simplement `LibraryWindow` + `NewDbDialog` pré-rempli (`preset_dir`) puis ajoute les dossiers supplémentaires après validation. Seul accessible par drop, aucune entrée de menu. Détail complet : skill `batch-library-create`.

## Comment ajouter un nouveau flux de conversion batch (ex. XYZ→CBZ)

1. Dans `batch_dialogs_qt.py`, copier intégralement la structure du flux le plus proche (CBT est le plus simple, pas de dépendance externe) :
   - `_XyzSummaryDialog` (classe résumé — copier `_CbtSummaryDialog`, adapter les clés de traduction `dialogs.batch_xyz.*` et les compteurs de renommage pertinents).
   - `batch_convert_xyz_to_cbz(parent, callbacks, directory=None)` — scan + garde "aucun fichier".
   - `batch_convert_xyz_to_cbz_confirm(parent, files, directory, callbacks, directories=None)` — `_refuse_if_batch_running` + `_ConfirmDialog` + branchement vers `_run_xyz_conversion`.
   - `_run_xyz_conversion(...)` — `_start_batch_claims` (retour si `None`) + `_ProgressDialog` + `_ThreadSignals` + `_register_batch`/`_unregister_batch` + thread lancé par `_start_batch_thread(do_conversion, parent, claims, prog, signals)` (jamais `threading.Thread` directement — sinon ni confirmation ni arrêt propre à la fermeture de l'application, ni annulation, ni fin du lot) + dans la boucle, `claims.release_all()` puis `_claim_file` pour chaque fichier et `claims.reserve(free_name_candidates(...))` pour chaque nom à créer + écriture CBZ via `_interruptible_zip_writer` (jamais `zipfile.ZipFile(..., 'w')` directement — voir « Arrêt à la fermeture de l'application »), `_IncompleteCbz` levée dans le `with` si des pages manquent + log + résumé.
2. Ajouter toutes les clés de traduction `dialogs.batch_xyz.*` dans **toutes** les langues (`locales/*.json`) — voir skill `add-translation`. Clés minimales à couvrir (calquer sur `batch_cbt`) : `select_directory_title`, `no_xyz_title`/`no_xyz_message`, `confirm_title`/`confirm_message`, `checkbox_permanent_delete`, `start_button`, `converting_title`, `converting_progress`, `page_progress` (si barre de pages), `complete_title`, `complete_message`/`complete_message_errors`, `errors_count`.
3. Dans `panel_widget.py` : ajouter `_get_batch_callbacks()`-compatible méthode `_batch_convert_xyz_to_cbz(self)` sur le modèle de `_batch_convert_cbt_to_cbz`.
4. Dans `menubar_callbacks_qt.py` : ajouter l'entrée dans le dict de callbacks (`"batch_convert_xyz_to_cbz": mw._batch_convert_xyz_to_cbz`).
5. Dans `menubar_qt.py` : ajouter `_add_action(batch_menu, _("menu.batch_xyz_to_cbz"), callbacks.get("batch_convert_xyz_to_cbz"))` près des 5 autres (sous-menu `batch_menu` de `_populate_file_menu`).
6. Dans `batch_drop_dialog_qt.py` (`BatchDropDialog`) : ajouter un `QRadioButton` (`self._radio_xyz`), l'enregistrer dans `self._btn_group.addButton(self._radio_xyz, N)` avec le bon index, l'ajouter au layout, au tuple de résolution dans `_on_ok` (`self.chosen = (...)[checked]`), et à `_retranslate()`.
7. Dans `drop_handler_qt.py` (`_show_batch_drop_dialog`) : ajouter une fonction `_make_batch_xyz()` sur le modèle de `_make_batch_cbt` (scan récursif sur `dirs`, garde "aucun fichier", appel à `batch_convert_xyz_to_cbz_confirm(parent, files, dirs[0], batch_callbacks, directories=dirs)`), puis l'ajouter au dict `callbacks` final avec la clé `'batch_xyz'` (doit correspondre à `"batch_" + dlg.chosen` résolu dans `show_batch_drop_dialog`).
8. Respecter les 8 règles UI Qt obligatoires du CLAUDE.md pour toute nouvelle fenêtre (`_XyzSummaryDialog` notamment) : non-modale, thème, langue à la volée, `_wt()` pour le titre, centrage sur le panneau source.

## Pourquoi pas de factorisation malgré la duplication massive

Les 5 flux de conversion (CBR/CB7/CB7/CBT/PDF/IMG) partagent ~80% de code identique (structure confirm/progress/summary/thread/registre anti-GC). C'est un choix assumé du projet existant, pas un oubli. Seule exception : la boucle de copie des pages CBR/CB7/CBT, mise en commun dans `_copy_pages_to_cbz` (section "Écriture du CBZ de sortie") pour que la détection des pages en échec ne puisse pas diverger entre les trois flux. Ne pas lancer d'autre refactoring de factorisation sans demande explicite de l'utilisateur (règle CLAUDE.md : ne jamais modifier hors du périmètre demandé). Si une demande porte sur "corriger un bug dans le flux CBR", corriger uniquement CBR sauf instruction contraire, même si le même bug existe ailleurs — le signaler et attendre l'accord.

## Pièges connus

- **Boucles de lot testées par `tests/test_batch_loops.py`** : les fonctions `_run_*` (sauf le lot PDF, exécuté par `tests/test_error_reporting.py`) et leurs aides sont extraites par `tests/ast_loader.py`, qui refuse toute dépendance absente de l'espace de noms (le test échoue en la nommant). Une nouvelle dépendance d'une boucle (fonction importée en tête de `batch_dialogs_qt.py`, nouvelle aide du module) s'ajoute à `LOOPS`/`HELPERS` ou à l'espace de noms de la fixture `batch`. Les fenêtres, signaux et lecteurs RAR/7z y sont remplacés ; `modules.qt.archive_loader` est remplacé par un module contenant ses vraies fonctions de lecture et de taille (tout nom importé localement d'`archive_loader` par une boucle doit y figurer).
- **Test extrait par AST : déclarer chaque nouvelle dépendance** : `tests/test_batch_copy_pages.py` n'importe pas `batch_dialogs_qt.py` (qui importe Qt) ; `_load()` en extrait par AST une liste nommée de fonctions (`_unique_flat_name`, `_normalized_page_bytes`, `_copy_pages_to_cbz`, `_log_incomplete_cbz`) et les exécute dans un espace de noms fourni à la main (`os`, `io`, `gc`, `Image`, la fausse traduction `_fake_translate` pour `_`, la constante `_PAGE_FORMATS`). Toute nouvelle dépendance de ces fonctions — fonction du module, constante de module (un `Assign` n'est pas extrait, seules les `FunctionDef` le sont), appel à `_()` — doit être ajoutée à cette liste ou à cet espace de noms. Sinon, `NameError` à l'exécution du test ; pire, si l'appel se trouve dans un `try/except Exception` (cas de la normalisation des pages dans `_copy_pages_to_cbz`), l'erreur est avalée et le test passe sans vérifier cette partie.
- **Supprimer la source alors que le CBZ est incomplet** : une page ignorée par un `except Exception: continue`, un `break` sur timeout, ou une source supprimée avant la fermeture du ZIP laissent un CBZ incomplet (voire vide) à la place de l'original, parfois supprimé définitivement. Voir "Suppression de la source — uniquement après une sortie complète". Garde : `tests/test_check_no_swallowed_loop_errors.py` (scan AST de `modules/qt/` et `MosaicView.py`) échoue sur tout nouvel `except Exception: continue` dans une boucle ; un cas réellement sans conséquence se déclare dans sa liste `ALLOWED`, avec la raison.
- **Callback manquant dans `_get_batch_callbacks()`** : un nouveau flux qui a besoin d'une info non présente dans le dict actuel doit l'y ajouter en un seul endroit (`PanelWidget._get_batch_callbacks`) — ne jamais créer un chemin d'appel parallèle qui contourne cette fonction, sinon le menu et le drop divergent silencieusement.
- **Oublier `_register_batch`/`_unregister_batch`** : crash aléatoire et difficile à reproduire (le thread accède à un `QObject` déjà détruit par le GC). Toujours les deux, jamais l'un sans l'autre.
- **Écrire dans l'UI depuis le thread `do_conversion`** : toute mise à jour visuelle doit passer par `signals.update_*.emit(...)`, jamais un appel direct à une méthode de `_ProgressDialog` depuis le thread — violerait le threading Qt (widgets non thread-safe).
- **`directory` (singulier) vs `directories` (liste)** : le menu passe toujours `directories=None` (un seul dossier choisi par dialogue) ; le drop passe `directories=dirs` (plusieurs dossiers déposés). `_add_dir_links` dans les fenêtres de résumé gère les deux cas — ne pas supposer qu'un seul dossier est toujours affiché.
- **Le décodage PDF ne se fait pas dans le thread du lot** — le thread délègue à un process séparé avec un protocole de messages et n'écrit que le CBZ résultant. Chaque appelant (panneau, batch, import métadonnées) doit créer et détruire son propre process via `_spawn_pdf_process`/`_kill_pdf_process` — ne jamais réutiliser le process d'un autre appelant, sous peine de "pipe broken" si deux chargements PDF tournent en même temps (voir skill `pdf-loading`). Ne pas copier le pattern PDF pour un nouveau flux simple ; copier plutôt CBT.
- **`_BatchMetadataOrchestrator` garde une référence module-level** (`_active_orchestrators`) le temps du batch — même piège anti-GC que `_register_batch`, mécanisme séparé car ce flux n'utilise pas `_ThreadSignals`/`_ProgressDialog`.

## Références croisées

Les 8 traitements ont chacun leur skill dédié, à consulter pour le détail exact (lignes de code, pièges propres, sections "comment étendre") plutôt que de dupliquer ici :

- `batch-cbr-convert` / `batch-cb7-convert` / `batch-cbt-convert` — les 3 flux "archive classique" quasi identiques en structure (résumé/log à 3 compteurs de renommage), qui ne diffèrent que par leur bibliothèque de lecture (`rarfile`/binaire `7z.exe`/`tarfile` stdlib). CBT est le modèle recommandé pour un nouveau flux simple.
- `batch-pdf-convert` — le flux le plus complexe, process séparé dédié au batch (voir skill `pdf-loading`), détection DPI intelligente, renumérotation auto, déverrouillage owner-password.
- `batch-img-convert` — seul flux avec un choix de mode préalable et une validation stricte par image (rejet ICO/multi-frame).
- `batch-recompress` — seul flux sans conversion de format ni suppression, fenêtre de confirmation dédiée (pas `_ConfirmDialog`).
- `batch-metadata-import` — seul flux interactif (pas de traitement silencieux), orchestrateur piloté par événements plutôt qu'une boucle synchrone, state allégé par fichier.
- `batch-library-create` — le plus atypique des 8, aucune des briques communes (scan/confirm/progress/résumé), accessible uniquement par drop.
- `pdf-loading` — architecture des process PDF dédiés (un par chargement, jamais partagé), utilisée par le flux PDF→CBZ ci-dessus et par `batch-metadata-import` pour écrire un CBZ à partir d'un PDF.
- `zip-compression` — réglage de compression utilisé par 6 des 8 flux (tous sauf IMG et Bibliothèque).
- `temp-files` — emplacement des logs d'erreurs/renommages écrits par la plupart des flux.
- `library` — `LibraryWindow`/`NewDbDialog`, réutilisées telles quelles par `batch-library-create`.
